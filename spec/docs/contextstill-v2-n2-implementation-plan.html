0. ownerの方針（2026-10-30）

正直repo固有の知識とか蓄積したくないので、まずはglobalを基本とし、重複、矛盾を排除したナレッジベースにしたいです。何時でも似たようなシナリオだった場合の有効な情報を引き出したい

  1. repo固有の知識は蓄積しない。globalが基本。
  2. 重複と矛盾を取り除いた知識ベースにする。
  3. 検索の目的は、似たシナリオ（状況）が来たときに、有効だった情報を引き出すこと。

維持する方針：Eumenesがsearchして使う知識基盤であること、graphはN3、context_compileはコーディングエージェント向けでN5に移植、テーマ単位の蒸留を残す、コーディングエージェントの蓄積は捨てずに行を残して根拠（L1／L0）にする、TypeScript only、embeddingはLARMのintfloat/multilingual-e5-small（384次元）。

1. 目的と非目標

目的

  • 原子知識（L1）9,530件（active）を、状況（どんなときに効くか）を第一級に持つ正本知識（L2）へ再蒸留する。重複はクラスタ単位でまとめ、矛盾は検出して解くかownerの確認へ回す。
  • repo固有の事実は検索から外す（行は消さない）。汎用化できる教訓は、repo名・path・portなどを外した正本として取り込む。scope・repo・spaceをまたいで重複を束ねる。
  • 正本ができた原子知識をsupersededにして検索から外し、検索とMCPの主対象を正本へ切り替える。MCPの既定spaceを全spaceにする。
  • テーマ（2階層）とテーマ知識、facet語彙の正規化、正本に添える一般化した事例を作る（段階N2b）。
  • シナリオ形式の評価集合と、上位k件の重複率・矛盾率を作り、N2の完了を数値で判定する。

非目標（N2で作らない）

  • 芋づる展開、related_knowledge・browse_theme・knowledge_feedback、LLMによる型付き関係（requires、supports、refines）、co_used、テーマ一致の検索lane。いずれもN3。N2が書くmap_edgesはsupersedes、contradicts、about、broader、example_of（candidate）だけである。
  • 新しい原子知識の生成（finding、covering、finalize、Episode蒸留、agent logの同期）。N4。N2は旧版からの差分取り込みで増えた・変わった原子知識をクラスタへ足す最小の差分stageだけを持つ。
  • context_compileの移植とrepo scopeのfail-closed分離（N5）。Web UI。外部へ出すLLM providerの本実装（ownerの判断待ち。14章）。

2. すべてのworkstreamに共通する制約

4. 設計の要点

  • scopeは由来の記録にする。正本は常にscope='global'・repo_key=NULLで作る。原子知識とEpisodeのscope・repo_keyは取り込んだ由来としてそのまま残し、検索の安全柵（repo scopeの行はrepoKeyなしでは出ない）も残す。検索に出すかどうかは新しい列retrieval（searchable／evidence_only）で決める。
  • 一般性の判定：原子知識をgeneral（そのまま一般知識）、generalizable（repoの具体を外せば一般の教訓）、repo_specific（特定repoの事実）、unusable（行動に使える内容がない）に分ける。旧scopeは判定の材料にするだけで、globalの行も判定する。repo_specificとunusableはevidence_onlyにする。
  • 正本は状況を第一級に持つ：状況（situation）、有効だった対処（body）、理由（rationale）、適用する条件・しない条件、手順、例外、事例、根拠の原子知識。検索の問いは状況の記述として来る前提で、FTSは状況の列を最も重くし、ベクトルは状況を先頭に置いた文で作る。
  • 重複：scope・repo・spaceをまたぎ、type・polarityでも分けずに、上限12件の平均連結でclaimクラスタを作る。LLMはplanner（部分集合への分割と下書き）とverifier（独立の照合）の2段で、その間にhost側の照合を挟む。正本へ吸収した原子知識はsupersedesで繋いでsupersededにする。
  • 矛盾：クラスタ内はplannerが部分集合間の関係として出し、クラスタ間は正本の近傍の組をLLMで判定する。条件違いは状況別の指針に分け、本当の対立は根拠の強さと新しさで決めて負けた側をretractedにし、決めきれないものはownerの確認queueへ回す。auditで「active正本どうしに未解決の対立がない」を検査する。
  • 切り替えは段階的：検索の既定layerを["canonical","atom"]にし、retrieval='searchable'かつstatus='active'の行だけを出す。吸収された原子知識はsuperseded、repo固有はevidence_onlyになるので、再蒸留が進むほど原子知識は検索から自然に消える。未吸収の一般的な原子知識だけが一時的な予備として残る（点数は0.8倍）。
  • LLMの実行はbackendのqueueで行う。queue domainにhandlerを載せ、backendがrunnerとretentionを回す。stageの投入、状況の確認、確認queueの解決はAPI（/api/distill/*）と、それを呼ぶ薄いCLI（bun run distill）で行う。

6. stageごとの設計

6.0 前提：ベクトル

  • クラスタリングと矛盾候補はベクトルが前提である。distill.clusterは、母集団の行のベクトルがorigin='larm'かverification='verified'で、かつcontent_digestが一致するものだけを使い、使えない行が母集団の1%を超えたらdistill_vectors_unverifiedで止まる。allowUnverified:trueは試行（pilot）専用で、そのrunで作ったclusterはalgorithmに|unverifiedを付け、canonical stageはこれを拒否する。
  • owner作業（N1から残っているもの）：bun run vectors:verify-legacy、不合格ならbun run vectors:embed -- --owner knowledge --all（約9.6k件）、bun run vectors:embed -- --owner episode（14,160件。N2bの事例とテーマに必要）。いずれもbackend停止中に行う。

6.1 S1 一般性の判定（assess）

  • 対象：activeの原子知識9,530件と、scope='global'のEpisode 843件。repo scopeのEpisode 13,317件は判定せず、検索に出ないまま根拠として残す（N1の範囲の絞り込みで既に出ない）。
  • 決定的な兆候（signals_json）：(a) repo名の出現（knowledgeとepisodesの全repo_key 204種＋のうち4文字以上で、一般語の除外表に無いもの。除外表はdistill/service/checks/repo-terms.tsに固定し、todolistのような一般語を入れる）、(b) 絶対path（/Users/、/home/、~/、[A-Z]:\）、(c) repo内の相対path（[\w.-]+/[\w./-]+\.(ts|tsx|js|rs|py|go|md|json|toml|sql|yml|yaml|dart)）、(d) port（(localhost|127\.0\.0\.1|\[::1\]):\d{2,5}、port\s*\d{4,5}）、(e) 旧scope・repo_key・classificationStatus。
  • LLM：20件ずつassessOutputで判定させる。promptには定義と例（repo固有＝特定repoのfile・設定値・機能・決定の事実、汎用化可能＝repo名を外しても他のrepoで通じる教訓）を書く。
  • 決定：LLMの判定を採る。ただしLLMがgeneralで兆候(b)(c)(d)のいずれかがあればgeneralizableに下げる（正本の段階で具体を外させる）。repo_specificとunusableは同じtransactionでretrieval='evidence_only'にする。判定時のcontent_digestを保存し、本文が変わったら再判定の対象にする。
  • 確かめ方：判定の層（旧scope×判定）で200件を層別に抜き、agentが判定の正否を付け、ownerが40件を確認する。repo_specificの精度≥0.90、再現率≥0.80を合格とする。不合格ならpromptを直して再判定する（promptVersionを上げると全件が対象になる）。

6.2 S2 閾値の較正

  • calibrationSample(300)：判定がgeneral／generalizableの原子知識の10近傍の組を、類似度の帯（0.86–0.89、0.89–0.91、0.91–0.93、0.93–0.95、0.95–0.97、0.97–1.00）ごとに50組、sha256(pairId)の順で決定的に選ぶ。scopeをまたぐ組とtype・polarityが違う組を、母集団の比率以上に含める。
  • ラベル：「同じ主張（統合して失うものがない）」same／different／unsure。agent-draftで全件を付け、ownerが60組を確認する。ラベルはgitに入れずdata/distill/（gitignore済み）に置く。
  • applyCalibration：clusterEdgeはsameの組の再現率が0.95以上になる最大の閾値、clusterMergeは平均連結で純度が0.90以上になる最小の閾値を、ラベルから計算する（unsureは除く）。pairCandidateはclusterEdge − 0.03。結果をdistill_params.thresholdsへ保存し、calibratedAtを入れる。

6.3 S3 claimクラスタ

  • 母集団：activeでretrieval='searchable'、判定がgeneral／generalizableの原子知識。scope、repo、space、type、polarityで分けない（type・polarityは下書きの材料としてLLMへ渡し、極性の対立は矛盾の候補として扱う）。
  • 近傍：Float32の総当たりで20近傍（約9.5k件で13秒。計測値）。clusterEdge以上の辺を候補とする。
  • 凝集：候補辺で繋がった2つのclusterだけを併合の候補にし、平均連結（全組のcosineの平均を、ベクトルから正確に計算）が最も高い組から、clusterMerge以上かつ併合後の大きさがclusterCap（12）以下の間だけ併合する。同点は平均連結の降順、2つのclusterの最小seqの昇順。単連結の鎖（3章）を避けるためである。
  • 保存：大きさ2以上をmap_clusters(kind='claim', state='pending')に、各memberをcentroidとの類似度付きで保存する。大きさ1の行はclusterを作らず、canonical stageで8件ずつまとめて処理する。既存のclusterとmember_digestが同じならそのまま（unchanged）、構成が変わったら新しいclusterを作り、古いものをstaleにする。
  • 件数の見込み（推測）：t=0.94の単連結で1,669件が532成分に入ることから、複数要素のclusterは1,000〜2,000個、そこに入る原子知識は2,500〜5,000件、単独が4,000〜6,500件と見込む。正本は6,500〜8,500件（重複の削減15〜30%）。較正後に計り直す。

6.4 S4 再蒸留（planner → host照合 → verifier）

  1. planner：clusterの原子知識（別名、type、polarity、title、body、旧scopeとrepoの有無、判定）を渡し、plannerOutputを返させる。指示の要点：同じ主張の部分集合に分ける（全memberをちょうど1回ずつ使う）、正本はsituation（どんな状況で効くか。具体的な状況の記述）を先に書く、repo名・path・port・識別子を外して一般化する（他repoでも通じる言い方にする）、原子知識にない主張を足さない、主張を1文ずつclaimsに支持する別名付きで書く、条件の違う部分集合の関係をrelationsに書く。旧版のlandscape-curation-v2（git show legacy/v1:shared/prompts/landscape-curation-v2.txt）の「条件・否定・例外・数値・識別子を保つ」「類似は根拠にならない」を引き継ぐ。単独の原子知識は8件まとめて同じschemaで正本化する（groupは1件ずつ）。
  2. host照合（決定的。distill/service/checks）：
    • 別名の実在と所属：members・supportの別名がすべて入力に存在し、各supportが自分のgroupのmemberである。
    • 被覆：入力のmemberが、groupsにちょうど1回ずつ現れる。
    • 新しい主張がない：各claimの内容語（Intl.Segmenterの2文字以上の語から停止語を除く）のうち、支持する原子知識の本文に現れるものが60%以上である。数字・単位付きの値・英数字の識別子・コード片（`…`）は、支持する原子知識に同じ文字列がある場合だけ許す。
    • 一般化の検査：正本のtitle、situation、guidance、rationale、条件、手順、例外に、repo名（6.1の表）、絶対path、repo内の相対path、portが現れない。
    • 極性：正本のpolarityが、支持する原子知識の多数のpolarityと一致する（同数ならnegativeを優先しreviewへ）。
    • 長さとschema（Zodで済み）。

  3. verifier：plannerの理由は渡さず、元の原子知識と下書き（claims付き）だけを渡してverifierOutputを返させる（旧版のlandscape-curation-verify-v2を引き継ぐ）。verdict='supported'、全claimがentailed='yes'、checksがすべてpreservedのときだけ採用する。rejectedなら指摘を添えてplannerに1回直させ、もう一度verifierに通す。それでも通らないかunknownならverifier_unknownの確認queueへ回す。
  4. settle（1つのstore.write）：
    • 正本の行：layer='canonical'、scope='global'、repo_key=NULL、spaceはmemberの多数（同数ならcoding）、body＝guidance、situation等、facetsはmemberのfacetの和集合、importanceはmemberの最大、confidenceはmin(0.95, max(member) + 0.05·log2(n))（全memberがsource_missingなら0.6を上限）、provenance_statusはmemberにresolvedかexternalがあればそれ（resolved優先）、なければsource_missing。metadata.distillに{clusterId, promptVersion, plannerCallId, verifierCallId}、metadata.usageにmemberの利用実績の合計（used、not_used）。

    • 根拠：各memberをknowledge_evidence(target_kind='atom', role='derived_from', origin='pipeline')、quoteにそのmemberが支持するclaimの文。
    • 置換：map_edges(src=正本, relation='supersedes', dst=原子知識, origin='llm', status='active')、原子知識をstatus='superseded'・retrieval='evidence_only'にする。

    • relationsのconflictはdistill_pair_judgmentsへ入れ、distill.resolveを投入する。condition_splitは両方の正本を残し、判定をresolution='split'で記録する。
    • clusterをdistilledにする。runの最後にdistill.embedを1件投入する。

6.5 S6 矛盾の検出と解消（conflict）

  • 候補：activeの正本ごとに、正本のベクトル（状況を先頭に置いた文）で5近傍のうちpairCandidate以上の組、加えて同じclaim clusterから出た正本どうしの組。両方のcontent_digestが同じ判定がdistill_pair_judgmentsにあれば省く。
  • 判定：8組ずつpairOutput。同じ状況で両立しない指示をconflict、状況や条件が違えば両立するものをcondition_split、同じ主張をduplicateとする。
  • 解き方：
    • duplicate：2つの正本の根拠の和集合で新しいclaim clusterを作って再蒸留し、settleで古い2つをsupersededにしてsupersedes（新→旧）で繋ぐ。
    • condition_split：判定が出したnotAppliesWhenを各正本へ足す下書きを作り、verifierで「根拠と矛盾しない」ことを確かめてからrevisionを上げる。通らなければverifier_unknownへ。
    • conflict：強さS = log2(1+原子知識の数) + log2(1+原記録の数) + 0.5·log2(1+used) + R（Rは、根拠の最新の時刻が相手より90日以上新しければ1、それ以外0。原記録の数はsource_missingの原子知識を数えない）を両側で計算し、差が1.0以上かつ両側のimportanceが0.8未満なら、弱い側をretractedにしてcontradicts（強→弱、origin llm、active）を張り、resolution='a_wins'|'b_wins'を記録する。それ以外はowner_pendingにしてconflictの確認queueへ回す。係数は初期値で、pilotの結果で見直す。
    • unknown：conflictの確認queueへ回す。
  • ownerの確認：a_wins／b_winsは自動と同じ処理、splitはcondition_splitの処理、keep_bothはcompatible（origin human）として記録する。未解決のconflictの両側は、MCPでwarningsに{"kind":"unresolved_conflict","handles":[…]}を付けて返す。

6.6 S7 audit：「active正本どうしは矛盾しない」の検証

  1. unresolved_conflict：両方がactiveでverdict IN ('conflict','unknown')かつresolutionがa_wins／b_wins／owner_resolvedでない組が0件。
  2. unjudged_near_pair：6.5の候補の組のうち、現在のdigestで判定のないものが0件。
  3. citation_invalid・generalization_lint：全active正本に6.4のhost照合を再実行し、違反0件。

9.3 pilotと失敗・再実行

  • pilot：較正のあと、複数要素のcluster 200個と単独200件だけをlimit付きで流し、受入率（verifierのsupported／全group）、host照合の違反率、1回あたりのtokenと時間、品質の標本（ownerが20件）を測る。基準：受入率≥0.70、host違反（修正後）≤0.05、標本の18件以上が可。満たせばprovider・promptを固定して全件へ進む。
  • 再実行：jobのdedupeKeyはcluster（member_digest）とprompt版を含むので、同じstartStageを何度投げても済んだものは投入されない。LLMの応答はdistill_llm_callsに残り、settle前に落ちても同じ入力なら再利用する。prompt版を上げると全clusterが再実行の対象になる（正本のidはJaccardで引き継ぐ）。
  • 失敗：provider側の一時障害はqueueのretry（最大3回、busyはRetry-After）、恒久的な誤りはjobをfailにしてstageのcountsに出す。LLMの出力の誤りとhost照合の違反は確認queueへ回してjobは完了にする（同じ入力を無限に繰り返さない）。

9.4 queueの使い方とretention

  • backend（api/application/runtime.ts）でdistill.registerHandlers()を呼び、server.tsの起動時だけqueue.recover()とqueue.start()を呼ぶ（maintenance commandではrunnerを動かさない）。
  • retention：backendの起動時と1時間ごとにstore.write((tx) => queue.pruneInTransaction(tx, Date.now()))を呼ぶ（終わったjobは14日、outcome_unknownは90日で消え、dedupeKeyが再利用可能になる。api/domains/queue/service/index.ts:193-200）。同じtimerで、distill_llm_callsのうちoutcome!='ok'で30日を過ぎた行を消す（okの行はauditと再利用のために残す）。
  • backendの再起動はownerが行う。distillのstageはbackendが動いている間に進み、MCPは止まらない。

  • larm.baseUrlがloopback以外のときにhttpsを必須にするか（ownerの判断）。いまはloopback以外のhttpも受け付けるので、その設定では知識の本文とtokenが平文で流れる。
  • pilotで「cluster 200個と単独200件」を1回の--limitで指定できない（limitはclusterから数える）。
  • callJsonの記録の書き込みが混雑で失敗すると、LLMの応答が保存されないままjobが失敗する（費用だけが無駄になる）。
  • 評価の、畳む前のref単位のcoverageの併記（EvalReportの契約の変更が要る）。
  • 原子知識だけの0.8倍は、knowledgeとEpisodeを混ぜた検索で、Episodeを相対的に上げる（計画どおり。評価集合はknowledgeだけ）。

15.3 ownerの作業（順に）

  1. LARMの接続とベクトル：bun run settings:larm -- --base-url <URL>、LARM_API_TOKENを付けてbun run vectors:verify-legacy。不合格ならvectors:embed。最初にDBを開いたcommandがN2のmigrationを当て、その前にdata/context-still.sqlite3.pre-migration-<時刻>.sqlite3（約640MB）を作る。
  2. backendの起動（bun run start）。以後のstageはbun run distill（API経由。DBを開かない）で行う。
  3. bun run distill -- run assess → 判定の標本の確認 → bun run distill -- calibration-export <path>・ラベル付け・calibration-import → distill run cluster → pilot（bun run distill -- run canonical --limit N）→ 全件のcanonical → conflict → audit → reviewの解決 → theme、examples。
  4. 基準線とシナリオ集合の評価は、backendを止めてbun run eval:searchで行う（基準線のdupRateは再蒸留の後に測る）。
