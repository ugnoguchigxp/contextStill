contextStill v2 実装計画：N0 骨組みとN1 取り込み・検索（2026-10-30）

方針提案の段階N0とN1を、coder subagentがこの文書だけで実装できる粒度に落とした計画である。前提となる事実は現状調査にある。方針そのもの（TS化、Rust排除、3層の知識、Eumenes方式の基盤）は決定済みで、本書では扱わない。

本書の数値のうち旧DBの件数と分布は、2026-10-30に~/Code/contextStill-db-backup-20261029/context-still-core.sqliteをmode=ro&immutable=1で開いて集計した値である。Eumenesのコードは~/Code/eumenes（読み取り専用）を参照した。確認できなかった点は「未検証」と書く。

1. 目的と非目標

目的

  • N0：mainから旧コードを外し、Eumenes形式の骨組み（単一writer、migration一覧、settingsと秘密、API token、LARMのembedding接続、queue、vectors、N1の中核スキーマ）を置く。bun run verifyが通る。
  • N1：snapshotからの取り込み（冪等、由来の修復、UTC ISO化、space='coding'）、FTS5 trigram、ベクトル（要検証状態での引き継ぎと検証command）、RRFによるhybrid検索、Eumenes向けMCP（search_knowledge、get_knowledge）、評価集合と旧版の語彙採点器との比較runner。

非目標（N1までに作らない）

  • 正本知識（canonical）、テーマ、クラスタリング、再蒸留、知識マップ（map_*表）、芋づる展開、related_knowledge・browse_theme・knowledge_feedback。N1の検索対象は原子知識（atom）とEpisodeだけである。
  • 蒸留パイプライン（finding、covering、finalize、Episode蒸留）、agent logの同期、context_compile、Web UI、LLM推論のLARM接続。LARMはembeddingだけを使う。
  • 旧DBとの差分追跡の自動化、旧daemonの停止、秘密情報の移行。新しいlibraryの導入（下記の固定版以外）。

4.3 backendの組み立て

  • config.ts：resolveConfig(env: Record<string, string | undefined>, repoRoot: string): RuntimeConfig。3節の規則をすべてここで検査する。
  • runtime.ts：openRuntime(config, deps?: { fetch?: typeof fetch; now?: () => Date }): Promise<Runtime>。openStore(config.dbPath, allMigrations)、createSettings、createLarmEmbedding、createQueue（handlerなし、start()しない）、createSearchを組み、close()でLARM接続をreleaseしstoreを閉じる。
  • app.ts：createApp(runtime: Runtime, tokens: { api: string; mcp: string }): Hono。GET /api/health（認証なし、{"ok":true,"version":"2.0.0-alpha.0"}）、/api/*はAPI tokenのbearer（定数時間比較）、registerMcp(app, …)で/mcp。app.onErrorは{error: code}とerror-status.tsの表のstatusを返し、表にないcodeは500 internal_error。
  • server.ts：唯一のBun.serve呼び出し。hostnameはconfig.host、portはconfig.port、SIGINT／SIGTERMでruntime.close()。テストからimportしない。
  • N0のAPI：GET /api/settings（文書と診断。秘密は「あるかどうか」だけ）、PUT /api/settings/larm（{baseUrl: string | null}）、GET /api/larm/status。

  1. 範囲を先に絞る。各laneのSQLは、絞り込み条件をWHEREに持ったうえで順位を付ける。条件はstatus='active'（knowledgeは加えてlayer IN (:layers)、type IN (:types)）、space IN (:spaces)、(scope='global' OR (scope='repo' AND :repoKey IS NOT NULL AND repo_key=:repoKey))。絞り込み前に件数を切ることはしない。
  2. 語の分解（tokenizeQuery）：NFKCとlowercaseのあとnew Intl.Segmenter("ja", {granularity: "word"})でisWordLikeの語を取り、隣り合う2語がともにCJK（漢字・かな・カナ）なら連結した語も足す（連結後12文字以下）。3文字以上の語はftsTerms（最大32）、ちょうど2文字の語はshortTerms（最大8）、1文字は捨てる。重複は除く。ひらがなだけの2文字語（「する」「して」など）は、上限を当てる前にshortTermsから除く（2026-10-30改訂：上限16では60問中45問で問いの後半が捨てられ、ひらがなの2文字語はknowledgeの過半に現れる雑音だった）。NFKCはquery側だけに掛けており、索引側の全角英字などは正規化していない（N1の既知の制約）。trigram tokenizerは3文字未満の語を引けないため（確認済み）、2文字の語を別laneで扱う。
  3. fts lane：knowledge_fts MATCH ?に、各語を"で囲み（中の"は""） OR で連結した式を渡す。順位はbm25(knowledge_fts, 2.0, 1.0)の昇順（episodeはbm25(episodes_fts, 2.0, 1.0, 1.0, 1.0, 1.5)）。上位100件。
  4. short lane：対象行ごとにinstr(lower(title), t) > 0なら2点、instr(lower(body), t) > 0（episodeはsituation、action、outcome、lessonのいずれか）なら1点を語ごとに足す。語ごとのヒット数（その語がtitleか本文列のどれかに含まれる）がceil(語数/2)以上の行だけを候補にし、points降順、ヒット数降順、seq昇順の上位100件（2026-10-30改訂：網羅条件がないと、共通の2文字語を多く含む長い本文で100件が飽和し、RRFでfts上位の正解を押し下げていた）。
  5. vector lane：queryVectorかembedQuery(query)（既定timeout 2秒）で問い合わせのベクトルを得る。vectorsと対象表を絞り込み条件付きでJOINし、space_key=:spaceKey AND (origin='larm' OR verification='verified') AND verification NOT IN ('mismatch','stale')で、knowledgeはさらにvectorのcontent_digestが対象行のcontent_digestと一致する行だけを（episodesにはcontent_digest列がないので、verificationだけで判定する）topKで上位100件にする。embeddingに失敗したらvector_unavailable、使える行が0件でverification='unverified'の行があればvector_unverifiedをdegradedに入れ、laneを外す。検索全体は失敗させない。
  6. RRF：score(d) = Σ_lane w_lane / (k + rank_lane(d))。k = 60、rankは1始まり、w_fts = 1.0、w_vector = 1.0、w_short = 0.5。laneに出なかった文書はそのlaneの項を0とする。knowledgeとepisodeはlaneごとに別々に順位を付け、合算後に混ぜる。同点はlaneの最良rank昇順、kind（knowledgeが先）、id昇順。上位limit件を返す。
  7. ftsTermsとshortTermsがともに空ならno_lexical_termsをdegradedに入れ、vector laneだけで返す。summaryはknowledgeが本文、episodeがlesson→outcome→situationの最初の空でないものを、空白を1つにまとめて280文字で切ったもの。N1ではexpansion_unavailableとtheme_unavailableは呼び出し側（MCP）が付ける。
