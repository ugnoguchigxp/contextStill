landscapeCuration Queue 障害調査（2026-09-09）

調査時点は2026-09-09 16:26 JST。対象はローカル常駐daemonが使用する data/context-still-core.sqliteと現行Rust executorである。本調査ではQueueの再投入、 設定変更、コード変更は行っていない。

結論

landscapeCurationはpauseも停止もしていないが、共有LLM provider poolの固定Queue順序により episodeDistillerに飢餓させられている。実行可能なcurationが7,957件あるのにrunningは0件、 最後のclaimは2026-09-08 10:05:58 JSTで、以後約30時間claimされていない。

さらに7,957件中7,082件は、成立要件を緩和した「repository identityなしのrepo-scope knowledge」である。 curationはこのknowledgeを受理してenqueueする一方、同一repository判定では比較候補を必ず0件にする。 そのままLLMへ渡すため、Queueの89.0%が比較対象のない高コスト処理になる設計不整合がある。

過去のv1処理では7,959件中5,906件（74.2%）が3回の試行を使い切ってfailedになった。 主因はprovider transport失敗と、retryableと明記されたagent session競合であるが、curationは全エラーを 一律5分間隔・最大3回で扱い、恒久failedにしている。したがって、単純な再配備だけでは同じ失敗を再生産する。

主因1: Queue間の固定順序による飢餓

provider claimはfindingCandidate → coveringEvidence → episodeDistiller → deadZoneMergeReview → landscapeCuration → mergeActivationFinalize → finalizeDistilleの順で候補を並べる。 比較関数は最初にqueue_orderを比較し、その後でのみ待機時間による effective_priorityを比較する。このためagingは同一Queue内でしか効かず、古いcurationが episodeDistillerを追い越すことはない。この挙動を正として固定するunit testも存在する。

調査時点でepisodeDistillerは1,370件、landscapeCurationは7,957件がrunnableだった。 直近3時間のprovider leaseはepisodeDistillerが2,323回、landscapeCurationは0回である。 provider poolは2 targetを持つがmaxConcurrent=1で、実効枠は1つだけである。 episodeDistillerが継続的に供給される限り、curationの開始時刻には上限がなく、永久にclaimされない可能性がある。

主因2: identity任意化と候補選定の不整合

v2 pendingの分類 件数 候補選定
repo scope・identityなし 7,082 同一repository候補は必ず0件

same_repositoryはrepo scopeの場合、repoKey、repoPath、projectRefの少なくとも1項目が双方で一致することを要求する。 3項目が全て空ならfalseになる。これは誤ったmergeを防ぐ安全側の判定として妥当だが、 enqueue_allはidentityの有無にかかわらず全active knowledgeをenqueueするため、producerとconsumerの契約が一致していない。

v1でもidentityなしrepo knowledgeは7,082件あり、5,200件failed、1,210件needs_evidence、 654件keep_separate、18件observeだった。候補0件のsubjectにLLMを使ってもmerge/deprecateには到達できず、 provider枠と試行回数を消費するだけである。

主因3: retryable障害を恒久失敗へ変換

現行persistはエラー種別を区別せず、失敗ごとにattemptを1増やし、5分後に再試行し、3回目でfailedにする。 provider/session/embeddingの一時障害と、schema validationの恒久障害が同じ状態遷移である。 なお現在はactive knowledge 7,957件すべてにembeddingが存在するため、現時点の停止原因はembedding欠落ではない。

観測性と負荷の問題

  • 失敗時にdistillation_queue_eventsへfailed/retried eventを書かず、行のlast_errorだけを更新する。
  • skippedであるneeds_evidenceやblockedもevent上はcompletedとして記録される。event集計だけでは成功率を判定できない。
  • executor起動ごとに全active knowledgeを走査してcontent revisionを計算する。backlogが大きくても毎回O(N)のenqueue確認を行う。
  • 1 jobはplannerに加え、merge/deprecate時はverifierとembeddingも実行するため、単一provider枠で7,957件を消化する設計ではない。

修正優先順位

  1. Queue間の公平性を導入する。queue_orderより先にagingを効かせる、連続claim上限を設ける、 またはcuration専用provider枠を設け、古いrunnable jobに有限のclaim待ち時間を保証する。
  2. identityなしrepo knowledgeの契約を明示する。安全性を維持するならenqueue前またはLLM呼び出し前に 「比較不能」としてローカル完了し、identityが後から付与されたrevisionでのみ再評価する。 identityなし同士を同一repo扱いする変更は誤mergeの危険があるため行わない。
  3. provider/session/embedding障害をretryableとしてattempt budget外のbackoffへ分離し、schema違反などの恒久障害だけを bounded attemptにする。HTTP本文・status・retry-afterを構造化して保持する。
  4. statusと同じ意味のclaimed/completed/skipped/retried/failed eventを必ず記録し、Queue別の最終claim時刻、 runnable最古時刻、starvation時間、provider利用率を監視項目にする。
  5. 上記修正後、まずv2 pendingを処理する。v1 failed 5,906件はv2に同じsubjectがあるため一括再配備せず、 v2で未評価となるsubjectだけを差分再投入する。

検証

現行のcandidate選定test 2件と、固定Queue順序を確認するprovider claim test 1件を実行し、全て成功した。 したがって今回の停止はdaemon crashや既存testの偶発的失敗ではなく、現行仕様どおりのscheduler挙動が 実データ量で飢餓を起こしているものと判断する。
