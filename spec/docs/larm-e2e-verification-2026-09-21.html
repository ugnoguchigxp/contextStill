過去のOS code 65

対象期間は2026-09-19 21:38 JSTから2026-09-20 21:58 JST。provider leaseは provider_unavailable_retry=1332、worker_failed=366、 worker_finished=6だった。保存済みfinding errorには connect=true、timeout=false、Os code 65、 HostUnreachable、No route to hostが残っている。

  • pmset -g logには対象期間のsystem sleep、wake、darkwake遷移がなかった。
  • airportdの記録では対象networkへのassociationは2026-09-14から継続し、対象期間中もalready associatedと記録されていた。
  • airportdのusage snapshotはFaultReasonArpFailure=0、DHCP failure 0を示すが、peer固有のARP履歴ではない。
  • configdにはen0のIPv6 publishが多数あるが、IPv4 route消失またはen0 link-downを示す記録は確認できなかった。
  • macOSは過去のARP/neighbor entryを永続保存しないため、当時192.168.0.130のARP解決が失敗したことを直接証明できない。

192.168.0.130はContextStillホストと同一/24にある。listener未bindなら通常はTCP connection refusedまたはtimeoutになり、code 65はIP/TCP接続前のhost到達性を示す。このため、LARMホストのsleep、電源断、Wi-Fi切断、IP競合、またはpeer固有のARP応答欠落が有力である。ただし、当時のpacket/neighbor証跡がないため原因は未確定とする。

次回発生時に必要な採取

  1. 最初のcode 65と同時に、UTC/JST時刻、route -n get 192.168.0.130、arp -n 192.168.0.130、ifconfig en0、scutil --nwiを採取する。
  2. 同時にdefault gatewayと同一subnet内の別hostへTCP connect probeを行い、local interface全体の障害とLARM peer固有障害を分離する。pingだけでは判定しない。
  3. secretを含むHTTP payloadを採取せず、ARP request/replyとTCP SYN/SYN-ACKの有無だけを短時間採取する。
  4. Queue errorにprobe時刻、interface、route interface、neighbor stateを関連付ける。routeやfirewallは変更しない。
