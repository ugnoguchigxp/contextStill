Queue大量失敗インシデント調査（2026-09-20）

2026-09-20 21:38 JST時点で、resident daemonは稼働しているが、LLMを使うQueueは正常処理できていない。 直近24時間にcoveringEvidenceで646件がfailed、episodeDistillerで1,288件がpaused、 findingCandidateで62件がpausedになった。同期間のQueue eventにcompletedは0件だった。

結論

  1. 全LLM routeが同じlarm-qwen-background poolを参照し、その3 targetがすべて利用不能である。 LARM Qwenは接続失敗、Museはhost fingerprint不一致または初期化timeout、Codex SparkはCLI catalogに存在しない。
  2. Queue laneはすべてunpausedで、利用不能targetに対する有効な停止・隔離が働かず、claim、retry、terminal failureを継続している。 6秒間の再観測でもdistillation_queue_eventsは425,419件から425,420件へ増加した。
  3. 別件として、稼働中daemonにはcovering成功後のfinalize enqueueでparameter順序を誤る既知不具合が残っている。 logにはfinalize_distille_queue.protocol_versionへTEXTを保存しようとした失敗が123件ある。 repository上ではcommit cd130e9で修正済みだが、daemon processは修正前の実行imageを保持している。

実装不具合と稼働imageの不一致

修正前のcovering persistenceは、INSERT列順がpriority, protocol_version, requested_revision_id, provider_policyなのに、 bind値をpriority, provider_policy, protocol_version, requested_revision_idの順で渡していた。 STRICT tableのためprotocol_versionへのTEXT bindで拒否される。commit cd130e9はbind順を修正している。 現在のdaemon PID 99918は2026-09-12 23:52 JSTから継続稼働しており、修正commitは2026-09-13 08:59 JSTである。 binary file自体が後から更新されても、稼働processのmemory imageは置換されないため、再起動まで旧不具合が残る。

LARM調査・改修依頼

findingの保存済みerror chainでは、LARM接続失敗の最終原因は OS code 65 / HostUnreachable / No route to hostだった。HTTP response受信前のTCP接続失敗であり、 credential拒否やmodel未登録とは異なる。同一hostから保存済みBearer credentialを使った追加probeでは、 /health、/v1/models、/v1/chat/completionsがすべてHTTP 200になり、 qwen-agent-workerも確認できた。Chat Completionsの接続時間は0.039秒、総時間は11.696秒だった。

このため、恒常的なLARM設定不備ではなく、network経路、listener停止・再起動、sleep/wake、または長寿命daemonに限定した 間欠障害としてLARM側logとの時刻相関が必要である。調査で終わらず、原因修正、test追加、実環境検証まで依頼するpromptは LARM調査・改修依頼に保存した。

Muse利用制限中の呼び出し抑止

provider quotaはruntime.provider-quotaへtarget IDとretryAtを保存し、 provider lease claim前に未来のretryAtを持つtargetを候補から除外する。今回、Museが返す rate_limit_errorかつretryable=falseもquota exhaustedとして認識し、 数値・millisecond・ISO timestampのreset表現と、秒数のretry_afterを正規化するようにした。 reset情報がない場合は5分、過去時刻の場合も最低60秒は選択しない。解除時刻を過ぎると通常のleast-recently-used選択へ戻る。

現在のMuseはquota exhaustedではない。認証付き/v1/agents/models?runtime=muse probeはHTTP 503を返し、 provider_host_exited、runtime.initialize timed out、retryable=false、 retry_after=nullだった。このため今回追加した「解除時刻まで抑止」の条件には該当せず、Muse bridge自体の復旧が別途必要である。

Codex Spark設定の撤去

Codex Sparkは利用制限targetではなく廃止targetとして扱った。live settingsの larm-qwen-background poolからcodex-sparkを削除し、pool concurrencyを3から2へ縮小した。 runtime.provider-quota/codex-sparkも削除し、live settings document内の codex-sparkおよびgpt-5.3-codex-spark参照が0件であることを確認した。

影響

  • LLM依存の新規distillationは、少なくとも2026-09-17 23:06 JST以降、正常完了していない。
  • episodeとcoveringのbacklog合計は約8,252件で、さらにpaused・failedが蓄積している。
  • 失敗中もprovider callとDB event書き込みを継続するため、無駄な負荷、ログ増加、失敗状態の増加が続く。
  • coveringがknowledge-readyを返しても、旧daemonではfinalize enqueueが失敗し、下流へ進めない。

推奨する復旧順

  1. まずLLM依存laneを一時停止し、失敗の増加を止める。
  2. 3 targetのうち、実probeで成功するtargetだけをpoolへ戻す。LARM認証、Muse fingerprint、Codex model catalogを個別に検証する。
  3. current sourceからdaemonをbuildし直して再起動し、cd130e9の修正を稼働imageへ反映する。
  4. 各Queueで1件ずつcanaryを流し、claimからcompleted、coveringからfinalize enqueueまでを確認する。
  5. canary成功後にfailed・paused jobを段階的に再投入する。一括再投入は避ける。
  6. 全target利用不能時のpool circuit breakerと、時間窓ごとのfailure-rate alertを追加する。

調査方法

data/context-still-core.sqliteをread-onlyで参照し、7 Queue table、 distillation_queue_events、llm_provider_leases、非secret設定を集計した。 あわせてLaunchAgent状態、PID、logs/context-stilld.log、local providerのhealth endpoint、 Git履歴と稼働開始時刻を確認した。DB更新、Queue操作、daemon再起動は行っていない。
