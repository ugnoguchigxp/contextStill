LARM foreground preemptionを失敗にしないQueue再試行設計

結論

実装済み。共通HTTP分類、Finding・Episode・Curationのattempt非消費再試行、構造化info log、Queue UI表示、連続preemption・cancel fence・再試行成功の回帰testを追加した。

LARMへの推論要求がHTTP 409かつJSON本文の error.codeが厳密にforeground_preemptedである場合、通常のProvider障害や 推論失敗とは別のInferencePreemptedとして分類する。対象jobは failedへ遷移させず、既存schemaのpendingと next_run_atを使って再開待ちへ戻す。通常のattempt_count、 retry budget、失敗回数は変更しない。

LARM targetへの接続確立前に名前解決、connection refused、connect timeoutなどで到達不能になった場合も、 同じattempt非消費の再開待ちへ戻す。この場合は last_outcome_kind='provider_unreachable'、 event='contextstill_provider_unreachable'としてpreemptionとは理由を区別する。

待機をworker内のsleepで実装してはならない。preemptionを永続化してProvider leaseを解放し、 resident schedulerに再claimさせる。これにより、待機中のユーザーpause、job削除、lane停止、 resident shutdownを既存の制御経路で処理できる。

対象範囲

現在のdirect LARM routeで実行されるfindingCandidate、 episodeDistiller、landscapeCurationを実装対象とする。HTTP応答の分類器は Queue共通部品にし、将来LARM routeが増えた場合も同じ契約を利用できるようにする。

現行のdirect LARM Chat Completions要求はstream: falseである。したがって初期実装は 非streaming JSON errorを必須範囲とする。streamingを有効化する将来変更では、明示的な foreground_preemptedイベント、または切断直前に保持した同等のpreemption情報がある場合だけ 同じ分類にする。理由不明のEOF、timeout、connection resetはpreemptionへ昇格させない。

到達不能分類はLARM targetのtransport errorでis_connect()が真の場合に限定する。 HTTP応答を受信した認証エラー、入力不正、429、5xx、応答本文の読み取り失敗、推論中の一般timeoutは 既存のエラー分類を維持する。

現状との差分

  • FindingとEpisodeのProvider unavailable経路はattempt_countを増やし、連続時には exhaustedとしてpauseする。foreground preemptionをこの経路へ流すと要件違反になる。
  • Curationの一部Provider unavailable経路はattemptを消費しないが、preemption専用の判定、表示、 1〜30秒のbackoff、構造化logを持たない。
  • HTTP失敗は現在、多くの呼び出し箇所で文字列化され、その後にstatus文字列を検索して分類される。 error.codeを主条件にするには、本文を文字列化する前のHTTP境界で型付き分類する必要がある。
  • Episodeはsegment失敗をprogressへ保存してから外側の失敗処理へ進む。preemptionでは現在のsegmentを failedとして記録せず、未完了のまま残す専用伝播が必要である。

HTTP応答の分類contract

共通分類器はstatus、headers、bounded body、対象targetがLARM direct routeかを受け取り、 次の条件をすべて満たしたときだけInferencePreemptedを返す。

  1. 対象target IDがlarm-agent-connection:で始まる。
  2. HTTP statusが409である。
  3. 本文がJSONとしてparseできる。
  4. /error/codeが文字列foreground_preemptedと完全一致する。

X-LARM-Preemption-Reason: higher-priority-foreground-taskと Retry-Afterは補助情報であり、分類条件にはしない。headerがなくても上記4条件を満たせば preemptionである。反対にheaderだけが一致する応答、409だけの応答、別のerror code、parse不能な本文は 既存のエラー処理を維持する。message文言は診断用に保持できるが判定には使わない。

型は少なくともreason、retryAfterMs、sanitized messageを保持する。 reasonは外部文言をそのまま採用せず、内部の固定値 higher_priority_foreground_taskへ正規化する。

状態遷移と永続化

running
  |  409 + error.code=foreground_preempted
  v
pending + next_run_at=future
  |  dueかつlane/jobが有効
  v
running  -- success --> completed/skipped

pending(waiting)
  +-- user pause --------> paused + next_run_at=null
  +-- job delete --------> removed
  +-- resident shutdown -> DB上のwaitingを保持し、停止中は再claimしない

preemption永続化では次をatomicに行う。

  • status='pending'、next_run_atを計算済み時刻へ設定する。
  • attempt_countと通常retry budgetを変更しない。
  • completed_at=null、lockとheartbeatを解除する。
  • last_error=nullとし、障害欄へpreemption messageを入れない。
  • last_outcome_kind='inference_preempted'とする。
  • FindingとEpisodeはmetadataへreason、preemptionCount、 retryAfterMs、preemptedAt、必要ならsanitized messageを保存する。 metadata列を持たないCurationは同じ情報をqueue event ledgerへ保存する。
  • Provider leaseをforeground_preempted理由で解放する。
  • 既存event schemaとの互換のためqueue event typeはretriedを使い、metadataの eventをcontextstill_inference_preemptedとする。

更新条件には既存のProvider lease ownership fenceを必須とする。preemption応答の到着前にjobがpause、 delete、または別claimへ移った場合、古いworkerは状態を書き戻さずSupersededとして終了する。

Retry-After、指数backoff、jitter

通常のattempt_countとは別に、metadataの連続 preemptionCountをbackoff指数として使う。成功時はこの連続回数を0へ戻すか履歴欄へ退避する。 待機時間は次の規則で決める。

  1. Retry-Afterが正のdelta-secondsなら、それを再試行可能な最早時刻として使う。 欠落、不正、0以下なら1,000msを最小値にする。
  2. 指数上限をmin(30,000ms, 1,000ms * 2^preemptionCount)で求める。
  3. 待機時間を、最小値からmax(最小値, 指数上限)までの範囲でランダムに選ぶ。 これにより初回はheaderなしなら1秒、連続時は指数的に広がり、同時再開をjitterで分散できる。
  4. 最小値と上限は最終的に30,000msへclampする。30秒を超えるRetry-Afterも本機能の最大待機契約を優先して 30秒とする。

next_run_atはミリ秒を保持できるUTC timestampとして保存し、worker threadを占有しない。 テストでは乱数源とclockを注入し、境界値を決定的に検証する。

Queue別の変更点

LARM foreground preemptionを扱うQueueごとの伝播方法と重複防止策
Queue 伝播 重複防止
findingCandidate FindingWorkerResult::Preemptedを追加し、ProviderUnavailableより先に永続化する。 候補書き込み前の推論だけを再実行し、既存のtransactionとlease fenceを維持する。
episodeDistiller segment推論からentryまで型付きpreemptionを伝播し、segment error、failed segment count、通常attemptを 増やさない。 保存済みsegment resultとepisodeのidempotent source keyを維持し、未完了segmentだけを次回処理する。
landscapeCuration plannerとverifierの両HTTP境界からCurationExecutionError::Preemptedを返し、文字列ベースの ProviderUnavailable分類より先に処理する。 mutation phaseより前の推論だけを再実行する。既存のsnapshot検証とtransactional mutationを維持する。

一つのjobで複数のLLM呼び出しがある場合もtask IDは維持する。Queueの再claimごとに新しいProvider lease IDが 発行されるため、これを実行attemptのfenceとして使える。純粋な推論要求のためだけに永続的な別taskを作らない。 将来、推論要求自体が外部副作用を持つ場合はLLM呼び出し単位のrequest attempt IDを追加する。

ログ、API、UI

状態更新のcommit後に、error/warningではなくinfoレベルのJSON logを1件出す。最低限のfieldは次のとおり。 

{
  "level": "info",
  "event": "contextstill_inference_preempted",
  "reason": "higher_priority_foreground_task",
  "taskId": "queue-job-id",
  "attempt": 1,
  "retryAfterMs": 1000
}

attemptは通常のattempt_countではなく、今回の連続preemption内の1始まりの回数とする。 Provider token、request body、入力context、LARM credentialはlogへ含めない。

Queue APIは既存statusをpendingのまま返し、 lastOutcomeKind='inference_preempted'とnextRunAtで理由と再開予定を表現する。 Admin UIはこの組合せをfailure色やerror文言にせず、次を表示する。

優先タスクの実行により一時停止しました。リソース解放後に自動再開します。

到達不能時はlastOutcomeKind='provider_unreachable'を参照し、次を表示する。

処理プロバイダーに接続できないため一時停止しました。接続回復後に自動再開します。

UI上のstatus labelは再開待ちまたは一時停止・自動再開とし、通常の手動 pausedとは区別する。attempt列は増えないことが視覚上も確認できるようにする。

受入テスト

  1. 共通分類器へ409とerror.code=foreground_preemptedを渡すとpreemptionになり、messageや補助headerが なくても判定できる。
  2. 409でも別code、code欠落、JSON不正、headerだけ一致、非LARM targetでは既存エラー分類を維持する。
  3. 各対象Queueでpreemption後にstatusがpending、completed_atがnull、 last_errorがnull、last_outcome_kindがinference_preemptedになる。
  4. preemption前後で通常のattempt_countとretry budgetが不変である。
  5. headerありではその時刻より前にclaimされず、headerなしの初回は1秒、連続時はjitter付き指数backoff、 全ケースで30秒以下になる。
  6. 複数回連続preemptionしてもexhaustedやfailedへ遷移しない。
  7. LARMへのconnect errorではprovider_unreachableとしてattemptを消費せず再開待ちになり、 非LARM targetやHTTP応答を伴うエラーは既存処理を維持する。
  8. 待機中のjob pause、job削除、lane pause、shutdownでは再claimしない。応答到着とpause/deleteが競合した場合は ownership fenceにより古いworkerの書き戻しを破棄する。
  9. Episodeではpreemptされたsegmentをfailedとして記録せず、完了済みsegmentと作成済みepisodeを重複させない。
  10. preemptionを1回以上経た後に200応答を返すfixtureで、同じtask IDのjobが通常どおり完了する。
  11. queue eventとinfo logに指定fieldが入り、warning/error countとProvider failure集計が増えない。
  12. Admin UIが障害色やraw errorではなく、自動再開する一時停止文言を表示する。
  13. streamingの理由不明切断をpreemptionにしない分類テストを追加する。

推奨実装順

  1. bounded JSON bodyとheadersからpreemptionを厳密判定する共通型・分類器、Retry-After parser、決定的backoff関数を 追加する。
  2. Findingへ専用worker resultとattempt非消費の永続化を追加し、最小のend-to-end fixtureを通す。
  3. Episodeのerror伝播を型付きにし、segment progressを汚さないことと再開時のidempotencyを検証する。
  4. Curationのplanner/verifierへ同じ分類を適用する。
  5. 共通info log、queue event metadata、API/UI表示を追加する。
  6. 対象Queueの回帰test、Rust全体test、Web component testを実行し、fake LARMによる preempt-preempt-successとpreempt-cancelのcanaryを行う。

今回変更しないもの

  • 409全体をretryableにしない。
  • 認証、入力不正、通常のallocation inactive、quota、503 busyの既存分類を変更しない。
  • 新しいQueue status enumやDB migrationを追加しない。
  • preemptionを理由に別Providerへ暗黙fallbackしない。
  • worker内sleep、無制限retry、通常retry budgetの水増しを行わない。
