landscapeCuration Queue 改善設計

本設計は、2026-09-09の障害調査で確認したQueue飢餓、repository identity任意化との契約不整合、retryable障害の恒久failed化、 全件scanと観測性不足を解消するための実装案である。単純な再配備や固定優先順位の入れ替えは採用しない。

実装状況

2026-09-09にRust executorへ実装し、常駐daemonへ配備した。provider公平化、Queue別concurrency、 identityなしpreflight、候補なしLLM bypass、typed retry、event整合、差分reconciliationを有効化している。 live v2 backlogではidentityなし7,082件をattempt 0のままskippedへ移行し、claim前の対象を875件まで縮小した。残りはclaim後のcandidate preflightでさらに絞り込まれる。

目標

  • 競合Queueにbacklogがあっても、curationが有限時間内にclaimされる。
  • 比較不能または候補0件のknowledgeにはLLMを呼ばない。
  • provider、session capacity、Embeddingの一時障害をsemantic attemptとして消費しない。
  • 同じsubject revisionを二重処理せず、identity付与や内容変更時だけ再評価できる。
  • status、event、provider leaseの集計が一致し、停止理由を運用画面から判定できる。

非目標

  • identityなしknowledge同士を同じrepositoryと推定してmergeすること。
  • 過去のv1 failed 5,906件を無条件にpendingへ戻すこと。
  • curationの判断promptやauto-mutation policyを同時に全面改訂すること。

推奨構成

  1. LLMの前に決定論的なlocal preflightを置き、比較不能・候補なしをterminalにする。
  2. provider claimを固定Queue順序からburst制限付きのweighted fairnessへ変更し、Queueごとの同時実行上限を設ける。
  3. worker結果を成功、非対象、retryable infrastructure、repairable model output、permanent failureに分類する。
  4. knowledge変更時の差分enqueueを正規経路にし、全件scanは低頻度のreconciliationへ降格する。
  5. 既存v2 pendingをlocal preflightで縮小してから、LLM対象だけをcanary処理する。

1. LLM前のlocal preflight

pending curationを小さなbatchで検査する。repository identity欠落はclaim前に一括判定し、 stale subjectと候補なしはclaim後のsnapshot段階で判定してprovider leaseを即時解放する。 いずれもLLMを使用しない。

local preflightの判定と永続化結果
条件 status decision / outcome 再評価条件
repo scopeかつidentity 3項目が全て空 skipped observe / identity_unavailable identityまたはscope変更で新revisionをenqueue
安全な同一repository候補が0件 skipped observe / no_candidate 新knowledge側の評価、またはcandidate index epoch更新
subjectがinactiveまたはrevision不一致 skipped observe / stale_subject 最新revisionのjobへ一本化
候補が1件以上 pendingのまま llm_required provider schedulerへ渡す

identityなしをglobal扱いしたり、空identity同士を同一repository扱いしたりしてはならない。 identityがないknowledgeも検索用ナレッジとしては成立するが、安全な重複統合の比較domainは確定できないためである。 現在のv2 pendingでは、この分岐だけで最低7,082件、全体の89.0%をLLM対象から除外できる。

terminal化時はattempt_countを増やさず、review ledgerへoutcomeとsubject revision、candidate index epochを記録し、skipped eventを1件だけ追加する。これにより「処理失敗」と「現時点では比較対象外」を分離する。

2. 飢餓しないprovider scheduler

現在のqueue_order最優先比較に、pool単位の連続claim上限を加える。 初期burst上限はfindingCandidate=4、episodeDistiller=3、 landscapeCuration=1とする。上限に達したQueue以外にrunnable jobがある場合は別Queueを選び、 他Queueが空なら現在のQueueを継続する。 これによりepisodeとcurationだけがrunnableなら、最大3回のepisode claim後にcurationが1回claimされる。

fairness stateは専用の二重ledgerを作らず、既存のSQLite provider lease履歴から直近のQueueと連続claim数を読む。provider lease作成と同じclaim transaction内で判定するため、daemon再起動や複数executorでも順序を維持する。既存のjob priorityとagingは、選ばれたQueue内のjob選択にだけ使用する。

provider poolの推奨初期設定
設定 推奨値 目的
pool maxConcurrent 2 現在登録済みの2 targetを利用する
landscapeCuration maxConcurrent 1 長いplanner/verifier処理がpoolを占有しない
curation最大連続claim 1 foreground Queueの遅延を制限する
starvation alert runnable最古が5分超 claim保証違反を検知する

targetが1台しか利用できない環境でもburst制限付きfairnessを適用する。target数を増やすだけでは、固定Queue順序のまま 全targetがepisodeに割り当てられる可能性があるため、公平性の代替にはならない。

3. failureとretryの契約

curation worker結果の分類と状態遷移
分類 例 遷移 attempt_count
NotApplicable identityなし、候補なし、stale subject skipped 増やさない
ProviderUnavailable transport、408、425、429、5xx、retryable 409 pending + backoff 増やさない
EmbeddingUnavailable daemon接続失敗、408、429、5xx pending + backoff 増やさない
RepairableModelOutput JSON/schema bounds、verification不完全 pending、最大3回 増やす
PermanentFailure DB invariant、必須snapshot破損 failed 増やす

retryable応答ではRetry-Afterまたはresponse内のretry_after_secondsを優先し、 値がなければ60、120、300、600、1,200、最大3,600秒の指数backoffを使う。jobのsemantic attemptとは別に、retried event件数をinfrastructure retry履歴として保持し、semantic attempt_countは増やさない。provider targetには既存のcooldownを適用するため、 復旧後に手動requeueなしで再開できる。

providerから得たHTTP statusとresponse bodyを失わず、worker内部のenumへ一元分類する。 永続化時にはerror code、retry-after、target idを構造化event metadataへ残す。 Embedding停止は既存の共通retry判定を利用し、curationだけ別契約にならないようにする。

4. enqueueとrevisionの改善

executor tickごとのreconciliationは、Queue未登録、またはそのsubjectの最新Queue作成時刻以後に 更新されたknowledgeだけを対象にする。同じcontent revisionは既存の一意性判定で二重登録しない。 これにより既存のknowledge write pathを壊さず、変更のない全active knowledgeの反復scanを避ける。

content revisionにはtitle、body、type、polarity、scope、repository identity、appliesTo、正規化したsourceGroupsだけを含める。 metadata全体、usage時刻、Queue実行履歴は含めない。curation自身が書いた運用metadataによる再enqueue loopを防ぎながら、 mergeでbodyやsourceGroupsが変わった場合は再評価できる。

uniquenessは(subject_knowledge_id, content_revision, candidate_index_epoch, detector_version)を論理keyとする。 同じrevisionのactive jobは1件だけとし、claim後にrevision不一致が判明したjobは stale_subjectとしてskippedにする。

5. 観測性

すべての状態遷移で、statusと同じ意味のeventを同じtransactionに書く。

  • claimed: pool、target、Queue、lease時刻
  • skipped: identity_unavailable、no_candidate、stale_subject
  • retried: error code、retry-after、attemptを消費したか
  • completed: decision、disposition、mutation有無
  • failed: permanent error codeとattempt_count

dashboardではstatus件数に加え、runnable最古時刻、last claim時刻、p50/p95待機時間、Queue別provider占有時間、 preflight skip率、LLM対象件数、retryable error率を表示する。event件数とQueue行の遷移が一致しない場合はhealth warningにする。

6. 既存backlogの移行

  1. curationだけをpauseし、他Queueとknowledge登録は継続する。
  2. schemaと新workerをdeployし、read-only dry-runで分類件数を出す。
  3. v2 pendingのうちidentityなし7,082件をlocal preflightでskippedにし、ledgerとeventを記録する。
  4. 残る最大875件にcandidate preflightを行い、候補0件を追加でskippedにする。
  5. LLM対象から50件をrecord-only canaryとして処理し、provider retry、candidate精度、event整合性を確認する。
  6. 問題がなければauto-mutation policyを現行上限のまま戻し、Queueをresumeする。
  7. v1 failed 5,906件は履歴として保持し、対応するv2 jobがないactive subjectだけを差分抽出して再投入する。

rollbackは新規claimをpauseし、schedulerを旧固定順序へfeature flagで戻す。local preflightでskippedにしたjobは削除せず、 reasonとrevisionを保持するため、必要なら対象reasonだけをpendingへ戻せる。auto-mutation canary中は既存rollback snapshotを維持する。

受け入れ条件

  • episode backlog継続中でも、runnable curationの最初のclaimが5分以内に発生する。
  • 単一targetでepisodeとcurationが競合するtestにおいて、3回を超えてepisodeだけが連続claimされない。
  • identityなしrepo knowledge 7,082件に対するLLM requestが0件である。
  • 候補0件のjobがLLM requestを送らず、短時間でprovider leaseを解放し、skipped eventとledgerを1件ずつ残す。
  • retryable 409、429、503、transport、Embedding停止でattempt_countが増えない。
  • schema不正は最大3回で止まり、pausedまたはfailed理由を構造化して残す。
  • 同一subject revisionのactive jobが複数存在しない。
  • 30分窓のQueue status遷移とevent件数が一致する。
  • 50件canaryで意図しないknowledge mutationが0件、rollback不能が0件である。

採用判断

推奨は「local preflight → typed retry → burst制限付きscheduler → 差分enqueue」の順に実装する案である。 最初の2項目だけで現在のbacklogと再失敗を大幅に抑えられ、その後schedulerを切り替えて安全にLLM対象を流せる。 優先順位配列の並べ替えだけでは別Queueを飢餓させ、provider target追加だけでは全targetを上位Queueが占有できるため、 恒久対策としては不十分である。
