期待する動作と固定しない値

ContextStillは単一connectionIdに対応するAgent Connectionとclaim descriptorを共有する。実効request capacityは、LARMの広告値とContextStill設定上限の小さい方。既定設定は1。広告が3かつ設定が3なら同一baseURL・model・credentialへ3件を並行送信し、4件目は未claimのpendingに残す。広告が1なら1件とする。物理slot、id_slot、KV、continuous batching、推論daemonの起動数はLARM所有である。

ContextStill内部の設計方針

以下の型名は新設する内部型の案であり、LARMのJSON field名ではない。既存の命名に合わせた変更は許容するが、責務は維持する。

  • SharedLarmConnection：registryに常駐するArc。短時間のMutexで状態・generation・active permit数・drain状態だけを保護する。DBパスの異なるテスト／residentが同じ設定IDで衝突しないようregistry keyはruntime scopeとconnectionIdの組にする。
  • ConnectionSnapshot：検証済みdescriptor、契約revision、実効capacity、window情報を持つ不変snapshot。credentialはZeroizing等で保護したメモリ内だけに保持し、Debug・ログ・DBへ出さない。
  • LarmRequestPermit：generationとrequest相関IDを持つRAII guard。成功・失敗・panicでローカル所有権を一度だけ返す。上流終了が不明なら、その枠は状態照合待ちとして別途占有を残す。
  • PreparedLarmRequest：実際に送る最終body、token見積り方式・必要量、出力予約、選択tier、入力revisionを持つ。bodyはメモリ内だけ。計測後にbodyを書き換えた場合は必ず再計測する。
  • AdmissionOutcome：Ready、CapacityWait、ContextUnsupported、Draining、ContractUnavailable、ReconcileRequiredを区別する内部enum。待機はsemantic attemptではない。

lockを取ってCreating/Renewing等へ遷移し、その所有者だけがlockを外してHTTPを実行する。完了後はgenerationを比較して結果を適用し、待機者へ通知する。HTTP待機中やSQLite writer待ち中にregistry／manager lockを保持しない。全connectionを1つのHTTP待機で止めない。

設定変更・bootEpoch/configRevision変更・renew失敗は新規admissionを停止し、古いgenerationをdrainする。旧requestが有効な間に別managerを作らない。既存credentialを更新してよい条件がC4で確認できない場合、active=0までrenewを待ち、新規requestを止める。

P4〜P5：共有接続とlease

P4の初回接続は既存Service Activityのfail-closed gateを使う。確立後はC2の公開admissionに従い、自身のactive workloadを理由にreleaseしない。advisory healthで空きと判定しても、実request受付時のretryable overloadを最終判断として扱う。実効capacity低下時は稼働中requestを勝手に切らず、新規permitを停止する。

permit取得はactive数の比較と増分を同じcritical sectionで行う。connectionId・generation・job correlationを結び、credentialはcloneする場合も保護型を維持する。create・ready poll・claim・renew・releaseのそれぞれでsingle-flightを試験する。registry lock下でHTTPを送らないことを、無関係なconnectionが進める試験で確認する。

P5ではProviderPoolClaimConfigのtarget一覧とtargetごとのrequest容量を分ける。内部の明示的capacity policyを導入し、未指定static targetは常に1にする。文字列prefixやpool.max_concurrentだけでdynamic多重leaseを許可しない。検証済みnegotiationからのみdynamic policyを構築する。

claim transaction内でpool active数とtarget active数を確認してleaseを挿入する。pool上限とtarget上限の双方を満たすこと。target使用数は別Poolからのactive leaseも数える。既存fencing、stale heartbeat、cooldown、quota、Landscape上限1を維持する。SQL変更が必要なら既存schema・migration登録を追跡し、場当たり的な起動時DDLは追加しない。

permitを先に取得し、その後SQLite writerでjob/leaseをclaimする。jobが取れない／writerが失敗したら、まだHTTP未送信のpermitを即返す。permit待ちの間にQueue jobをrunningへしない。送信済みのtimeoutは未送信permitの返却と同じ扱いにしない。

P6：context照合とtier選択

  1. Finding・Episode・Landscapeについて、最終request bodyの組立箇所を特定する。target_chat.rsだけに上限チェックを足して、上流の固定128K前提や証拠の切り捨てが残らないよう、定数・token budget・max_tokensの全呼び出し経路を検索し一覧にする。
  2. prompt計測と実送信で同じPreparedLarmRequestを使用する。system、messages、tool schema、retrievalを含める。モデル依存の正確なtokenizerを使用できる場合はそのrevisionも記録する。使えない場合は安全側の見積りをfixtureで検証し、推定であることを記録する。安全性を説明できない見積りで上限近くを送らない。
  3. prompt + requested output + advertised safety marginがwindow以下、かつ広告されたoutput条件を満たす候補を選ぶ。outputReserveTokensの意味はC3で確定し、requested outputと二重加算しない。
  4. 最小の適合tierを優先する。大きいtierにしか入らないjobが待っている場合、小jobがそのtierを取り続けないようbounded agingを設ける。既存aging設定を再利用できるか確認し、初期値・時間の起点・公平性を試験で固定する。
  5. request作成前にtierを決める必要があるので、read-onlyにjob候補を取得してbodyを準備し、claim transactionでjobがまだpendingかつ入力revisionが同一か再検証する。変更があれば準備結果を捨てる。複数workerが同じjobを準備してもclaimは1件だけにする。準備段階で外部LLM呼び出しを行わない。
  6. 証拠取得等で実行中にbodyが増える経路は、送信直前にも再照合する。不適合なら送信せず、現在のleaseとpermitを適切に返して型付き待機へ移す。途中の成果を重複適用しないため既存永続化境界を確認する。

候補tierなし、広告なし、capacity待ちはsemantic failureにしない。必要token数・上限・profile・推定方式・retry条件だけをeventへ残す。本文・プロンプト・credentialは残さない。暗黙のtruncateや新しいcompactionを追加せず、既存の明示policyを使う場合は適用後に再計測する。

64K・64K・256Kの要求例は一般化した境界試験に用いてよいが、本番field・設定へ固定しない。実fixtureが64K／128Kならその組合せを契約試験に使う。広告集合が変わっても選択ロジックが成立することを確認する。

正常応答・保存成功 fencing確認後にjobを完了しlease解放。request終了条件を満たしたpermitだけを返す。他のactive permitのconnectionは保持
capacity/tier不足・retryable overload semantic attemptを消費せずpendingへ戻すかclaim前に待機。retry条件と型付き理由を残す
timeout・cancel・通信断 jobの実行所有権を整理し、上流終了が不明なら枠は照合待ちに残す。C4に従う確認なしで追加requestを送らない
panic・保存失敗 RAIIでローカルguardを片付ける。DB解放失敗は再照合対象として保持し、新規claimで上限を超えない。completed扱いにしない
renew失敗・revision変更・shutdown 新規admission停止。既存requestをdrainし、終了確認後release。新旧generationを混ぜない
stale heartbeat・再起動 stale lease回収と上流request終了を同一視しない。LARM状態と照合し、所有権不明の枠を即再利用しない

P9：移行・canary・rollback

通常設定の既定1を維持してコードを検証し、fake試験が通った後に対象connectionだけ設定上限を広告値以内へ引き上げる。実機ではAPI契約versionとprofile一覧を読み取り確認し、他サービスを妨げない試験用3jobで相関とactive数を観測する。未契約のhealth pollingがsemantic probeを走らせる場合、その負荷を通常の状態監視に混ぜない。

live canary用に、P3のfixture試験とは別のignored test shared_connection_live_canaryを追加する場合の実行形は cargo test -p context-stilld shared_connection_live_canary -- --ignored --nocapture とする。これは新設予定であり現在存在するコマンドではない。URL・profile・認証の入力方法はP1の実契約と既存secret storeへ合わせて、その時点で正確な実行方法を文書化する。未配備契約ならliveは未検証として残す。

rollbackは新規admission停止→active requestの終了照合→旧connection release→上限1と旧単一profileへ復帰の順。active requestが残る間にcredentialを破棄しない。DB migrationが必要になった場合は旧binaryが新schemaを読めるかを試験し、互換でなければコードrollbackを禁止して設定rollbackだけを案内する。

現行 larm-dynamic-provider-contextstill-implementation-plan.html の「各job前にidle確認」は、実装が完成した時点で初回gate＋共有connection追加admissionへ更新する。本書作成だけでは現行契約を置換しない。

実装実績：2026年9月21日

P0を実施し、開始時点の未commit変更は契約監査・settings文書と本書であり、製品コードには変更を加えていなかった。P2を完了した。dynamic_providerのLARM manager registryを、connectionIdだけではなくSQLite runtime scopeとconnectionIdで識別する常駐entryへ変更した。checkout中にもentryをregistryに残し、同一scope/connectionの後続取得は未claimとして扱う。このため、実行中managerがregistryから外れて二重createされる従来の経路はない。

config変更または参照解除では新規checkoutを止めてdrainする。idle managerは直ちに、active checkoutは返却後の次回取得時に旧connectionをreleaseしてから新managerを構成する。release失敗はcleanup未確認として新manager作成をfail-closedで拒否する。registryとentryのlockをHTTP中に保持しない。claimで必要なtargetはcheckout所有のmanagerからsnapshotとして複製し、credentialは既存のZeroizing型のまま保持する。Dropはcheckout状態の返却だけを行い、HTTPを実行しない。

P3は既存のTCP fake HTTP canaryを用いて単一connectionのclaim済みtargetとreleaseを回帰確認した。新規unit testは同一scope/connectionの同時checkoutが2件目を拒否し、返却後には同じregistry entryを再利用することを確認する。3並行requestのchannel制御fixture、capacity negotiation、targetごとの複数lease、context tier admission、設定UIはP1のC1〜C4公開契約が未提供のため未実装・契約待ちとする。推測したfieldや固定capacityで有効化していない。

変更ファイル：crates/context-stilld/src/domains/queue_lifecycle/dynamic_provider.rs、crates/context-stilld/src/domains/provider_connection/service.rs。本実装の検証結果：rustup run 1.98.0-aarch64-apple-darwin cargo check -p context-stilld、cargo test -p context-stilld manager_checkout_keeps_one_manager_per_runtime_connection -- --nocapture、cargo test -p context-stilld dynamic_larm_canary -- --nocapture、cargo test -p context-stilld（491 passed、5 ignored）、git diff --check は成功した。rustup defaultのstable cargoは環境上適用不能だったため、導入済み1.98 toolchainを明示した。live LARMは未検証である。
