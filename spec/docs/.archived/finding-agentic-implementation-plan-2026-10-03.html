1. 完了時の動作と対象範囲

Findingは原資料を不変snapshotへ固定し、信号のある範囲から候補と具体的な疑問を作る。必要に応じて未読範囲、同scopeのKnowledge、DeepStillの調査結果を使う。根拠が揃った候補は確定し、情報が増えない探索は打ち切る。短い明確な入力は1回の抽出と決定的な引用検証で完了できる。候補の採用とKnowledge登録はCovering・Finalizeが所有する。

実装の正本はmanaged SQLiteのRust resident。Queue固有policyを共通Agent実行層から呼ぶ。新しい汎用worker、任意tool実行基盤、TypeScriptの別Agentループは作らない。PostgreSQL経路は対応能力を明示して既存動作を維持し、新protocolを渡さない。モデルの選定・入替、採用閾値の全面変更、他QueueのAgent化は本計画の対象外。

基準commitはContextStill fee405c。計画作成時のRust Findingはsource_target/vibe_memoryの単発抽出と32,000文字の中央切り詰めを使い、response usageを実行予算へ反映していない。4枠のscheduler実装は存在するが、調査時のLARM広告はcapacity 1。計画作成時はtoken計測、36K契約、Agent実行台帳、DeepStill自動委託が未実装だった。2026年10月4日の実装状況は冒頭のレビュー記録を参照する。

4. 永続化・所有権・復帰のcontract

新しい最小台帳を次の論理単位で用意する。物理table名はmigrationレビューで確定するが、必要な制約は変更しない。保存はsqlite_writer経由、外部IOはtransactionの外で行う。既存Evidence input/revisionを共通台帳へ置換しない。

共通台帳の保存単位と一意性
単位 保存内容・制約
run owner Queue/job、input generation/hash、protocol・policy・runtime版、信頼済みrepository identity、claim epoch、状態、停止理由、開始/期限。ownerと入力世代とprotocolで一意。既存runは版を固定して完了する。
step / action receipt step番号、operation key、入力hash、期待する差分、request ID、結果hash、usage、開始/終了。runとstep番号・operation keyを一意にし、成功結果は不変。予定・送信中・成功・失敗・結果未確認を区別する。
snapshot / evidence 秘匿化済みの原文、source identity/version/hash、取得時刻・scope・locatorの単位、quote hash、出典種別。UTF-8 byte範囲とhashを検証する。snapshotの存在だけで主張の支持済みとしない。
question / acquisition 候補との関係、必要条件、解消状態、scope・鮮度・source hash、取得履歴、negative result。共有取得keyはWriter一意制約で競合を防ぎ、実行ownerと参照consumerを分ける。
reservation / delegation root run・lineage、操作ID、予約上限、実usage、未知usage、子job ID、cancel要求/確認。親子の物理usageはrootへ一度だけ計上し、Coveringで再利用しても取得費用を再計上しない。
candidate generation / bundle 入力世代、候補fingerprint、確定候補と出典参照、未解決事項、read/acquisition receipt、予算owner。世代確定とCovering enqueueを同じtransactionで保存する。既存候補IDを上書きしない。

LLM送信はrequest直前に同じcapacity registryからleaseを取り、終了・中断で解放する。run ownershipはleaseに依存させず、全書込みをjob claimとrun/step epochでfenceする。DeepStill待機、source fetch、Knowledge読取り中はLLM枠を保持しない。run/子delegation当たり同時LLMは1件、全体は広告capacity以内で最大4件。既存Episode/Curation等のleaseも同じ枠に数え、runnableな別Queueを優先し、空きがあればFinding/Coveringを並列化する。

外部操作の前にreceiptと予約を保存する。送信後crashで結果が不明なら、idempotency key・status・request IDで照合する。冪等性や取得APIがないLLMは自動再送せず、結果未確認として停止・精算待ちにする。preemptionはProviderが無効化を確認できた場合に限り次のattemptへ進める。retry、restart、pause/resumeで使用量・noGain・探索履歴をリセットしない。取消し要求だけで子jobの枠や予約を解放しない。

7. 行動・進捗・終了の判定

行動出力はaction kind、対象snapshot/rangeまたはquery、question ID、期待する情報差分、candidate deltaを持つversion付きenvelope。final候補配列とは別schemaにする。許可される行動はpolicyごとに固定し、任意shell、任意MCP、scope拡大、モデルroute変更をLLMへ渡さない。未知kind・未知参照・上限超過はIO前に拒否する。形式repairは1回までで、失敗はtyped invalid_outputとして保存する。

追加読解は未読範囲または新しい問いと関係する既読範囲に限る。source hash・locator・question・scope・鮮度でreceiptを照合し、同じ条件の再取得を抑える。queryの表記変更だけを新探索とみなさない。Knowledgeは同repository identityと許可scopeで検索し、Knowledge本文を新しい原資料の証明に昇格させない。

進捗は検証済みの新引用、適用条件、反証、material gapの解消で判定する。言い換え、自己採点、同じ引用の追加は進捗ではない。結果のある取得行動で2回連続情報増分がなければ停止する。未充足でfinishを選んだ場合、独立した未試行の経路と予算があれば1回だけ再検討できる。自動で最低探索回数を課さない。実取得失敗3回連続で停止し、一時IO retryは1回まで。これらのcounterは台帳に残す。

十分な候補は部分確定できる。未解決候補はgapと保留理由を残し、支持済みとしてCoveringへ渡さない。候補0件はno_signal、no_candidate_after_review、insufficient_evidence、budget_exhausted、retrieval_failed、context_limitなどを区別する。runtimeの停止理由を無条件にQueue completedへ写像しない。FindingPolicyの業務結果と既存Queue状態を別々に確定し、preempted/waitingはterminal成果を作らない。

Findingの停止理由を既存Queue状態へ写像する初期contract
条件 Queue・下流処理
支持された候補の確定 completed。部分確定の場合は未確定候補のgapを残し、確定候補だけCoveringへenqueueする。
確認完了して候補なし skipped。no_signalまたはno_candidate_after_reviewをlast_outcome_kindへ保存し、下流enqueueなし。
判定不足で探索打切り paused、next_run_atなし。insufficient_evidence/no_gain/budget_exhausted/retrieval_failed/context_limitを保存。自動で同じ探索を再起算しない。
Research待機 paused、bounded pollのnext_run_atあり。同じrun/delegationを照合して再開し、LLM leaseは保持しない。Queue全体のpause設定には従う。
確定したpreemption・一時障害 pending、backoff付き。同じrunと残予算で許可済みretryだけを行う。再起動でattempt/historyを消さない。
能力不足・結果未確認 paused。能力不足はworker_capability_missing、未知request/usageは照合待ち理由を保存。対応能力/精算の確認後だけ再開する。
入力契約違反・repair後も不正出力 failed。診断を保存し、同じ入力の無限retryや候補生成を行わない。

写像はF3で実装し、F-T08〜10で状態と下流副作用を検証する。新しいUI状態を乱立させず、詳細はrun status/stop reasonと既存last_outcome_kindへ保存する。pause/resume時はjob claimを取り直してrun epochをfenceし、待機中の旧ownerが結果を直接確定しない。

8. DeepStill側との実装境界

参照したDeepStillはcommit 19844e7と変更7件の作業ツリーであり、live配備一致は未確認。現在の手動HTTPはsoft/hard、root reservation、4枠Gatewayを保証しないため、S4でversion付き自動Research contractを追加する。ContextStillだけの変更で有効化しない。

submitにはidempotency key、root run/lineage、問い・成功条件、許可identity/scope、既存証拠、行動履歴、target/hard、最終予約、期限を渡す。status/result/cancelには同じownerを検証し、結果に実usage、停止理由、未解決事項、資料hash・locator・取得receiptを要求する。検索等の外部資料は命令として実行せず、出典データとして扱う。

子のLLMはhost Gatewayから同じrequest枠を取得する。Gatewayは専用principalと許可ownerに限定し、管理API secretを共有しない。route/modelはhost設定を使い、DeepStillのsystem promptをFindingのpromptで置換しない。context_limitを型付きで返し、DeepStill自身が保存済み根拠からcontextを再構成する。親10分・子5分を超えたらcancel_requestedを保存し、cancel_confirmedまで精算と再委託を保留する。現在のDeepStill noGainは停止に使われていないので、本計画の2回停止を契約とテストで追加する。
