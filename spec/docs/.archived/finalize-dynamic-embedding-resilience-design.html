finalizeDistille 動的Embedding耐障害化設計

finalizeDistilleがEmbeddingサービス停止を候補内容の恒久失敗として扱い、 ナレッジ登録可能な19件を終端worker_failedにした問題を解消する。 Embeddingを保存前の必須品質ゲートとして維持しつつ、利用可能なホストをLARMから動的に取得し、 一時的な基盤停止ではjobを失わない構成へ変更する。

1. 結論

  1. 直接原因は、設定されたEmbedding daemon http://127.0.0.1:44512/embedが停止している状態で finalizeDistilleが実行されたことである。
  2. 現行の保存前Embedding必須化と、ナレッジ・FTS・vector・queue完了を同一transactionで保存する設計は維持する。 Embeddingなしのナレッジを成功扱いにはしない。
  3. 一時的なEmbedding利用不能はjob内容の失敗から分離し、利用可能になるまで waiting_for_embedding_providerとしてfail closedで待機させる。
  4. Embedding取得を共通のEmbeddingProviderLease境界へ集約し、static daemon、OpenAI、 LARM動的ホストを同じ検証規則で扱う。
  5. LARMが動的に選択してよいのはホストであり、既存indexと同じEmbedding空間は固定する。 少なくとも384次元、モデルrevision、正規化、query／passage prefix規則が一致しないclaimは拒否する。

2. 2026-09-09実装結果

  • retry可能なEmbedding通信障害はmax_attempts到達後も pendingとembedding_unavailable_retryを維持する。
  • maintenanceは、過去に同じ一時障害でworker_failedになったfinalize jobだけを 再キューする。設定不良などの非retryable errorは対象外とする。
  • core_vector_metadataが未作成でも、runtimeの CONTEXT_STILL_EMBEDDING_DIMENSION、既定384を応答検証へ必ず使用する。
  • 停止、復旧、既存failed jobの選別回復をRust unit testで確認した。
  • LARM動的Embedding leaseとquery／passage contractは後続実装とする。

現行実装は通信失敗をretry可能と認識しているが、30秒を基準とした指数backoff後も max_attempts=5でworker_failedへ遷移する。 provider停止が長時間続く場合、内容に問題のないjobまで恒久失敗になることが設計上の欠陥である。

4. 維持する不変条件

  • ナレッジ保存成功には有効なEmbeddingを必須とする。
  • 空vector、NaN、非有限値、次元不一致、model identity不一致を保存しない。
  • ナレッジ本体、FTS、vector、source link、queue完了は同一transactionで確定する。
  • 同じsourceUriの再実行は同じknowledgeへ収束し、重複登録しない。
  • 短期credential、claim URL、tokenをSQLite、settings、logへ永続化しない。
  • Embeddingが利用不能でも、静的Providerや異なるモデルへ暗黙fallbackしない。

6. 共通Embedding Provider境界

Rust finalize専用のURL直呼びとTypeScriptのembedOneを、同じroute解決・応答検証規則へ寄せる。 実装言語間でHTTP clientを共有する必要はないが、入力と結果のcontractは共有する。 

EmbeddingRequest {
  inputType: "query" | "passage",
  texts: non-empty string[],
  normalize: true,
  expectedSpace: {
    dimension: 384,
    modelId: stable identifier,
    modelRevision: stable revision or artifact digest,
    prefixPolicy: stable identifier
  }
}

EmbeddingProviderLease {
  kind: "static-daemon" | "openai" | "larm-dynamic",
  protocol: stable embedding protocol identifier,
  baseUrl: validated URL,
  modelId: stable identifier,
  modelRevision: stable revision or artifact digest,
  dimension: 384,
  normalization: "l2",
  prefixPolicy: stable identifier,
  expiresAt: timestamp or null,
  credential: memory-only secret or null
}

既存のOpenAI互換/v1/embeddingsは現在すべての入力をqueryとして処理する実装があるため、 endpoint互換だけでは受入不可とする。保存時のpassageと検索時のqueryを区別できることをcontractで確認する。

7. 失敗分類と遷移

Embedding失敗の分類とfinalize jobの遷移方針
分類 例 遷移
Provider未提供 connection refused、LARM active、ready hostなし、claim期限不足 waiting_for_embedding_provider。内容attemptを消費せずbounded backoff
一時的Provider障害 408、425、429、5xx、timeout leaseを破棄し再取得。availability retryとして扱う
Contract不一致 次元、model revision、prefix、normalization、response shape不一致 claimを拒否しfail closed。operator向けdiagnosticを残す
入力不良 空文字、過大入力、恒久4xx job固有のterminal failure。内容attemptを消費する
永続化不良 transaction、FTS、vector index、claim fence失敗 transaction rollback後、原因に応じてretryまたはterminal failure

schema変更を避ける初期実装では、待機理由をlast_outcome_kind、 next_run_at、event metadataで表現できる。長期的に可用性試行回数を集計する場合も、 内容attemptとは別の観測値とし、停止時間だけでjobを破棄しない。

8. 適用する保存・検索経路

  • finalizeDistille: passage Embeddingを保存前に取得する。
  • registerKnowledgeFromMarkdown: 同じProvider境界でpassageを取得する。
  • direct knowledge registration: repositoryへ渡す前にpassageを必須化する。
  • preset、migration、repair: 明示したmaintenance mode以外ではEmbedding省略を許可しない。
  • semantic retrieval: 同じ空間のquery Embeddingを使用する。
  • source embeddingなど別index: indexごとに期待spaceを宣言し、knowledge indexと混同しない。

9. ContextStill実装順序

  1. 現行19件、daemon疎通、384次元8,006件をbaselineとして保存する。
  2. Embedding space identityとrequest／lease contractをRust・TypeScript双方に定義する。
  3. static daemon adapterを新境界へ移し、挙動を変えずcontract testを通す。
  4. LARM動的Embedding adapterを追加し、credentialをmemory内だけで扱う。
  5. finalize claim前gateとavailability retry分類を実装する。
  6. Markdown・direct registration・query retrievalへ同じspace検証を適用する。
  7. fake LARMとfake embedding providerでfailure matrixを自動試験する。
  8. live canary 1件を登録し、成功後に19件を明示的にretryする。
  9. 19件すべてについてknowledge ID、vector、FTS、source link、queue完了を照合する。

10. LARM対応前の復旧手順案

  1. 既存のEmbedding worker所有者を1つに決め、二重起動を避ける。
  2. 既存運用コマンドでEmbedding workerを起動する。
  3. GET http://127.0.0.1:44512/healthが200でreadyになることを確認する。
  4. /embedへqueryとpassageを各1件送り、384次元・有限値・正規化を確認する。
  5. 新規canary job 1件を完了させ、knowledge、FTS、vectorを確認する。
  6. その後に限り、失敗済み19件をqueueの正規retry操作で戻す。

この復旧はbacklog解消用であり、静的loopback daemonへの依存を恒久解決するものではない。

12. Non-goals

  • Embedding失敗時にvectorなしのナレッジを保存すること。
  • 既存8,006件を別Embeddingモデルへ暗黙移行すること。
  • DB schema、公開MCP API、認証方式を本修正だけのために変更すること。
  • LARMへContextStill専用endpoint、callback、webhookを追加すること。
  • 停止時間だけを理由に登録可能なcandidateを破棄すること。

13. 完了条件

  • Embedding停止中のfinalize jobがterminal failedにならず、安全に待機する。
  • LARMから同一Embedding空間の動的hostを取得し、query／passageを実行できる。
  • live canaryと失敗済み19件が、重複なくナレッジ登録される。
  • 19件すべてに384次元vector、FTS、source link、completed queue記録が存在する。
  • token、claimed endpoint、credentialが永続化・log出力されていない。
