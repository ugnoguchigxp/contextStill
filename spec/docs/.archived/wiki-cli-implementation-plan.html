SQLite単一writerと知識抽出の評価

推奨は、Markdownの保存に加え、既存daemon writer経路でソース・索引を更新し、対象ページの知識抽出を明示依頼する方式。 Markdownだけを保存する方式は、知識化が不要なメモやdaemon停止中の保管には向くが、contextStillの知識抽出機能を利用したい今回の目的には不足する。以下はコード上の確認であり、daemonの実稼働は未確認。

Markdown変更は自動的に知識化されるか

今回確認したsourcesモジュール、daemon実装、automationの範囲では、Wiki Markdownの変更を常時監視してFindingへ投入する処理は見つからなかった。全リポジトリ・実運用の外部ジョブまで不在を証明したわけではないため、「監視なしと断定」せず「自動取込みは未確認」とする。ファイルを置くだけで知識が抽出される前提は置かない。

  • ページPOST/PUT: Markdown/Git/ソースと検索用断片を更新するが、Findingへの投入はない。
  • sources.routes.ts 192行付近の /reindex: ページのソース/断片を再登録する。Finding投入はなく、removed: 0。移動/削除に伴う旧ソース清掃も保証しない。
  • markdown-importer.service.ts 85〜180行付近: 明示import時にソース登録、wiki_file のFinding job検索/投入、root内のstale source削除を行う。既存jobを見つけるとskipするため、編集後の新しい版が必ず再抽出される保証はない。
  • importerのURIは絶対file path、ページAPIのURIはpagesからの相対path。importerのtree全体呼出しを保存APIに足すだけでは、同じページの二重sourceや意図しないstale削除を生み得る。共通のページURI/source keyを決め、ページ単位の投入だけを再利用する。

ソース登録と知識抽出の完了を分ける

推奨仕様ではcreate/updateに --extract または --no-extract の一方を必須とする。--no-extract でもソース/索引はwriter経由で更新するため、Markdownのみの方式とは異なる。無指定で全会話/全Wikiを抽出しない。ユーザーが選んだページの保存版だけを対象にする。SAAAからの利用例は --extract を選ぶ。

共通サービスでファイル/Git保存、source/断片登録のあと、既存queueのDB所有境界を再利用してページ単位の抽出依頼をwriter経由で永続化する。既存 enqueueFindingJob を無条件には呼ばない（下記の制約）。root全体import、直接Knowledge作成、候補の自動active化はしない。既存URIとwiki target keyの整合、内容version単位の重複抑止、更新時の再投入可否は追加設計が必要。既存jobがあるというだけで新しい版をskipしない。schema追加が必要かはqueueの既存payload/metadata・重複規約を確認して判断する。

抽出経路は実装前の必須確認事項。 finding_executor.rs の execute_finding は source_target/vibe_memory 以外を UnsupportedInput とする。finding_executor_tests.rs では wiki_file がpausedになることを検証している。このRust経路だけではWiki抽出は進まない。別worker/legacy経路がWikiを処理できるか、実運用のroutingとローカルprovider構成を確認する。対応経路がなければ、Wiki抽出worker対応を別の明示的な実装項目として見積もり、初期版で実施するか判断する。未対応のまま抽出受付成功を返さず、--extract は保存前に EXTRACTION_UNSUPPORTED として拒否する。--no-extract は索引更新までの機能として独立して受け入れ可能。

worker.ts の enqueueFindingJob（2265行付近）は、同じinput kind/source kind/source key/distillation versionのjobがあるとpendingへ戻し、locked_by/locked_at/heartbeatを消す。実行中jobの再投入には使わない。findFindingJob → enqueueFindingJob の二段階呼出しだけでは、他のproducerとの競合も防げない。writerの短いtransaction内で状態を確認し、実行中なら変更せずbusyとして扱う。完了済み同一版は結果を再利用、更新版は別の版別依頼として扱う。distillation versionはpipeline版であり、本文hashの代用にしない。既存制約で版別jobを持てない場合は、既存schema/契約を確認した上で最小のversion/operation対応を追加する。実行中jobへの変更はclaimを維持するだけでなく、後段結果の永続化をlease/versionで照合して古い結果を採用しない。これは要調査の変更であり「DB schema変更不要」とは確定しない。

抽出workerが現在ファイルを読む場合、job受付後の編集で別の版を抽出する危険がある。covering_executor/source.rs は source_read_root/pages 以下のsource keyからファイルを読む。importerのtarget keyは markdown-importer.service.ts の readFile.root 基準なので、両者の基準を同一視しない。保存版を抽出する保証は、後段の証拠読取りまで含めて必要。 採用するworkerがimmutableな保存版を読めるならcommit/versionを伝播させる。対応しない場合は、各読取り/結果永続化でexpected versionを確認し、不一致をsupersededとして止める最小対応を計画する。最新ファイルを無条件に読むまま、古いversionの抽出成功を記録しない。この対応を確認できない間は --extract の受入を保留する。

応答は fileState（saved）、indexState（ready/pending/failed）、extractionState（not_requested/queued/failed）、jobId、knowledgeState（unknown/not_requested）を分ける。queued はjobがwriter経由で永続化された状態であり、KnowledgeやSAAA検索が完了した状態ではない。受付は202相当でもCLIの終了コード0としてよいが、短い人向け出力も「保存・索引反映・抽出受付」と明示する。初期四操作はjobの後日の状態を追跡するコマンドを持たないため、knowledgeStateは受付応答時点のunknownに留める。jobIdで既存管理UI/queue確認へ引き継ぐ。処理待ち・失敗・棄却・未active化を知識化完了と誤表示しない。

file/Git成功後にwriter/queue依頼が失敗した場合は部分完了（exit 7）。同じoperation IDで索引/抽出投入の未完phaseだけを復旧する。別operationでの自動重複投入はしない。抽出受付前にwriter不調を検知した場合は原則として保存前に終了するが、途中停止はあり得るためphase記録は必要。Operation記録にjob ID/対象versionを追加し、応答消失後の再試行で二重抽出を防ぐ。

評価として、DB索引更新と抽出依頼を行う方がユーザーの目的に合う。追加の抽出にはLLM/embedding処理・queue待ち・既存レビューのコストがあり（実測費用/所要時間は未確認）、保存ごとの自動知識化は採用せず、選択したページに限って依頼する。非公開性はloopbackだけでなく、抽出側のLLM・外部検索providerについてもローカル/無効であることを確認する。既存pipelineが外部調査を必須とする場合は、ローカルのみの対応方法を決めるまで --extract の非公開受入は未成立とする。

HTTPを第一候補にする理由

HTTPならCLIがDB、SQLite writer、Git設定、embedding providerを個別に初期化せず、UIと同じ所有者・同じ保存経路を使える。Mac上の別作業ディレクトリからも呼べる。代わりに、APIが利用可能で、管理キーを安全に渡せることが前提となる。CLIはAPIを自動起動しない。

内部サービスをCLIから直接呼ぶ方式はAPIへの到達を不要にするが、現状の保存手順はrouteにあり、ファイル操作だけを呼ぶとGit・DB登録が抜ける。DB設定/環境読込み、writer接続、embedding、複数プロセス競合もCLI側へ持ち込む。既存直接サービスCLIであっても本番DBへのmutationはremote writerへ委譲されるため、直接サービス呼出しは「SQLite直接書込み」と同義ではない。ただし今回のCLIにこの依存を持ち込む利点は小さい。初期版では採用せず、HTTP失敗時にも自動切替しない。

サーバー側に小さい wiki-page.service.ts を作り、既存routeの処理を移す。HTTPと将来のMCPは同じサービスへ入力を渡せる構造にする。汎用プラグイン基盤や複数transport抽象は作らない。新しいCLI向け入口案は /api/sources/wiki-cli/pages（一覧/作成）と /api/sources/wiki-cli/pages/*（読取り/更新）。既存管理認証をそのまま適用し、専用領域・必須版照合・operation IDの契約をこの入口で強制する。URLと命名は実装時に既存routeとの順序衝突を確認する。

コマンドと入出力

正式な入口は context-still wiki <command>。開発時は bun run context-still -- wiki ... とし、既存landscapeとaliasを壊さない。実装時にBunの引数渡しを確認する。任意の作業ディレクトリから呼べるよう、CLIのcwdでサーバーの保存先やDBを決めない。

以下の saaa-notes は未決の専用領域名の例であり、現在の設定ではない。 

# 呼出元が保存したUUIDとgetで取得した版を使用する
REQUEST_ID="保存済みのUUID"
VERSION="sha256:getで取得したhash"
context-still wiki list --json
context-still wiki get saaa-notes/example --json
context-still wiki get saaa-notes/example --format markdown
context-still wiki create saaa-notes/example --title "題名" --file ./note.md --extract --request-id "$REQUEST_ID" --json
context-still wiki create saaa-notes/example --title "題名" --stdin --extract --request-id "$REQUEST_ID" --json
context-still wiki update saaa-notes/example --file ./note.md --if-version "$VERSION" --extract --request-id "$REQUEST_ID" --json
  • list: 専用領域内のslug、title、versionを返す。既存treeの全件取得後にCLIだけで隠す方式にしない。初期版はページング・全文検索を追加せず、件数/応答サイズ上限超過を明示エラーとする。
  • get: JSONにはbody、meta、versionを含める。--format markdown は本文のみを出力し、create/updateの本文入力として往復できる。title/metaはJSONで取得する。frontmatterを含むファイル入力は曖昧な二重frontmatterを避けるため初期版では拒否する。--format と --json の同時指定も拒否する。
  • create: title必須。既存ページを更新するupsertは行わない。
  • update: 本文置換、titleは任意で未指定なら維持。既存metaは維持し、初期版では任意meta変更、slug変更、renameを提供しない。--if-version 必須、強制上書きフラグなし。
  • --stdin と --file は必ず一方のみ。暗黙のstdin待ちはせず、UTF-8とサイズを検証。本文をコマンドライン引数へ埋め込む --body は提供しない。
  • 書込みの --extract / --no-extract は一方を必須とする推奨仕様。request IDは呼出元が生成・保持して渡す。曖昧な失敗後は同じIDと同じ入力で再試行できる。SAAA/タスク向け使用例にUUID生成と保持方法を示す。
  • 通常出力は短い人向け表示。--json はstdoutに単一JSON、診断はstderr。body、認証情報、HTTPヘッダーを診断ログへ出さない。

JSON契約案:

{"ok":true,"command":"update","page":{"slug":"saaa-notes/example","version":"sha256:..."},"commit":"...","sourceId":"...","operationId":"...","fileState":"saved","indexState":"ready","extractionState":"queued","jobId":"...","knowledgeState":"unknown"}

{"ok":false,"error":{"code":"VERSION_CONFLICT","message":"ページが更新されています","retryable":false},"slug":"saaa-notes/example","currentVersion":"sha256:...","operationId":"..."}

一覧/読取りは items または page を持つ。indexState はソース/断片更新の結果であり、Knowledge蒸留の完了を意味しない。エラーに本文やキー、絶対内部パスを入れない。

接続・非公開・領域制限

API URLはCLI専用環境変数 CONTEXT_STILL_WIKI_API_URL、未指定時 http://127.0.0.1:39170 とする案。開発用39171は明示指定し、URLの自動走査やMCP URLからの推測はしない。許可ホストは数値loopback 127.0.0.1 / [::1] に限定。userinfo、query、fragment、APIパスを含むbase URL、redirect、外部ホストを拒否する。schemeはhttpのみ、portは1〜65535の明示値とする。接続/read/writeのtimeoutを設定し、外部接続を行わない。初期値案はHTTP 60秒、ロック待ち5秒。応答サイズ上限は32MiB、本文入力は8MiB以下、JSON request全体は既存API上限16MiB以下、Markdownシリアライズ後も16MiB以下。一覧は最大1000件で、超過は切り捨てずエラー。HTTP timeoutはembedding処理時間と照らして実装時に確認する。

管理キーは既存 CONTEXT_STILL_ADMIN_API_KEY を呼出元が秘密を扱う仕組みから環境へ渡す。引数指定、設定自動生成、.envの自動探索/表示は行わない。推奨仕様では専用CLIのキーを明示必須とし、built-inキーへの暗黙fallbackをしない。API側の既存キーは変更しない。API独自キーの場合、同じ名前の環境変数がCLI側にあるだけでは有効性を保証しない。401/403で終了し、別キーへ自動fallbackしない。

専用領域はサーバー設定 CONTEXT_STILL_WIKI_CLI_NAMESPACE 案で固定し、未設定ならCLI向け入口を無効化する。利用者の --root / --namespace で境界を変更させない。例: wiki/pages/saaa-notes/。一覧・読取り・作成・更新のすべてでサーバーがslugのsegment境界を検証する。saaa-notes-other を許可しない。既存管理UIの権限は変えず、CLI専用入口を介した操作を限定する。

これは管理キー自体の権限縮小ではない。キー保有者は既存の管理APIへ直接アクセスできるため、悪意あるクライアントに対する強制隔離はできない。初期版は同一Mac・信頼する呼出元向け。権限を厳密に分ける必要があれば新規認証基盤の別計画が必要となる。

slugはクライアント・サーバー両方で検証する。絶対パス、空/root slug、./..、backslash、NUL/制御文字、encoded slash/backslash、二重エンコードで意味の変わる値を拒否する。HTTP pathはsegmentごとにencodeし、decodeは一度だけ。現状の sanitizeSlug は絶対形を相対形へ変換するため、それだけに依存しない。実パスはcanonicalなpages/専用領域内に収まり、既存祖先とtargetにsymlinkがないことを検証する。外部プロセスによるsymlink差替えを完全に防ぐOS sandboxは追加しないため、所有者以外が保存先を変更できない運用を前提にする。

本文は自動的に全会話から採取せず、明示されたstdin/fileだけを送る。既存upsertはembeddingを呼び得るので、APIがloopbackでも情報が外部providerへ送られない保証にはならない。実装開始前に既存embedding設定がローカルまたは無効であることを秘密値を表示せず確認する。確認不能なら非公開受入条件を満たしたと扱わない。

版照合・Git・失敗と再試行

version は保存されたMarkdown全体（frontmatter含む）のSHA-256とする。Git HEADだけでは別ページの更新でも競合するため使わない。getの本文/meta/versionは一回の読取りから生成する。updateは共通書込みロック内で現在版と照合し、差異は412、precondition欠落は428。createの存在確認も同じロック内で行う。クライアントのget直後に通常PUTを呼ぶだけでは競合を防げない。

Wiki Gitリポジトリ全体を対象にしたプロセス間ロックを用いる。ページ単位ロックだけではGit indexを共有する競合が残る。既存UIのcreate/updateを同じサービスへ移し、既存delete/rename等のGit変更にも同じロックを適用する（新しい削除コマンドは追加しない）。複数API/既存importerなどロックに未参加のwriterは同時利用しない。Git HEAD/indexと対象ファイルの外部変更を検出した場合は停止する。手動編集と完全な原子的競合防止ができるとは約束しない。

処理順は「入力検証・writer/抽出capability確認 → operation登録/ロック → 版照合・Git事前確認 → 一時ファイルと同一ディレクトリで原子的rename → 対象ページだけGitコミット → writer経由のソース/断片更新 → 要求があればwriter経由で抽出jobを受付 → 完了記録・結果返却」。関係ないstage済み変更がある場合は初期版では書込みを拒否し、他人のindexをreset/stashしない。現状の通常git commitをそのまま再利用せず、ロック下で対象path限定の履歴を作る。対象ページが手動変更中の場合も拒否し、呼出元へ確認を促す。CLIはGit未初期化/identity未設定も変更前に拒否し、git initやidentity設定を自動実行しない。未完operationがあるページへの新規IDの更新はサーバーで拒否する。読取りは未初期化のrootを作らず、明示エラーとする。

ファイル/Git/DBを一つのtransactionにできない。最小のoperation記録をowner-onlyの既存runtime領域へ置き、request ID、入力hash、slug、旧/新version、完了phase、commit、sourceIdを原子的に保存する。本文・キーはoperationファイルに保存しない。operation記録単独ではschema追加不要だが、jobの重複抑止/版対応で必要となる可能性は残る。同じIDの別入力は409。request hashにはcommand、slug、本文、title指定有無、if-version、抽出指定を含める。再試行ではoperation照合を現在版のpreconditionより先に行う。同じID・同じ入力の完了済みoperationは当時の結果を返し、二重commitを作らない（後続編集があれば現在ページの版とは異なり得る）。進行中/部分完了では新しいIDで同じページを書かず、同じIDで復旧する。

  • 保存前失敗: 変更なし。ロック取得失敗は待ち時間を制限し、busyを返す。
  • ファイル保存後/Git失敗: exit 7。手動変更がなければ同じIDでGit以降を続行。自動git reset/rollbackはしない。
  • Git後/DB失敗: exit 7、phaseを示す。同じIDでソース/断片だけを再構築し、新しいcommitを作らない。
  • 応答消失: exit 6、結果不明を示す。書込みの自動再送はしない。同じIDと入力による明示再試行だけを許可する。
  • 記録更新前のプロセス終了: 現在のファイルhashとGitの対象path/operation識別情報で完了phaseを照合する。確証がなければ RECOVERY_REQUIRED として停止。曖昧な結果を成功扱いしない。
  • 抽出登録後/operation記録前の終了: request ID/対象versionをjobと同じwriter transactionで記録し、既存jobを照合して復旧する。runtimeファイルだけの記録では二重投入を防げない。実行中jobのclaim状態を消して復旧しない。
  • ロック/operationの残骸: 所有プロセスの状態を確認し、勝手に破棄しない。初期版の復旧手順を文書化する。初期版ではoperation記録を自動削除せず、10000件に達したら新規書込みだけを拒否し、既存IDの再試行/読取りを許す。保持期間による自動清掃は別途設計する。古いIDを新規依頼と誤認しない。

既存upsertをそのまま呼ぶだけでは断片のdelete/insert途中失敗が残る。embedding生成は可能ならtransaction前に行い、source本体と全断片の置換を既存writer境界に従ってまとめる。SQLiteは既存remote adapterの同期transactionを使用し、writerの30秒所有期限内で完了させる。PostgreSQLは従来のDB所有境界で確認し、未対応backendはCLI書込みを明示拒否する。embedding失敗の既存fallbackは維持できるが、検索用テキスト断片の登録失敗は成功扱いしない。版は実際に保存されたMarkdown bytesを対象とする。現状はWikiのサニタイズと索引の秘密除去が別処理なので、秘密除去済みの同一本文が両方に入る保証はまだない。CLI向けサービスで保存前の共通正規化を行い、その最終本文からファイルと索引を作る案を採る。既存UIの正規化仕様を無断で変えず、差分をテストする。

実装順序・最小テスト・受入条件

  1. 到達可能なAPIの正本URL、backend、専用領域、管理キー運用、embeddingのローカル性を確認する。自動起動/設定書換えで到達問題を隠さない。
  2. 既存保存手順を小さいサービスへ抽出し、既存UIの挙動を維持。source/断片の整合、Git対象限定、共通ロックを先に成立させる。
  3. Wiki対応workerのcapabilityと版固定/照合を確認し、不足対応を見積もる。namespace、version、operation ID/復旧契約、抽出の明示選択・job受付状態をAPIへ追加。旧routeとの併用による競合をテストする。URI/版の対応と再抽出の重複規約を確認する。
  4. CLIの一覧/読取りを実装し、続いてcreate/updateを追加。既存CLI入口へ接続。
  5. 隔離した一時Wiki/Gitとtest DB/writer、fake HTTPで必要なテストだけ実行し、使い方と復旧手順を記載する。実Wiki/本番DBで試さない。

最低限の検証は次の通り。

  • CLI: help、四操作のmethod/path/body、stdin/file排他、UTF-8/上限、JSON stdout、上表の終了コード、秘密を出さないこと。redirect/外部URLを拒否し、接続失敗でサービスや直接DBへfallbackしないこと。
  • 境界: namespace外、似たprefix、絶対パス、dot segment、encoded/double encoded traversal、backslash、symlinkを拒否。一覧も領域外を返さないこと。
  • 競合: 同じversionで並列updateし一方だけ成功。create並列でも一件だけ作成。UI経由の先行変更はCLIの版照合が検知。同時操作は共通ロックで直列化（旧UI自体の必須版照合を保証するものではない）。他人のstage済みファイルをコミットしないこと。
  • 隔離した実Git/DB: create/get/update/listが一致し、対象履歴とソース/断片が反映。Git失敗、DB失敗、応答消失、phase記録直前の終了を注入し、同じIDの再試行で二重commit/二重sourceを作らないこと。
  • writer/抽出: testフラグのない別プロセスと隔離writer/DBで、API/CLIが書込みSQLite接続を開かず、mutationが既存writerに委譲されること。writer不在でも直接書込みにfallbackしないこと。選択ページ/版だけFindingへ投入し、同じoperationの再試行は二重投入せず、更新版は再抽出を依頼できること。抽出受付後のLLM失敗や処理待ちをKnowledge検索完了と誤表示しないこと。
  • backend: 使用するbackendで断片置換途中失敗による不整合が残らないこと。未対応backendは変更前に拒否。既存source/routeの関連回帰テストとtypecheckのみを基本とし、広い全体suiteは回帰が疑われる場合だけ実行。

--extract の受入には、隔離環境でWikiのFinding/証拠処理が実行され、保存版に対応する候補へ到達する一件のend-to-end検証を含める。実データを外部へ送らず、最終Knowledgeのactive化や実SAAAへの接続は別の評価とする。未対応workerにjobを置いただけでは受入を通さない。

受入条件は「同じMacの任意の作業ディレクトリから、明示した本文だけを専用領域へ保存できる」「古い版と領域外の書込みは拒否される」「成功時はMarkdown/Git/ソースと断片が整合し、要求した抽出が対応workerへwriter経由で受付済み」「途中失敗を成功とせず再試行手順がある」「外部通信/公開を伴わない」の五点。SAAAからのKnowledge検索完了は別の蒸留経路のため受入に混ぜない。SAAAのCLI呼出し統合は初期版CLI完成後の別作業であり、本計画では接続例と入出力契約までとする。

初期版の実装判断

ユーザーの実装依頼を受け、推奨HTTP方式、明示管理キー、抽出選択必須、サーバー固定namespaceを採用する。namespaceは環境設定で指定するまで無効とする。Rust常駐Finding workerはWiki入力を未対応としているため、初期版の --extract は保存前に422 EXTRACTION_UNSUPPORTED で拒否する。版固定のWiki抽出workerを追加するまではqueuedを返さない。

CLI書込みのbackendはSQLiteに限定する。テキスト索引は既存writerの同期transactionで原子的に更新する。非公開性を実証できないembedding daemonの下流providerへ本文を送らないため、初期版のCLI書込みは CONTEXT_STILL_EMBEDDING_PROVIDER=disabled を要求する。既存UIのembedding仕様は維持する。ローカルprovider対応の拡張は別途必要である。

未決事項と初期範囲外

ユーザー判断が必要なのは、推奨する索引/抽出依頼方式で進めるか（Markdownのみは明示的な別案）、抽出の --extract / --no-extract 選択契約、専用領域名（例 saaa-notes）、その領域を既存のglobal知識として扱ってよいか、管理キーを持つ信頼する呼出元向けという権限範囲でよいか、明示キー必須という推奨仕様を採用するか。領域名/キー配布を決めるまでは新規入口を無効に保つ。

実装前に調べる点は、API到達方法、Wiki抽出worker/routingの対応状況、readFile.rootとsourceContent.root/pagesの基準、既存writer経路の実稼働と正本DBの一致、短い同期transactionへのまとめ方、LLM/embedding/外部検索の接続先がローカルまたは無効か、ページAPI/importerのURI・版別抽出規約、runtime領域の正本とoperation記録保持期間、既存importer等の同時writerがあるか。これらは今回の計画書保存のために起動・秘密読取り・設定変更で解決しない。

削除、公開、rename、新規認証基盤、MCPツール追加、任意root指定、無指定の自動蒸留/会話全量保存、サービス自動起動、SAAA本体の改修は初期範囲外。保存する処理の分離は将来MCPで再利用できる程度に留める。
