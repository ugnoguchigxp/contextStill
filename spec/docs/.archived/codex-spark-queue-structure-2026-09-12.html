4. Queue側で必要な変更

  1. RustからSDKへの接続。crates/context-stilld/src/domains/queue_lifecycle/executor.rsの静的route_claim_group_idはlocal-llmだけを選び、claim_provider_execution_for_connectionは全targetをproviders.local-llm.modelsから解決する。TypeScriptのschedulerやprovider型にcodexが存在しても、Rust側の実行機能は完成していない。
  2. targetごとのモデル固定。現在のRuntimeProviderPoolTargetのcodexにはtargetIdしかなく、専用modelを持たない。applyProviderLeaseRouteContextもcodex選択時はproviderを変えるだけで、元routeのmodelを残す。Spark targetのmodelを明示的に引き継ぎ、SDK送信値と利用ログを一致させる必要がある。
  3. 実際に並行実行するdispatcher。run_split_provider_executor_tick_for_pathはclaim後に同期実行し、完了してから次をclaimする。Finding・Episode・CurationはmaxConcurrentを上げるだけでは同時に走らない。max_claimsも1tickの処理件数である。Coveringには別途thread spawn/joinの並列実装がある。
  4. Spark枠切れの扱い。provider_lease.rsの一時障害cooldownは60秒。Agent Sessionのturn.failedは文字列化され、Findingのretry判定はHTTP 429等の文字列に依存する。各接続のquotaエラーを分類し、利用枠が尽きた接続を候補から除外する仕組みが必要。Sparkは別bucketを確認し、Museも提供側の利用枠情報または明示的な枠切れ応答を扱う。

既存leaseには使用中targetの除外とQueue間のfairnessがある。モデルtargetは既存の最終使用時刻に基づく選択を行い、poolのtarget列はBTreeSetで集約される。設定の並び順を担当比率として扱わず、並列workerと必要なtarget公平性で配分する。

5. 改訂案：既存SDKをキュー実行基盤へ接続する

確定方針：Qwen・Muse・Sparkは同じ優先度の実行候補とする。 モデル別の優先順位や固定の担当比率を設けず、利用可能な空き接続へjobを配分する。利用枠が尽きた接続だけを候補から外し、残る接続で処理を続ける。MuseとSparkの両方が枠切れになった場合はQwenへ処理を集める。同列とは優先度が同じという意味であり、処理件数を3等分する制約ではない。

Codex SDKを継続使用し、Spark専用targetとRustからの薄いSDK呼び出しadapterを追加する。Muse・Qwenは現在のHTTP経路を継続する。「同じ扱い」は接続プロトコルの統一ではなく、共通のpool・claim・leaseで別jobを分担できることとする。

  1. 既存SDKの実行CLIを、Spark catalog確認済みのバージョンへ揃える。SDK／依存CLIの更新かcodexPathOverrideの明示指定を選び、JSONイベント互換性を確認する。現在のSDK同梱CLIとPATH上CLIの差を解消する。
  2. codex-sparkという専用targetを設け、model=gpt-5.3-codex-sparkを必須にする。共通codexモデルの変更だけで済ませず、route → target → request → startThreadまでモデルを保持する。通常Codexモデルへ自動fallbackしない。
  3. Rustの実行targetをlocal-llm専用構造からprovider別の構造へ拡張する。Codex targetはJSONの入出力だけを扱うBun/Node adapter経由で既存createCodexProviderを呼ぶ。QueueのclaimやDB保存はRust側に残し、TypeScript Queue worker全体を二重起動しない。これは提案する追加実装であり現状機能ではない。
  4. Qwen worker・Muse・Sparkを共通background poolへ同じ優先度で参加させる。初期案は各target同時1、pool上限3。実行候補からcoding-defaultを除く。同じQueueの別jobを利用可能な空きtargetへ配分する。候補が減っても残る接続を待たせず、各targetの同時実行上限の範囲で処理を集める。
  5. Rust dispatcherに上限付きの並列LLM実行を追加する。DBのclaimと結果保存は既存single writerで行い、LLM待機はwriter外、job所有権確認・heartbeat・lease解放を維持する。既存Queue fairnessも維持する。
  6. 各接続の利用枠を確認し、枠切れの接続だけを候補から除外する。Sparkのみ枠切れならQwen・Muse、Museのみ枠切れならQwen・Spark、両方ならQwenで続行する。provider共通エラー契約にquota・retry時刻を含め、枠の回復を確認できた接続は同じ優先度で候補へ戻す。残量不明を枠切れとみなさず、明示的な枠切れ情報を使う。全接続が利用不能ならjobを待機させ、通常Codexモデルへfallbackしない。

既存のagenticCompileにはcodex fallbackが残る。今回のQueue範囲ではfallback=[]だが、ContextStill全体で通常Codex枠を使わない方針にする段階では、この別経路もSparkへ固定または無効化する必要がある。

6. 確認済み事項と次の検証

分業の受入確認では、3接続が同じ優先度で選択対象になること、Muse・Sparkそれぞれの枠切れで当該接続だけが除外されること、両方の枠切れでQwenが処理を継続すること、枠回復後に同列へ戻ることを確認する。この方針更新は文書のみであり、実設定へはまだ反映していない。

別利用枠、既存SDK有効化、SDKとPATHのCLI差、Muse・Qwenの公開状態、実Queue設定、モデル受け渡しと並列化の不足は確認済み。Sparkの実推論、JSON品質、複数target同時実行、quota切れ復旧は今回実行していない。これらは実装後の検証項目である。

受入確認では、SDKへ渡った実モデルがSparkであること、通常モデルへのfallbackがないこと、利用枠のbefore/after、JSON出力、job保存結果、3target同時実行、quota・timeout・停止時のlease回復を確認する。アカウントを他タスクも使用しているため、通常枠の差分だけを単独の因果証明にはしない。

公式app-serverにはmodel/rerouted通知が存在する。SDKのイベントで実行モデルをどこまで確認できるかも検証する。サービス側で行われた処理を通知後の停止で取り消せるとは保証しない。Sparkでrerouteを観測したわけではなく、アプリ側モデル固定と上流サービス動作の境界を示す。

7. 実装と検証結果

既存SDKへRust Queueから接続するadapterを追加した。Spark専用targetにはgpt-5.3-codex-sparkを明示し、通常Codexモデルへのfallbackを行わない。ChatGPT認証、Sparkのcatalog掲載、専用利用枠を推論前に確認する。CLIはCONTEXT_STILL_CODEX_CLI_PATH、外部PATH、同梱CLIの順に解決する。SDKの依存更新は行っていない。

プールの対象数・並列数に応じてQueue workerを同時実行し、既存の最終使用時刻による選択を維持する。明示的なquotaエラーを設定DBへ保存し、回復時刻までは当該targetだけを除外する。通常の通信エラーを利用枠切れと誤判定しない。設定画面から既存のQwen・Museと同じプールへCodex Sparkを追加できる。3候補を同時使用する場合はプール並列数も3にする。

Rust Queueテスト149件成功、3件は既存のignore。2つのHTTPリクエストが双方の応答前に到着する結合テスト、SparkとMuseの個別除外・Qwen継続・復帰テストを含む。TypeScriptの対象テスト10件と型検査が成功。既存SDKと外部CLI 0.149.1でSparkを呼び出し、要求したJSON出力を確認した。利用量は入力10704、出力57 tokens。SDK出力のmodel表示は送信指定値であり、上流の実モデルを独立に証明するものではない。

稼働DBへのプール登録、daemonの更新・再起動は行っていない。実際の3接続を使うQueue全体の継続運転と、実アカウントを枯渇させる試験は未実施。quotaと並列動作は隔離したDBおよび模擬応答で検証した。

9. Provider Poolへのタスク割り当て統一

Poolの利用可能な候補はFinding・Covering・Episode Distiller・Landscape Curationのどれでも担当できる。モデル名によるcoding-defaultの除外を撤廃した。Codex targetは引き続き別利用枠のSparkを明示指定する。通常Codexモデルへのfallbackは追加していない。

Coveringの独立した先行実行ループを廃止し、他のLLM Queueと同じ並列Pool workerからclaim・推論・保存する。Coveringの応答待ちが、同じtickの空きworkerによるFinding等の開始を妨げない。Pool容量、使用中lease、quota除外、Queueの優先度・pause・入力条件を維持する。LLMを使わないFinalizeは従来のローカル処理で継続する。

Pool参照を固定providerより先に解決するようRustとTypeScriptを統一した。設定画面でPoolを選ぶとprovider=auto、providerPoolId、fallback=[]となり、以前のmodel・localLlmModelを持ち越さない。稼働設定の11ルートも同じ共有Poolへ統一した。構成を解決できないtargetはclaim前に候補から外し、残る候補を使用する。

検証はRust Queue151件成功、既存ignore3件、関連TypeScript60件成功。3候補×4つのLLM Queueの割り当て検査と、Covering・Findingが両応答前にリクエストを送る結合テストを含む。2026-09-12 14:32 UTCにdaemonと設定を反映し、14:33:03 UTCに共有PoolのSpark Findingジョブがcompleted、leaseがworker_finishedで解放されたことを確認した。Qwenには一時的な接続失敗と再試行が引き続き見られる。Museのquota除外は継続している。

全体型検査は今回変更していないtest/sqlite-test-suite.test.tsからのmjs型宣言不足で失敗した。maintainability検査には既存finalize_executor.rsの行数超過が残る。今回の対象テストは成功している。文書全体検査は別変更のvalidated-improvements-implementation-plan-2026-09-12.htmlにある未解決リンクで失敗したが、本書の指摘はない。

10. コードレビューと回帰検証

停止中のFinalizeが他のQueueを妨げる分岐を修正した。Coveringのheartbeatを保存完了まで維持し、保存失敗時は所有権を確認してジョブをpendingへ戻し、leaseを解放する。並列workerはtickの残り処理枠を共有し、速いモデルが次のジョブを取得できる。

無効なlocal providerは候補から除外する。Codexだけが有効な場合もPoolを作成でき、無効化したCodexを既存Poolから外せる。Sparkのquotaリセットを整数秒で保存し、不明な利用率は利用可能と見なさない。

Spark確認RPCの終了直後に次の要求を送って待ち続ける問題を修正した。SDKアダプターはtimeout・出力上限超過で子プロセスを回収する。LaunchAgentのインストールもnpmラッパーからnative CLIを解決し、NodeがPATHにない環境へ対応した。

回帰テストには停止中Finalize、保存失敗からの回収、速いworkerの次要求、無効provider、quota境界、プロセス終了、入力詰まり、出力上限、設定UIを含む。Rust全体489件成功、3件ignore。関連TypeScript75件成功。型検査・Clippy・maintainability検査・差分空白検査は成功した。Sparkの実CLIによるアカウント・モデル・quota確認もavailable=trueで完了した。第9節の型検査と行数制限の問題は現在解消している。

レビュー修正をdaemonへ反映した後、2026-09-12 14:53:08 UTCにSparkのCovering（cover-evidence-f2ab13829108aa4f5d50c3565cc5d766b9c17aef9）、14:53:18 UTCにFinding（rust-finding-job-unix-ms:1788883921938-1350）がcompletedとなった。両方last_errorなし、leaseの解放理由はworker_finished。Spec全体検査も成功し、第9節に記載した別文書の未解決リンクは解消している。Museはquota除外中のため、この再検証でMuseの実推論成功は確認していない。
