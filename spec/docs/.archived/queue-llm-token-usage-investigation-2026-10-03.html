記録不足の根拠

  • llm_usage_logsにはsource、provider、model、入力／出力／合計／reasoning tokens、usage_mode、時刻がある。一方、queue名、job ID、attempt ID、成功／失敗状態がない。
  • TypeScriptのllm-usage-loggerとagentic-llm／distillationのwrapperは正常応答の後に記録する。usageがなければ推定するが、失敗としてthrowされた応答の消費は記録されない。保存自体も非同期で、失敗しても主処理を止めない。
  • Rust Findingは応答から候補contentだけを解析している。Coveringもmessage contentだけを返す。Episode、Curation、共有Agent Session経路にもqueue使用量の永続化はない。crates/context-stilld全体にllm_usage_logsへのwriteは見つからなかった。
  • キューmetadataやqueue eventにも実消費を補完するusage記録は見つからない。token名を含んだ3 eventはエラーメッセージ等であり、usageデータではなかった。
  • max_tokensは出力の指定上限であり、入力・出力の実消費には代用できない。Finalizeの現行Rust経路はembeddingと保存が中心で、生成LLMの呼出しを行わない。embeddingのトークンは別途計測が必要である。

全量を測るために必要な記録

今後、すべてのLLM呼出しにqueue名、job ID、attempt ID、呼出しID、処理段階、実際のprovider／model、時刻、結果状態、入力／出力／合計／cached／reasoning tokens、実測／推定／不明を持つ記録が必要になる。失敗・中断・再試行でも提供元からusageを取得できた分は記録し、不明を0に変換しない。Agent SessionやCodexの内部複数呼出しはsession単位のusageとの二重計上を避ける。job数とLLM呼出し数を分けて、総量と1 job平均を集計する。

これは調査結果と必要条件の整理であり、計測機能の追加は行っていない。既存記録の欠落期間について、正確な実消費を後から生成することはできない。提供元側の記録が残っていれば照合の余地はあるが、今回その取得・一致確認は行っていない。

集計根拠

読取専用で採取した集計JSONにsourceの帰属、全モデル内訳、期間集計、制限を保存した。秘密値やprompt本文は含めていない。 

SELECT source, provider, model, usage_mode, COUNT(*) AS calls,
       SUM(prompt_tokens) AS input_tokens,
       SUM(completion_tokens) AS output_tokens,
       SUM(total_tokens) AS total_tokens,
       MIN(created_at) AS first_at, MAX(created_at) AS last_at
FROM llm_usage_logs
GROUP BY source, provider, model, usage_mode;
