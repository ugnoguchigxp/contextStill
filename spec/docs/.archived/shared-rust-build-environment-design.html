Tauri / Rust共通ビルド環境基盤：設計メモと段階的移行計画

2026年9月21日時点のFoundry、contextStill、SAAAの調査に基づく。NightWorkersは停止済みのため対象外とする。本書の結論は、依存の取得元とコンパイル結果を同じ単位で共有しないことである。Rustup toolchain、Cargoのregistry / Git download、内容アドレス型のコンパイルキャッシュ、検証済みのnative prefixはユーザー環境で共有する。一方、Cargo.lock、Cargo feature、build script、Tauri設定、target出力、最終成果物はプロジェクトまたはcheckoutごとに分離する。

決定要約

  1. CARGO_HOMEは既定の~/.cargoを共有し、crates.io archive / sourceとGit database / checkoutをCargo自身の排他制御に委ねる。Cargo.lockは各リポジトリに残す。
  2. CARGO_TARGET_DIRはリポジトリ間で共有しない。環境側へ移す場合も、project ID、checkout ID、build unit、target tripleで分離する。異なるworktreeも別targetとする。
  3. 再利用は共有targetではなくsccacheで行う。Rustだけでなく、target固有のApple clang / clang++設定とCMake compiler launcherを通じてcc crateとCMakeのcompileも同じcacheへ載せる。compiler、入力、flag、環境を含むcache keyで安全に共有し、targetは削除可能な作業領域として扱う。
  4. SQLiteとlibwebpは当面bundledを維持する。現在のcrateは別version・別featureであり、Homebrewの同一ライブラリへ強制的に切り替えると再現性と配布互換性を失う。コンパイルコストの共有はsccacheに任せる。
  5. OpenSSL、FFmpeg等、将来system native dependencyが必要になった場合だけ、Foundry管理のversioned native prefixを使用する。グローバルなLDFLAGSやPKG_CONFIG_PATHは設定せず、Foundry経由のプロセスに限定して注入する。
  6. Foundryは環境のsource of truthではなく、宣言の検証、setupのplan / apply、環境変数の生成、doctor、cacheの観測と限定削除を担う。各リポジトリのrust-toolchain.tomlとCargo.lockが要求versionのsource of truthであり続ける。

2026年9月21日の実装結果

初期基盤をFoundryへ実装し、contextStillとSAAAをproject宣言へ登録した。Foundryはdoctor rust、cache status、setup rust、env rust、run rustを提供する。foundry-rust.tomlにproject ID、Rust toolchain、独立したCargo build unitを宣言し、外部targetをproject、checkout、unit、host tripleで分離する。共有するのは既定のCargo download cacheとsccacheだけである。

macOS arm64環境へRust 1.92.0、sccache 0.18.0、pkgconf 3.0.7、CMake 4.3.1、Ninja 1.13.2を準備した。ユーザーのshell rcと~/.cargo/config.tomlは変更していない。contextStillにはrust-toolchain.tomlを追加し、1.92.0、rustfmt、Clippyを固定した。SQLiteとlibwebpはbundledのまま維持し、Cargo.lock、build.rs、Tauri設定は変更していない。

Cargo download、target、コンパイルキャッシュ

Download cache

CARGO_HOMEのregistryとgitは全対象で共有する。Cargo.lockのsource、version、checksumまたはGit commitが選択を決めるため、共有cacheがdependency versionを決定することはない。通常buildは--lockedを必須とし、再現性試験では--frozenを使う。private registry credentialはCargo標準credential providerの領域に残し、Foundry profileや診断出力へ複製しない。

Target output

targetは共有cacheではなく、削除して再生成できるproject固有作業領域である。同じcrate名・versionでもfeature、build.rs環境、source path、linker、SDK、profileが異なる。単一targetへ全repositoryを集約すると、fingerprintの想定外共有、同時buildのlock競合、誤った最終binaryの回収、障害時の全project同時invalid化を招く。したがって共有しない。

環境側へtargetを置く目的は再利用ではなく、容量計測、LRU / age-based cleanup、checkout削除時の回収を一元化することである。keyにはproject IDだけでなくcheckout IDとbuild unitを含める。branch名やrepository名だけは衝突するため使わない。checkout IDはFoundryがcanonical pathとrepository identityから生成し、diagnosticでは対応表を示す。cleanは常に解決済みの単一keyを対象とし、cache root全体を暗黙に削除しない。

Compiler cache

RUSTC_WRAPPER=sccacheと共有cache directoryをFoundry が子processへ設定する。全repositoryのshellへ恒久exportはしない。共有cacheの再利用とtarget容量を優先し、初期profileはCARGO_INCREMENTAL=0を既定とした。release、CI相当、clean rebuildは再利用重視profileを候補とする。proc macro、build script、link、最終bundleはsccacheだけで完全共有できないため、hit率だけを成功指標にしない。

C / C++についてはCC_<target>とCXX_<target>をFoundryのversioned target固有のCC_*とCXX_*をprofileで確定したApple clang / clang++へ向ける。cc crateはRUSTC_WRAPPERを利用し、CMakeにはcompiler launcherを明示する。これによりFoundryのlibwebp、contextStillのsqlite-vec、両projectのbundled SQLiteを、source versionとflagが一致する範囲でproject / worktreeを越えて再利用できる。この設定を認識しないbuild systemはdoctorが検出し、直接clangへfallbackした事実を測定結果へ残す。

Foundry管理tool自体も共有する。~/Library/Application Support/Foundry/rust-build/tools/<tool>/<version>/<platform-arch>へimmutableに配置し、sccache、pkg-config、CMake、Ninja、必要なcargo補助toolを全projectから参照する。HomebrewのPATH順序には依存せず、profileが解決した絶対pathを子processだけに渡す。

C / C++依存の共通化

依存ごとに次の3 modeを明示し、暗黙の探索順序に任せない。

Foundryの責務と非責務

責務

  • foundry rust doctor [--json]：rustup / rustc / cargo / component、Xcode / SDK / clang / linker、pkg-config / CMake / Ninja / sccache、native prefix、Cargo download cache、target容量、profile driftを検査する。各項目はstatus、観測値、期待値、remediation codeを返す。
  • foundry rust setup --plan：変更内容、download、必要容量、導入先、rollback先を表示する。--applyを明示した場合だけrustup component、Foundry管理tool、native prefixを導入する。Xcode licenseやOS設定など対話が必要な作業は手順を示して停止する。
  • foundry rust run --project ... -- cargo ...またはenv出力：選択profileの環境変数を子processへ限定して渡し、実行前後にprofile fingerprint、target key、RustおよびC / C++のsccache統計を記録する。
  • Rust toolchain、component、cross target、sccache、pkg-config、CMake、Ninja、LLVM補助tool、cargo補助toolをversioned共有tool storeへ一度だけ導入し、profileから全projectへ提供する。
  • foundry rust cache status / prune：download、sccache、project targetを別categoryとして表示する。pruneはdry-runを既定とし、project / checkout / age / sizeで対象を限定する。
  • immutable profile manifest、native artifact checksum、license / provenance、診断schema versionの管理。個人情報を含むabsolute checkout pathはlocal indexだけに保存する。

非責務

  • Cargo dependency解決、Cargo.lock更新、Cargo featureの一方的変更、repositoryのbuild commandの置換。
  • SAAAのCodex runtimeやWebFetch sidecar、Tauri resource、icon、署名、notarization、最終app bundleの共有。
  • 全repositoryへ同一のRUSTFLAGS、linker、deployment targetを強制すること。
  • Homebrew全体のupgrade、ユーザーのshell rcや~/.cargo/config.tomlの無断編集。
  • targetをcross-project artifact storeとして扱うこと、またはcache hitをbuild成功の代用にすること。

環境profile contract

profile revisionはimmutableとし、最低限次を保持する：schema version、host triple、許可target triple、Rust channel / version / components、Apple clang / SDK制約、linker、managed native dependencyのname / version / checksum / link mode、sccache version / namespace、既定cache上限、環境変数allowlist。生成したprofileを上書きせず、新revisionを作ってcurrent pointerをatomicに切り替える。

環境変数はdeny-by-defaultのallowlistとする。RUSTC_WRAPPER、SCCACHE_DIR、CARGO_INCREMENTAL、必要なPKG_CONFIG_PATH、CMAKE_PREFIX_PATH、dependency固有変数、target固有linkerだけを生成する。credential、PATH全体、ユーザーの汎用CPPFLAGS / LDFLAGSをprofileへ記録しない。実行時には環境fingerprintをsecret除外済みJSONで保存する。

段階的移行計画

  1. Milestone 0 — 完了。 3repositoryでtoolchain、Cargo.lock hash、build command、SDK、target容量、clean / warm build時間を採取する。既存targetを削除せず、一時的なtarget directoryで測る。SAAAはsrc-tauriと4 packageを別build unitとして記録する。
  2. Milestone 1 — 完了。 読み取り専用doctorとJSON schemaを先に実装し、現在判明しているpkg-config / sccache不在、contextStillのdefault cargo不調、toolchain / CI差分、SDK fingerprint、SAAA target容量を再現できるようにする。この段階ではsetup、env注入、cache削除を行わない。
  3. Milestone 2 — 初期版完了。 Rust 1.92.0を最初のmacOS arm64 profile候補とし、required component、sccache、pkg-config、CMake、Ninja、C / C++ compiler 設定を準備した。profileをversioned directoryへ作り、setupを冪等化した。toolの独自immutable store、profile pointer、rollbackコマンドは後続とする。XcodeとHomebrewは自動upgradeしない。
  4. Milestone 3 — 完了。 build graphが小さいcontextStillへ共有sccacheを導入し、rust-toolchain.tomlを1.92.0へ固定した。SQLiteとsqlite-vecはbundledのまま、Cargo.lockとbuild.rsは変更しない。clean / warm / no-op結果が同一であることを確認後、project-scoped external targetを標準配置へ切り替え、targetの容量管理もFoundryへ集約する。
  5. Milestone 4 — build完了、test差分を記録。 src-tauriをwrapperへ移す。build.rsがBunとnode_modulesを参照しresourceを生成するため、Rust cache hit時にもsidecar更新契約が保たれることを重点検証する。既存約112 GiB targetは新laneのcheck完了後、ディスク残量が208 MiBまで低下したため、Cargoのunit単位cleanで削除した。新しい外部targetでdesktop checkは成功したが、全testは現在の作業ツリー由来の5件の期待値差分を残した。
  6. Milestone 5 — 完了。 4つの独立Cargo.lock / targetをbuild unitとして個別登録する。単一workspace / Cargo.lockへの統合はこの環境基盤の前提にしない。後日SAAA内部の依存管理として検討する場合も別設計・別検証とする。
  7. Milestone 6 — native managed prefix。 実際にsystem native dependencyを要求するprojectが現れた時点で、最初の1依存だけをcanary化する。SQLite / libwebpを実験台にせず、明示的にsystem linkを要求するFFmpeg等でABI、配布、license、rollbackを検証してから拡張する。

各Milestoneはopt-inで、従来の直接cargo実行をfallbackとして残す。Foundry wrapperが壊れてもrepositoryのCargo.toml、Cargo.lock、build.rsだけでbuild可能であることを恒久contractとする。

明示的に採用しない案

  • 全repositoryのCargo.lockを1つにする。製品ごとの更新周期とdependency graphを結合するため採用しない。
  • 全repositoryまたは全worktreeで単一CARGO_TARGET_DIRを使う。衝突、lock競合、障害半径が大きいため採用しない。
  • Homebrewの最新SQLite、OpenSSL、FFmpeg、libwebpを全buildへ自動注入する。versionとABIがprofile外で変化するため採用しない。
  • グローバル~/.cargo/config.tomlでlinker、rustflags、wrapperを強制する。対象外repositoryまで変更するため採用しない。
  • FoundryがCargo.lockやproject build.rsを生成・更新する。製品source of truthを奪うため採用しない。
  • 現在の巨大targetを無条件に一括削除する。baselineを採取し、新laneのbuildを確認したunitだけを明示的にcleanする。
