  • B：scripts/testing/sqlite-test-manifest.jsonにBun専用8ファイルを登録し、sqlite-test-suite.mjsで個別プロセス・逐次実行する。環境変数・dotenv・DB・endpointを隔離する。未登録、削除済み、重複のmanifestは失敗する。
  • B：test:sqlite-allとtest:sqlite-manifestを追加。verify:sqliteは同じ一覧を利用し、verify:fastで登録漏れを検出する。PR workflowには独立したsqlite jobを追加した。
  • B：Bun依存のCLIをimportするbackfill-repository-identity.cli.bun.tsをbun:testへ合わせた。Vitestへ移すとNodeのloaderがbun:sqliteを解決できないため、Bun suiteで実行する。
  • C：Dependabotの週次更新対象にbunとcargoを追加。Bunのテキストlockfileには専用ecosystemを使う。週次脆弱性監査、例外管理、GitHub設定の実確認は未実装。
  • E1：Rust検索で順位・候補集合を決めた後、256件ずつsource refsを取得する。各knowledgeのconfidence降順・created_at降順・最大5件を維持し、返すknowledgeの順序は変更しない。
  • E1：候補とsource refsを同一read snapshotで取得する。既存transactionがあれば再利用し、ない場合だけ検索中のread transactionを作る。関数終了時に解放し、外部provider待機をまたがない。snapshot開始失敗はNo Contentへ変換せずエラーを伝播する。
  • A1：consumer一覧と移行契約を作成。OSストア参照、環境変数fallback、clear、cache失効、部分失敗、backup復元の挙動を整理した。実値の保存先切替はまだ行っていない。

3. 検索の変更前後

同じ合成fixtureで、変更前に回帰試験が失敗することを確認してから実装した。1万件のactive knowledge、各1source、候補limit=256の条件でsource参照クエリは10000回から1回へ減少。1100件から600件を残す条件は1100回から3回、limit=0の条件はsource参照クエリ0回となった。テストではSQLite authorizerでsource URI読出しを含むstatementのprepare回数を数えている。

最初の1万件測定は変更前287.272ms、batch化直後81.792ms。後続のsnapshot保持を含む検証では104.913msを観測した。これは開発環境の単発retrieval計測であり、compile全体のp50/p95、peak memory、実運用での改善率を示さない。クエリ本数と結果互換性は自動assertし、時間の固定閾値はこの測定から設定していない。

全文採点はまだ残っている。候補削減、1千/1万件の密なsource分布を含む性能matrix、v2索引のrecall gateはE1の測定補完・E2として継続する。候補数の削減やranking変更を今回の成果に含めない。

4. 全体gateの残存失敗

verify:fastは今回変更していないqueue_lifecycle/finalize_executor.rsが2156行でbudget 2059行を超え、maintainability gateで停止した。verify:rust-daemonは今回変更していないcovering_executor/negative_response.rsのmap_orに対するClippy unnecessary_map_orで停止した。

全体format:checkもsharedのselector JSONや既存boundary script等の整形差分で失敗した。作業中の別変更を一括整形したりbudgetを緩めたりせず、後続のtypecheck・unit・lint・build・SystemContextを個別に実行した。したがって全体verify通過、merge可能、配布可能とは判定していない。
