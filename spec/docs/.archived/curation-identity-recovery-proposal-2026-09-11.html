Curationのidentity復元と再評価の改善案

2026年9月11日。改善コードと回帰テストを実装済み。実稼働daemonへの配備と実DBへの回復適用は未実施。既存のQueue改善設計に対し、identity欠落を比較対象外として終了する分岐と、その回復契約の改訂を提案する。既存設計のprovider公平化などは本提案の対象外とする。

実装と検証結果

Rust executorのidentity preflightは分類状態も検査し、needs_evidenceを記録する。enqueueとpreflightは同じtransaction内で実行し、不適格なpendingが外部からclaim可能になる隙間をなくした。分類のみの変更は同じjobを一度だけ再開し、identity変更は新revisionへ投入する。LLM応答後にもsubjectとcandidateのrevision・分類を再確認し、古い判定をreviewedや統合結果として保存しない。

Sourceのderived_fromとVibeのorigin link、構造化metadataとapplies_toから復元する。複数識別子には既存aliasでの結びつきを要求する。異なるrepositoryへcanonical値を置換せず、同じidentityの表記は共通resolverで正規化する。自動global化は行わない。TypeScript backfillにもリンク収集を追加し、SQLiteでは計画から書き込みまでのtransactionにより途中の証拠変更を防ぐ。

定期回復は60秒に最大500件。最大100件をKnowledge・Source・origin追加等の変更検出に割り当て、残りを永続cursorで巡回する。Vibe metadataの編集、リンク削除、alias変更など更新時刻だけでは拾えない変更も巡回で再確認する。新たな通知storeやDB schemaは追加していない。通常の分類済みKnowledge全件を再分類せず、未解決行とこの回復処理で変更した行を対象にする。128件を超えるoriginの自動判定は保留する。復元、監査、再投入、cursor更新を同じtransactionに含める。

実データのSQLite backupをOS一時ディレクトリへ作成し、providerを呼ばない明示実行テストで評価した。対象は5,200件のjobだけでなく、その時点のactive・repo Knowledge全体。分類済み896件、未解決7,082件から、分類済み1,084件、矛盾または識別子の結びつき未確認602件、未解決6,292件になった。188件を復元してpendingへ追加し、pendingは686件から874件になった。identity理由なのにreviewedだったledger 7,082件は0件へ減った。これはコピー上の結果であり、実DBの回復完了数やLLM処理成功数ではない。

Rust全体テスト465件、TypeScript/UI単体テスト2,109件、SQLite backfillテスト9件を通過。追加検証には分類のみの再開と再発、Source/Vibe復元、複数repositoryの保留、cursorの公平性、監査失敗時のrollback、LLM実行中の分類変更が含まれる。型チェックも通過。厳格Clippyは変更対象外のcovering_executor/negative_response.rsにある既存のunnecessary_map_or警告で失敗し、そのlintのみを除外した検査は通過した。PostgreSQL実DBでのintegration検証と本番LLMでのcanaryは未実施。

根拠と修正する問題

直前のDB調査で、再投入後の5,200件がidentity_unavailableとしてスキップされ、全件attempt_countが0、Qwen/LARMのprovider leaseも0件だった。全件がactive、repo scope、classification_status=unresolvedで、knowledge_itemsのidentity三列が空だった。これは当該調査時点の数値であり、今回の文書作成時に再集計した現在値ではない。

435件にはリンク元Sourceのidentity、141件にはVibe MemoryのprojectRootが存在した。他の構造化された根拠を含め、重複を除く581件に復元候補となる証拠がある。自由記述の絶対パスまで含めると589件となる。ただし、証拠の存在だけで単一repositoryへの帰属が確定するわけではない。581件のうち矛盾なく自動復元できる件数はdry-runで確定する。残る4,619件にも根拠がないと断定せず、今回調べた構造化経路では見つからなかったものとして扱う。

現在のpreflightはcanonical三列だけを検査し、identity欠落時にskippedとreviewedを記録する。enqueue_allの重複抑止はledgerではなく、同じknowledgeとevidence_hashのQueue行が存在するかで決まる。したがってledgerを修正するだけでは再開しない。content_revisionはidentity、scope、metadataなどを含むが、classification_statusや外部のSource link変更自体は含まない。根拠の追加を検出する経路が必要である。

推奨する処理契約

  1. Knowledge保存・分類時と既存データbackfill時に、共通のidentity解決規則で証拠を集める。Curationの毎tickで全provenanceを走査しない。
  2. 単一repositoryに矛盾なく帰属できた場合だけcanonical identityを補完する。classification_statusの更新も既存の分類契約に従い、同じ保存処理で整合させる。
  3. Curation投入時とclaim直前に、同じ適格性判定を使う。repo scopeは分類確定かつidentity解決済み、global scopeは明示的なglobal分類済みの場合に比較へ進める。
  4. 未解決・矛盾はneeds_evidenceとして永続化し、LLM claim対象から除外する。attemptやprovider cooldownを消費せず、根拠や分類の更新で再評価する。
  5. 候補比較と適用結果を確認した後にreviewedを記録する。候補0件の決定論的な判定とidentity未解決を区別する。

identityの復元規則

既存のrepository identity resolver、alias、backfill plannerを拡張し、Curation専用の別解釈を作らない。既存canonical identityを尊重し、knowledge metadataとapplies_to、knowledge_source_linksからSourceのcanonical identity、knowledge_origin_linksからVibe Memoryの構造化projectRoot等を収集する。sourceの所属がknowledge自身の適用範囲を示すかも確認する。複数repositoryの資料を参照することを、単一repositoryへの帰属と混同しない。

識別子を既存alias規則で正規化した上で、帰属証拠が同一repositoryへ収束する場合のみ欠落列を補完する。優先順位だけで矛盾を上書きせず、repoKey、repoPath、projectRefが別repositoryを指す場合やaliasが曖昧な場合はidentity_conflictとして保留する。絶対パスの文字列抽出、本文の語句、LLMの推測だけでは自動補完しない。既存canonical値は自動で置換しない。

identityがないことを理由にglobalへ変更しない。汎用性が疑われるKnowledgeは既存の分類・review経路へ渡す。Curationは分類された適用範囲の中で比較する責務を持つ。

Queueとledgerの扱い

初期改善は既存schemaを利用する。未解決の既存jobはskippedとlast_outcome_kind=identity_unavailableを維持し、ledger outcomeを既存のneeds_evidenceに修正する。矛盾はidentity_conflictで区別する。skippedは今回の実行が終了したことだけを示し、review完了を意味しない。UIはこれらを「根拠待ち」と表示し、完了件数から除外する。pausedは時間経過だけで再claimされ得るため、identity待ちには使用しない。

新規の不適格Knowledgeも同じ判定結果をQueueとledgerに原子的に記録するが、runnableなpendingにはしない。同じrevisionの待機記録を重複生成しない。適格になった場合は、identityまたはscope変更によって新content_revisionのjobを生成する。同じrevisionのまま分類だけが確定したケースでは、identity理由でskippedとなった該当jobだけを条件付きでpendingへ戻す。過去のeventとattemptは保存し、再評価理由をeventへ追加する。

Source、origin link、alias、分類の変更時に影響するKnowledgeを再解決する。通知の取りこぼしに備え、needs_evidence対象に限定した低頻度・上限付きreconciliationも設ける。外部証拠を反映した解決結果と根拠のrevisionを監査記録へ保存し、変更のない入力を繰り返し更新しない。DB更新とenqueueまたは再開は同一transaction、または既存の永続イベント経路で確実に連結する。claim時には最新revisionと適格性を再確認し、古いsnapshotによる実行を防ぐ。

ledger補正はjob参照とrevisionが一致し、identity preflightでreviewedと記録された行だけに限定する。正常な比較結果や別revisionのreviewを上書きしない。新しいoutcomeの追加やQueue全体の状態機械変更は初期改善では不要とする。

既存データの回復順序

  1. 調査時の5,200件を起点に、現時点の全identity_unavailable行と対象Knowledgeの件数・revision・leaseを再集計する。履歴job件数とKnowledge実体数を分け、バックアップと対象manifestを残す。
  2. 拡張backfillをdry-runし、補完可能、矛盾、証拠不足、明示的global分類待ちを集計する。既存のchecksum・監査機構を使い、計画後に変わった行は適用せず再計画する。
  3. 改訂したpreflight、投入判定、再評価経路を先に配備する。preflightの誤ったreviewed記録を限定補正し、矛盾のない対象だけidentityを補完する。
  4. 小規模の復元対象で、保存、再投入、候補取得、実際のCuration結果まで確認する。候補0件ならno_candidateを正常な結果として数え、LLM呼び出し件数を成功基準にしない。
  5. 検証済みの残りへ段階適用する。identity変更で新revisionを作り、過去のskipped行を一律pendingへ戻さない。証拠不足と矛盾は根拠待ちのまま保持する。

復旧処理は同じmanifestで再実行しても重複job・event・identity更新を生まないことを要求する。問題が出た場合は回復batchを停止し、監査のbefore値と現在値が一致する範囲だけを対象に復元計画を作る。回復後の正当な編集やCuration結果を一括rollbackで消さない。

検証と受け入れ条件

  • Source由来・Vibe由来それぞれの単一repository証拠で復元でき、複数repository、矛盾する識別子、曖昧alias、自由記述パスだけのケースは保留できる。
  • 真にidentity不明なKnowledgeがreviewedにならず、attemptとprovider leaseが増えない。毎tickや再起動で同じ待機jobが増えない。
  • Source link追加、分類だけの変更、identity付与で必要な再評価が各1回発生する。取りこぼした変更も限定reconciliationで回復する。
  • backfillと編集の競合、claim直前のidentity変更、処理途中の再起動で古い計画を適用しない。repo境界を越えた候補比較を増やさない。
  • 失敗注入により、identity保存後のenqueue漏れをtransactionまたは永続イベントで回復できる。比較結果・mutation確定前にreviewedとしない。
  • 既存Rust CurationテストとTypeScript backfillテストに上記の境界ケースを追加し、provider credential不要の検証を先に通す。実装時にrepositoryの必要な全体チェックを実行し、その後だけ少量の実行検証へ進む。
  • 回復前後で、Knowledge単位の復元済み・矛盾・証拠不足、job単位の根拠待ち・比較済み・候補なし・provider待ちを別集計する。正常reviewの書換え0件、重複投入0件を満たす。

推奨する実装順は、状態記録と適格性判定の修正、provenance解決と再評価経路、既存データ回復の順とする。Qwenの増設やモデル変更は、このidentity分岐を改善するための前提ではない。
