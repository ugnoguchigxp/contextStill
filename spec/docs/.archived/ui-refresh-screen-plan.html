UI刷新の画面構成案：日常4画面と設定

2026年9月20日時点の提案。ユーザーの利用実態と現行実装・撮影画像に基づく検討案であり、画面削除や実装変更を決定したものではない。

刷新する独立画面はKnowledge、Queue、Context Compile、Doctor、設定の計5画面とする。日常ナビゲーションには最初の4つを置き、設定は下部へ分ける。UI画像案は主要画面5枚と詳細状態3枚の計8枚を想定する。詳細状態は独立したナビゲーション項目にはしない。

判断の基準

画面は内部データの種類ではなく、ユーザーが終えたい作業で分ける。独立画面にする条件は、繰り返し訪れる目的があり、その画面で確認・判断・操作を完結できること。同じ目的の一覧と詳細は同じ画面の左右に配置し、診断の補足・低頻度情報は必要な箇所から開く。

情報は「現在の状況」「ユーザーに必要な判断」「次にできる操作」「結果」の順に示す。正常時は対応不要と分かる表示にする。数値やグラフには、見ることで何を判断できるかを求める。件数を増やすこと自体を成果とみなさない。

初期表示と画面間のつながり

初回の入口はQueueを暫定案とする。運転中の処理と介入の必要性を確認できるためである。通常利用では前回開いていた主要画面へ戻す。各画面で保持する検索・選択状態によって、詳細確認後に一覧を探し直す負担を減らす。

Queueで停止対象を確認し、接続障害が原因なら該当問題を選択したDoctorへ進む。Doctorから該当する設定を開き、修正後に再診断し、元のQueueへ戻る。Knowledgeでは利用実績から関連Compileを開き、Compileでは採用知識の本文へ戻れる構成を目指す。関連IDが取れない箇所は、機能が存在するように見せず実装上の不足として扱う。

Queueには処理単位の進捗と操作、Doctorには環境・接続単位の原因と対処を置く。同じ障害で多数のジョブが停止していても、Doctorでは同じ原因を繰り返し並べない。正常な自動再試行待ちや意図した一時停止を、失敗したまま介入が必要な状態と区別する。

5画面は新しく設計する画面の数であり、リポジトリ内の既存ルートを5つへ削除するという意味ではない。低頻度の機能・データ・自動処理は残し、初期段階では既存画面を「詳細ツール」から開けるようにする。

画像生成で検討する8つの状態

  1. Knowledge：検索・一覧・整理の入口。
  2. Knowledge詳細：本文・根拠・利用状況と編集への導線。
  3. Queue：対応が必要な処理・実行中・待機中の全体表示。
  4. Queue詳細：対象・理由・実行情報・次の操作。
  5. Context Compile：履歴一覧と出力。
  6. Context Compile詳細：採用された知識と評価。細かな順位計算は補足に置く。
  7. Doctor：問題と影響・対処。選択した問題の詳細は画面内で開く。
  8. 設定：接続一覧と選択した接続の設定を代表にする。

主画面5枚に、レイアウト検討が必要な詳細状態3枚を加える。各種フィルター、確認ダイアログ、設定の全項目は別画面として数えない。画像は構成案の比較用であり、サンプル件数・未実装の操作を現行仕様と混同させない。

現状から得た根拠と実装上の区別

現行54枚のスクリーンショット一覧を参照。Knowledgeは本文を開くと編集フォームになり、一覧には適用条件・品質・ライフサイクルが同時に並ぶ。Queueは6工程のカードとID中心の一覧が主である。Compileは初期表示が手動入力フォーム。Doctorは指標と警告が多く、関連する設定・処理への移動を中心とした画面ではない。

現行コードの確認先は web/src/modules/admin/components/knowledge.page.tsx、queue.page.tsx、doctor.page.tsx、web/src/modules/context-compiler/components/context-compiler.page.tsx。Queueの型には lastError、nextRunAt、attemptCount、subjectTitle があるため、理由・次回実行予定・試行数・対象名を中心にした表示は既存データから検討できる。

工程を横断した一覧のページング、同一障害の原因別集約、介入が必要かの分類、結果の知識への一貫したリンク、deepStillの接続・実行状態の取得は契約の確認が必要。表示だけで実現できると断定しない。原因が未確定なら不明と表示し、成功した再試行リクエストを処理完了として扱わない。

deepStillというサービス名だけで独立画面を追加しない。ContextStill側で扱う処理状態はQueue、接続問題はDoctor、接続設定は設定、蓄積結果はKnowledgeへ対応づける案とする。調査指示を人が頻繁に作成・編集する必要が生じた場合に限り、別の調査画面が必要か再検討する。deepStill本体の全機能を今回の5画面へ移植する提案ではない。

刷新の優先順位と確認条件

最初にQueueとDoctorで対応が必要な処理から原因確認までの流れを整え、次にKnowledgeの閲覧・整理、Compileの履歴確認を整える。設定は修復の流れを成立させる範囲から着手する。

  • Queueを開いて、介入が必要か、対象は何か、次に何をするかを一覧から判断できる。
  • Doctorで同じ障害の警告を何度も読み解かず、影響と対処先を確認できる。
  • Knowledgeの本文を、編集状態に入らずに読める。整理操作には根拠と対象範囲が示される。
  • Compileを開いて直近の出力を確認でき、採用知識の内容と評価へ到達できる。
  • 対応不要・データなし・取得失敗・情報が古い状態を区別できる。
  • 低頻度画面への到達手段を残しながら、日常ナビゲーションは4項目に収まる。
