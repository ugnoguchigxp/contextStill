ContextStill 再構築の方針提案：知識マップとEumenes向け検索（2026-10-29）

ContextStillをTypeScriptで作り直し、Eumenesが検索して使う知識基盤にする方針を提案する。前提となる事実は現状調査にまとめた。本書は方針案であり、段階ごとの実装計画は別に作る。

決まっていること

  • Eumenesは、ContextStillの知識を検索して使う。
  • Graphの目的は、検索で引いた知識に関連する知識を芋づる式に取ってくることにある。
  • context_compileは、通常のコーディングエージェント向けの機能として残す。
  • 重複と乱雑さは、良いクラスタリングと再蒸留で解消する。テーマに合わせた蒸留は残す。
  • コーディングエージェントの知識は残す。知識9,579件、Episode 14,160件、会話ログ19,730件を引き継ぐ。
  • TypeScriptで作り直し、Rustは排除する。名前はcontextStillのまま、同じリポジトリのmainで作り直す。
  • 旧版はbranch legacy/v1とtag v1-finalに退避済み（2026-10-29）。旧daemonは~/Code/contextStill-legacyから動き続けている。
  • Keychainは使わない。秘密情報の扱いを含め、必要な仕組みはEumenesを踏襲する。
  • 旧版の384次元embeddingは、LARMが提供するembeddingと同じモデル（intfloat/multilingual-e5-small）である。

提案の要約

  1. mainはEumenesと同じ構成で作り直す。Bun、TypeScript、Hono、bun:sqlite、Zod 4、oxfmt／oxlint、domains/<name>/{contracts,service,repository}、依存境界の検査を使う。backendの単一processがSQLiteのwriterを持ち、Web・CLI・MCPはAPIを経由する。
  2. 秘密情報・LARM・ベクトル・queueはEumenesの方式に揃える。秘密はmaster keyによるAES-256-GCMで暗号化してSQLiteに保存し、LARMのtokenは環境変数で受け取る。ベクトルはvector spaceごとのFloat32 BLOBとして持ち、TSで内積を取る。
  3. 知識を3層に分ける。旧版から引き継ぐ知識は原子知識として根拠に回し、クラスタ単位で再蒸留した正本知識と、それを束ねるテーマを作る。検索とcompileの対象は正本とテーマにする。
  4. 知識マップはSQLiteのedge表1つで持つ。正本知識、Episode、テーマをnodeとし、前提、支持、矛盾、置換、具体化、具体例、所属、共起の関係を、由来と確信度付きで保存する。
  5. 検索は「種を取る」と「芋づる式に広げる」の2段にする。FTS5（trigram）、ベクトル、テーマ一致で種を取り、関係ごとの重みと深さ・予算の上限のもとで広げる。結果の1件ごとに、出てきた経路を返す。
  6. 移行は「先に取り込んで検索、後から生成」の順に進める。まず旧DBを取り込み、整理して検索できるようにする。蒸留パイプラインとcompileはそのあとTSへ移植し、移植が済むまでは旧版が動き続ける。

3.3 関係の種類

map_edgesのrelationと、芋づる展開での扱い
relation 意味 主な作り方 展開での扱い
about／broader テーマへの所属／テーマの上位・下位 クラスタリング テーマを中継して、要となる知識へ広げる。結果が少なければ上位テーマへ
requires Aを使う前にBが必要 LLMによる関係判定 強く広げる（前提として添える）
supports／refines 補足・根拠付け／特定の条件への具体化 LLMによる関係判定 中程度に広げる
contradicts 同じ条件のもとで両立しない LLMによる関係判定、極性の対立 点数に関係なく、必ず注意として添える
supersedes AがBを置き換える 再蒸留、統合 Bを出さずにAへ差し替える
example_of EpisodeがAの具体例・根拠になる 同じ会話由来（旧データで3,069組）＋近さ＋LLMの確認 経験として添える
co_used 一緒に使われ、有用とされた usage eventの集計 弱く広げる。単独では表示しない

すべてのedgeに、由来（deterministic、clustering、llm、behavioral、human）と確信度、根拠、extractorの版を付ける。LLMが作った関係は、根拠の確認か利用実績があるまでcandidateとし、展開での重みを下げる。WorldModelの関係（因果、相関、依存）は外界についての主張なので、ここでは持たない。

外部のgraph DBは使わない。nodeは数万、edgeは数十万の規模で、SQLiteの索引と、メモリに載せた隣接リストで足りる。同じDB、同じwriter transactionに置くことで、忘却、backup、rollbackの整合も保てる。

4. 旧版からの取り込み

  • 旧DBは直接開かず、SQLiteのbackup APIで作ったsnapshotから読む。旧daemonが動いていても安全に読め、旧DBは変更しない。取り込みは何度実行しても同じ結果になるようにし、移行が終わるまで差分を追いかける。
  • 取り込む中身：会話ログ（vibe_memories）、wiki・web文書（sources）を根拠に、Episode（episode_cards）を経験に、知識（knowledge_items）を原子知識に入れる。spaceはcodingとし、利用実績（knowledge_usage_events）も持ち込む。
  • 取り込むときに直すもの：
    • 由来の固定文字列（3,033件）は、foundCandidateIdからfound_candidates、finding_candidate_queueと辿って、本当の原記録に結び直す。
    • 時刻はUTCのISO形式に揃える。
    • draftの知識は、gateの判定を見たうえで原子知識の候補として入れる。
  • ベクトル：旧版の384次元embeddingはLARMと同じintfloat/multilingual-e5-smallなので、知識の9,579件は引き継げる見込みである。ただし、同じモデルでもpassage: の前置きの有無や版が違えばベクトルは一致しない。そこで数十件をLARMでpassageとして埋め込み直し、元のベクトルとほぼ一致する（cosineが1に近い）ことを確かめてから、LARMのvector spaceの鍵で登録する。一致しなければ、全件を埋め込み直す（約1万件）。Episodeには旧版のembeddingがないので、新しく作る。
  • 秘密情報は旧版から移さない。旧版のKeychainは読まず、必要な資格情報は新版の設定から入れ直す。

5. クラスタリングと再蒸留

旧版のcurationは、知識を1件ずつ近い5件と組にして判定していた。17,851件のうち15,376件が見送りで、廃止まで進んだのは数件だった。組ごとの判定では、まとまりとしての重複を片付けられない。そこで判定の単位をクラスタへ変える。

  1. 近傍グラフを作る。embeddingで、type、極性、space、scopeが同じものどうしのk近傍グラフを作る。1万件規模なので、TSの総当たりで足りる。
  2. claimクラスタを作る。類似度の高いedgeだけを残し、graph clusteringで「同じ主張」の候補群に分ける。閾値は、人手で同じ／違うを付けた組のサンプルで決める。
  3. クラスタごとにLLMで確かめる。候補群をまとめて渡し、同じ主張の部分集合に分けさせる。plannerとverifierの2段にする。
  4. 再蒸留する。確かめたクラスタごとに正本知識を作る。中身は、統一した主張、適用する条件としない条件、手順、例外、矛盾の指摘、根拠にした原子知識の一覧である。根拠に挙げたIDが実在してクラスタに属しているか、原子知識にない主張を足していないかを、ホスト側で照合する。
  5. 置換を記録する。原子知識をsupersedesで正本へつなぎ、検索から外す。利用実績と確信度は正本へ集計する。
  6. テーマを作る。正本知識とEpisodeを粗い粒度で階層的にクラスタリングし、LLMで名前、説明、aliasを付ける。旧版で散らばったfacet語彙（domainsだけで3,084種）は、テーマへ対応付けて正規化する。
  7. テーマ知識を蒸留する。テーマごとに、概要、要となる正本知識、代表的な経験、注意点、未解決の点をまとめる。これが「テーマに合わせて知識を蒸留する機能」の新しい形になる。

継続的な運用では、新しい原子知識を最も近いclaimクラスタへ加え、そのクラスタに作り直しの印を付けて、背景のqueueで正本を作り直す。テーマは一定の量が変わったときか定期的に組み直す。組み直しの前後は構成員の重なりで対応付け、IDとhandleを保つ。

6. 検索と芋づる展開

  • 種を取る。FTS5はtrigram tokenizerで日本語の部分一致を効かせる。ベクトルは、spaceとscopeで絞ってから内積を取る。3つの経路の順位はRRFで統合する。
  • 芋づる式に広げる。種から、関係ごとの重みとhopごとの減衰をかけて点数を伝える（範囲を限ったpersonalized PageRankに近い）。深さは既定で2とし、nodeごとのfan-out、全体の件数、token予算に上限を設ける。
  • 経路を返す。展開で出た知識には「種Xの前提」「テーマYの要」のように経路を付け、Eumenesが採否を判断できるようにする。
  • 劣化しても止まらない。embeddingかmapが使えないときは、FTSとテーマ一致だけで返し、そのことを結果に明示する。
Eumenes向けMCP toolの案
tool 入力 出力
search_knowledge query、種類、テーマ、space、件数、展開の深さ 種と展開結果。各件にhandle、種類、題名、要約、テーマ、確信度、根拠の要約、経路を付ける。矛盾の注意も返す
related_knowledge handle、関係の種類、深さ、件数 指定した知識から辿れる関係先

knowledge_feedback handle、判定（used／not_used／wrong） 利用実績として記録する

MCPはbearer token、loopback限定、要求と応答の大きさの上限を持つ。handleは不透明な値とし、内部ID、path、repoの識別子は返さない。Eumenesに返す手順は実行権限を持たない参考知識であり、SKILLやpipelineとして採用するかどうかはEumenesが決める。

7. compileとコーディングエージェント

context_compileは、コーディングエージェント向けの機能としてTSへ移植する。repo scopeの分離（identityが不明なら取り違えを起こさないよう安全側に倒す）、facet、composer、利用評価の仕組みは旧版の契約を引き継ぐ。変えるのは、候補を正本知識にすることと、種の取得に6章の経路を使うことの2点である。移植が済むまでは、旧版のcompile（127.0.0.1:39172/mcp）を使い続ける。

10. 推奨案で進めること（変更があれば指示してほしい）

  1. 原子知識は、正本ができたら検索から外し、根拠としてだけ残す。
  2. 原子知識はgateを通れば自動でactiveにする。人手の承認は、確信度の低い正本知識に限る。
  3. Eumenesの検索は、既定でgeneralとeumenesのspaceを対象にし、codingは指定したときに含める。この点は、N1の評価集合でcodingを含めた場合の効果を見てから決め直してもよい。
  4. 個人の原記録からrule／procedureを作らない方針（SAAA契約と同じ）は、N6まで保つ。

付録：採らなかった案

  • 別リポジトリでの新規作成：名前をcontextStillのまま残すため、同じリポジトリのmainで作り直し、旧版はbranchに退避した。
  • 旧版を少しずつ置き換える：中核（writer、MCP、queue、ログ同期、LARM接続）がRustにしかなく、TSの書き込みもRustのwriterを経由している。データモデルも中心から変わるので、置き換えではなく作り直しになる。
  • 汎用のKnowledge Graph（entity抽出によるGraphRAG）：人物や組織といった外界のentityはWorldModelの領分になる。ContextStillのnodeは知識、経験、テーマに限る。
  • graphだけで候補を作る：種がない状態からの探索は誤りが広がりやすいので、展開は必ず検索で取った種から始める。
  • sqlite-vec：bun:sqliteへの拡張の読み込みが要るうえ、範囲の絞り込みとtop-Kの順序の問題があった。数万件規模なら、範囲を絞ってからTSで内積を取れば足りる。
