Decisionの責務とSAAA連携の検討（2026-09-20）

結論案：ContextStillのDecisionを独立した実行判断サービスとして維持・拡張する優先度は低い。ContextStillは知識と根拠を提供し、SAAAおよび各実行エージェントが現在の依頼・状態・権限と合わせて判断する構成を推奨する。反証検索、検索経緯、結果の記録は残す価値がある。本書は検討結果であり、機能の廃止や運用ルールの変更を実施したものではない。

調査範囲と限界

ContextStillのHEAD 760476e、SAAAのHEAD 5554e72を基準に、作業ツリーの実装と設計文書を読んだ。実稼働バイナリとの一致、Decisionの利用率・正答率・遅延、SAAAの実機検索品質は測定していない。「ほぼ使えていない」は利用者の評価であり、利用件数の計測結果ではない。ソース上の責務と実装方式から以下を提案する。

Decisionを判断主体として残さない理由

  1. 実行主体は現在の依頼、訂正、処理中の状態、権限を持っている。ContextStillへ判断を委譲するにはそれらの同期が必要になり、要約漏れや状態の変化によって判断がずれる。知識検索のために実行状態を丸ごと複製する必要はない。
  2. Rust版のhas_hard_stop_languageは「reset --hard」等の部分文字列で拒否する。その操作を避ける相談でも語句が含まれれば拒否し得る。一方、supportがなくてもrevise_and_executeを返す。固定confidenceの82 / 58 / 76 / 68は、このコード上では実測成功確率ではない。これを強制ゲートの根拠にするのは弱い。
  3. Rust版の検索SQLにはproject / repo scope条件がなく、dynamic_scoreの加算だけでも候補に入り得る。これに対してnative_memory_recall.rsはproject_refとglobal許可を検索条件に持つ。判断器の維持より、適切な範囲の知識が届く検索経路へ投資する方が重要である。
  4. TypeScript版には有用な検索・反証・評価処理があるが、最終判断まで引き受けると呼出し元の推論と重複する。初期ガイダンスの「rejectは停止条件」と組み合わせると、検索由来の助言が操作権限のように扱われる。

Decisionのcoverageが持つ「支持・反証・好み・リスク・検証・代案」の観点は残す価値がある。ただし常に6回検索する方式を固定せず、既存のrecall / context_compileの用途に合わせて必要な根拠を返す。新しい判断APIを名前だけ変えて再構築する必要はない。

feedback.service.tsには実行失敗やuser_overrode等から対象知識のpenalize effectを作る処理がある。移行後は「知識が誤っていた」「適用条件が違った」「実装に失敗した」を分ける。実行失敗だけで知識の品質を下げる結び付けをそのまま継承しない。

段階的な移行案

  1. Decisionの新規機能拡張を止め、MCP、HTTP API、UI、feedback、PR discard scan、doctor、評価fixture、利用者向けガイダンスの依存を棚卸しする。SAAA以外の外部利用者はコード検索だけでは把握できないため、呼出し実績も確認する。
  2. 比較用のケースを固定し、現状Decisionと「検索結果を受け取った実行主体の判断」を同じタスク・根拠・モデル条件で比較する。Rust版とTypeScript版は混ぜずに扱う。
  3. 有効性を確認した経路から必須Decision呼出しとrejectの強制停止ガイダンスを外す。旧APIを残す期間は非推奨を明示する。既存契約のまま黙って助言専用へ意味を変更しない。
  4. 知識検索の取りこぼし・反証・条件・出典を改善する。長期利用が必要になった段階で、安定した根拠ID、版、再検証・削除照会、scopeを含む版付き契約をSAAAと整備する。現行parserは未知fieldを拒否するため、v1へfieldを追加するだけでは移行できない。
  5. 利用者の移行後、Decisionの判定処理・新規作成UI・固有ML学習を撤去する。過去の判断とfeedbackは履歴として保持し、必要な検索traceやlessonを活用する。DBの即時削除は不要。

移行前の検証条件

比較対象には、日本語の言い換え、支持と反証が競合するケース、禁止操作を「避ける」相談、古い知識、ユーザー訂正、異なるprojectの知識、検索0件、検索停止、実行直前の状態変化を含める。正しい実行・保留・質問の割合、誤った拒否、根拠の取り違え、不要な質問、遅延とtoken量を記録する。検索0件を許可と解釈せず、検索停止を知識不存在と同一視しないことを確認する。

採用条件は、必須の認可・scope条件を満たし、既存Decisionに対して判断品質を悪化させず、誤停止・不要質問または遅延等の事前に選んだ指標を改善すること。知識検索が弱ければ検索品質を先に直す。責務分離だけで検索精度やSAAAの判断品質が向上したとは結論しない。
