LARM 接続を共有する4並列Queueの実装と反映状況

2026年10月4日の接続修正はLARM共通手順へのProvider接続修正を現行仕様とする。以下にある計測APIや固定runtimeを必須とする当時の記述は撤回済み。実tokenizer計測の未達は、公開Providerの受入れと分けて記録する。

2026年10月3日。ContextStillのfindingCandidate、coveringEvidence、episodeDistiller、landscapeCurationが、1つのLARM Agent Connectionを共有して最大4ジョブを同時実行できるよう変更した。Queueはユーザーの指示で全7レーンを一時停止している。ContextStill側のバイナリと設定は反映済み。LARM実機が広告する上限は1件なので、本番4並列の有効化は未完了。

接続と実行の契約

  1. GET /v3/agent-profiles?profile=contextStillでselectorを発見する。複数Providerのprofileからname=llmとOpenAI Chat Completions protocolを選ぶ。
  2. POST /v1/agent-connectionsでprofile=contextStill、client=contextstill、providers=[llm]、audience=saaa-desktop、ttlSeconds=900、allowFallback=false、deploymentPolicy=existing-onlyを送る。discoveryのcatalogRevisionをexpectedCatalogRevisionへ渡し、同じcreateを再試行するときは同じIdempotency-Keyを使う。
  3. readyとclaimableを確認してclaimする。返されたconfiguration.fields.baseURL/modelとcredential.tokenを使い、モデル名や物理ポートを固定しない。
  4. 同時実行上限はmin(ContextStill設定maxConcurrentRequests, LARM healthのllm.capacity.maxConcurrentRequests)。capacity広告がない旧サーバーは1件として扱う。
  5. 共有claimを各ジョブが独立したリクエストとして使う。空きがなければジョブはclaimしない。更新・再claim・設定変更・解放は古いcredentialを使う全リクエストが完了してから行う。
  6. 各実行バッチの開始時にactivityとconnectionを再確認し、bootEpoch、catalogRevision、期限切れ、drainingを検出する。障害時に別モデルへ暗黙にfallbackしない。

claimイベントにはqueue/job、worker、request ID、requested/canonical profile、connection/allocation、bootEpoch、catalogRevision、public model、contextWindow、採用した同時実行上限を保存する。credentialは保存しない。

4セッションのQueue選択方針

空きsessionを割り当てるとき、runnableなジョブを持つQueueのうち、現在のactive lease数が最小の種類を優先する。まずfinding、covering、episode、curationを各1件へ分散し、他の種類に実行可能ジョブがなければfindingとcoveringを並列実行して残りの枠を使う。片方だけにジョブがある場合は同じQueueを最大4件並列にできる。

選択とclaimを同じSQLite Writer transaction内で行うため、4workerが同時に動いても古いactive件数を使って同じQueueへ集中しない。既存のpriority・aging・burst fairnessは同じ負荷のQueue間で適用する。実行中ジョブの差し替えはしない。episodeとcurationはそれぞれ同Queue内1件までとする。

実装上の変更

  • RustのLARM managerはcontrol操作の排他と、最大4件のrequest permitを分離する。最初のdiscovery/create/claimをworker起動前に行う。
  • SQLite Provider leaseはLARMの同じtarget IDに複数のactive leaseを許可する。static Providerには従来のtarget単位排他を維持する。SQLite Writerでclaimを直列化し、5件目を待機させる。schema revisionは10。
  • coveringの全3ルートが同じLARM connectionを指す場合、他のQueueと同じ共有枠で実行する。covering modeとcanary job制約は維持する。landscapeCurationは台帳更新の競合を避けるため同Queue内1件を維持する。
  • 同時実行時のworker/lease/event IDの衝突を防ぐため、時刻に加えて単調なプロセス内sequenceを使う。

実機で確認した未完了条件

公開discoveryはcontextstill-backgroundのllm=qwen-agent-workerを返し、catalogRevisionは7545f8b0f5ed778abced40014d61ef9f97a3e20b40f0d66e49cb8ca1e99e7784。LLM subsetでcreateは202、ready後のhealthとclaimは200、解放は204。healthはmaxConcurrentRequests=1を返した。検証接続は解放済み。

LARMリポジトリにはOrnithのContextStill専用runtime、4スロット、KV総容量262144、ContextWindow 32768の設定があるが、現在の稼働リリースdbbe3237171218d94a9c1f3eeba8aef586288637には未反映。LARM作業ツリーには今回の設定以外も含む多数の未コミット変更があり、本タスクでは別サービスの配備を変更していない。

4並列の実機完了条件は、新しいLARM releaseの公開profile/claimがOrnithを返すこと、llm healthが上限4を返すこと、1接続から4リクエストが同時実行されること。これを確認してから、停止した4種のQueueを再開する。

ContextWindowとKVの区別

64K×4はサーバーの各slotに割り当てるKV容量。32Kは1回のLLM呼び出しにおける入力と最大出力の合計上限であり、4ジョブの累計ではない。今回contextWindow契約の受信とclaim照合・記録を追加したが、実tokenizerで最終promptを測り32K以内に再構成する処理は追加していない。

Ornith専用runtimeでは、consumerが利用できるcanonical tokenizer測定の提供が未確認。既存LARMのcontext-measurementsはmanaged-context認証済みruntime向けで、このruntimeにはその認証がない。従って、32K上限の厳密な保証や入力超過時の分割は別の未完了条件として扱い、文字数推定や物理backendへの直接接続で代用しない。

コードレビューで修正した問題

共有接続、ジョブ取得、停止・再設定、接続解放、ContextWindow契約を再レビューした。以下の問題を修正し、回帰テストを追加した。修正後の再レビューで、今回の差分に追加の修正指摘は残っていない。前述のLARM配備と32Kの厳密な入力制御は未完了条件のままである。

  1. 共有targetの確認からrequest permit取得までの間に更新・再設定が介入する競合を解消した。同じロック内で設定・target・capacityを確認してpermitを取得する。
  2. 準備時とclaim時でcovering mode、polarity、canary対象の判断が異なっていた。同じ検索条件を使い、実行できるジョブがない接続は準備しない。空の許可リストは対象なしとする。
  3. 接続待ち中のQueue停止やrouting変更がclaimに反映されなかった。Writerでclaim直前に最新設定と停止状態を読み直す。
  4. LARMのprefixだけで共有leaseを許す条件が広すぎた。poolと唯一のtargetが同じLARM識別子である場合に限定し、SQLiteのunique制約も同じ条件へ変更した。
  5. ContextWindow変更をdiscoveryから接続・claim・更新まで照合する。不正な上限、reserveとmarginで入力予算がなくなる契約、整数overflowを拒否する。
  6. 一時的なDELETE失敗で復帰できなくなっていた。古い接続identityを保持して解放を再試行し、成功するまで新しい接続の作成とrequestの受付を拒否する。

前提のトークン調査は1回のLLM呼び出しのContextWindow調査を参照する。
