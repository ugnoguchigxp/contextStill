添付指示と最新LARM文書の相違

最新作業ツリーの specs/contextstill-context-window-tiering.html は固定3 slot案を不採用とし、64K・128Kの最小tier選択を記載する。256Kはproduction tierとして未受入である。同じswap groupのruntimeは同時loadされないとも記載されている。これは添付の64K・64K・256K想定と異なるため、いずれの数値もContextStillへ固定しない。未配備の内部設定をliveの広告として扱わない。

ContextStill側の変更箇所と所有権

  • dynamic_provider.rs：max_concurrent=1固定、registryからmanagerをremoveするcheckout、1ジョブがmanager全体を保持する構造。並行checkout時には同じconnectionIdのmanagerが重複生成され得る。
  • provider_lease.rs：Pool容量をtarget数までに丸め、使用中targetを一律除外する。staticの既存排他は維持し、契約確認済みdynamic targetだけrequest枠を別計算する必要がある。
  • executor.rs：worker数に動的capacityを反映し、max_claimsと並列数を区別する。Provider HTTP待機はSQLite writerの外で行う。
  • provider_connection/manager.rs：各job前にactivityを確認しactiveならreleaseする。共有connectionの追加admissionに同じ判定は使えない。初回確立のfail-closed gateと追加requestのadmissionを分離する必要がある。

採用予定のownershipはconnectionIdごとに共有managerを1つ、各requestにはpermitを1つとする。create・ready・claim・renew・releaseはsingle-flightとし、request全体をmutexで覆わない。1件終了はpermit返却でありconnection releaseではない。queue idleかつactive permit 0でのみreleaseする。credentialはメモリ内だけに保持する。

直前の設定提案に記載した「session IDの終了追跡」は /v1/agents/sessions 接続用であり、この共有Chat Completions descriptorと同一ではない。本統合で返すのはrequest permitである。通信断で上流実行が継続している可能性を、ローカルHTTPの終了だけで解消したとみなさない。LARM側のadmission・cancel・終了保証に従う。

LARMへ追加を依頼する公開契約

以下は要求事項であり、存在を確認したfield名ではない。正式なAPI型とfixtureが確定した後、そのfieldだけをContextStillのdeny_unknown_fields付き型に追加する。

  1. descriptorまたはそれに紐づく公開応答で、同時request上限、必要ならsession上限、それぞれの共有範囲と単位を広告する。catalog・connection・claim・health間のidentity/revision対応を定義する。
  2. 追加requestを同じconnectionへ送れる条件を公開する。自身のworkloadと他サービス優先・drainingを扱うadmission契約を定義する。healthのacceptingRequestsが何を保証し、競合した際にどのretryable応答になるかをfixtureで示す。
  3. 選択可能なprofile/providerのcontext上限、output上限またはreserveの意味、安全marginを公開HTTP応答へ含める。最小tier選択後、実際にclaimしたdescriptorと同じwindowであることを照合できるようにする。
  4. capacity不足・tier不足・429・timeout・cancelの型付き応答、retry時刻、request終了の意味を定義する。通信断や再起動時に上流処理の終了をどう確認するかを示す。
  5. 単一connectionへ3requestが許可されるfixtureと4件目の拒否またはqueue応答を提供する。現行が1のみなら1を広告する。64K・128K・256Kも実際に受入済みの値だけを返す。

移行・検証・rollback

公開契約が揃った後の実効capacityは広告値とContextStill上限の小さい方とする。旧設定の既定値は1。情報なしの場合は従来1枠を維持するか、window検証が必須の新モードではclaim前に明示的に待機させる。未知fieldを黙って無視する移行はしない。現行checkout競合があるため、現在の実装が並行呼び出しに対して安全な1枠を保証するとの主張はしない。

最終messages・system・tools・retrievalを含むtoken見積り、出力予約、広告marginの合計がwindow以下の候補だけを使う。候補なしは本文を切り捨てず、semantic attemptを消費しない型付き待機にする。3枠広告時は4件目をpendingに残す。値が1なら1、別tier集合ならその集合に従う。

実装後は添付の16項目をfake HTTPとbarrier/channelで検証する。single-flight、3件の到達とresponse相関、4件目未claim、全終了経路のlease/permit返却、static排他、token境界を含む。今回製品変更を行っていないため、これらの新動作テストおよび実機canaryは未実施。巨大モデルでの試験で不足契約を代用しない。

今回のrollbackは不要で、既存実行方式を変更していない。将来は新規admissionを止めてactive permitをdrainした後、上限1と従来profileへ戻す。稼働中requestのcredentialを即時破棄する設定切替は行わない。実装時の検証コマンドはcargo fmt --check、cargo check -p context-stilld、cargo test -p context-stilld、対応するTypeScript settings test、bun run check、bun run spec:fix、bun run spec:checkを使用する。

今回の文書検証ではbun run spec:fixが出力を返さず停止したため終了させた。spec:checkも別途起動したが完了を確認できていない。標準HTML parserで2文書の単一article・lang・h1・section ID・th scope・タグ対応を確認したが、これはSpec HTMLチェックの代替合格とはしない。調査時のpackage.jsonには添付指示のdocs:check:fixとcheck scriptが存在しないため、実装再開時にその時点の検証scriptを確認する。
