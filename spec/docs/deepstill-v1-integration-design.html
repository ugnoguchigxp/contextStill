  • canonical JSONは、文字列とobject keyをUnicode NFCへ正規化済みであることを要求し、object keyをUTF-16 code unit順に並べ、array順を維持し、有限numberと通常のJSON値だけを許す。空白を加えずECMAScript JSON.stringifyと同じprimitive表現でUTF-8へ符号化する。protocol上のintegerはJavaScriptの安全整数範囲に制限する。requestはidempotencyKeyとrequestHash、resultはresultHash、capabilityはcapabilityHashを除いた全bodyをSHA-256の対象にする。未知minor fieldも改ざん防止のためhashへ含める。
  • DeepStill現行実装はACKと時間retentionを持たないため、capabilityはretentionMode=manual_delete、retention/graceをnull、acknowledge operationを未宣言とする。ACKを実装済みとみなさない。
  • repository間で共有する構造contractはshared/contracts/research-plugin-v1.schema.json、ContextStillのruntime検証はsrc/shared/schemas/research-plugin-v1.schema.ts、portはsrc/modules/research-plugin/contracts.ts、相互fixtureはshared/fixtures/research-plugin-v1.jsonに置く。JSON Schemaで表現できないhash、budget間比較、参照整合はx-contextstill-integrityとruntime検証を正本とする。

1. 結論

DeepStillをContextStillへコードとして取り込まず、localhost上の独立serviceとして接続する。 両repo間でTypeScript package、DB、migration、内部moduleを共有しない。共有するのはContextStill所有の版付きtransport非依存contractとcontract fixtureだけとし、HTTPは後続の薄いtransport adapter候補とする。

後続統合は3つの境界に分ける。ContextStillは必要性を確認した場合だけoptional LLM gatewayをDeepStillへ提供する。ContextStillのQueueはResearch Brokerを介してDeepStillへ非同期jobを委託する。DeepStillの結果はResult Ingressが検証し、Report参照、外部根拠、Knowledge候補、Episodeへ用途別に取り込む。 

ContextStill Queue
  └─ Research Broker ──HTTP──> DeepStill V1 job
                              ├─ search / crawl / report
                              └─ HTTP──> ContextStill LLM Gateway ──> configured provider

DeepStill result ──HTTP poll──> Result Ingress
  ├─ parent Queueの再開入力
  ├─ Report・claim・source provenance
  ├─ Knowledge candidate pipeline
  └─ EpisodeCard

4. ContextStill LLM Gateway候補（後続・optional）

この節はResearchEngine contract成立後に評価する候補設計であり、最初の実装単位ではない。endpoint名、request拡張、lease方式は未確定とし、capability negotiationで利用不能でもDeepStill standaloneとResearchEngine lifecycleが成立しなければならない。

ContextStillに/api/integrations/deepstill/v1/llm/chat/completionsを追加し、DeepStillの既存CompatibleLlmから利用する。wire formatはDeepStillが現在使うOpenAI chat completionsの必要部分に限定する。公開OpenAI互換serverを目指さず、messages、model、max_tokens、temperature=0、非streamingだけを受ける。

  • ContextStill設定へtaskRouting.deepStillResearchを追加し、そのrouteのprovider、model、fallbackを使う。
  • DeepStill側はLLM_BASE_URLをこのendpointの親pathへ向け、Bearer tokenを既存LLM_API_KEYで送る。LLM_MODELにはprovider実modelではなく論理名contextstill/deepstill-researchを指定し、任意modelへの迂回指定を許さない。
  • ContextStillは既存のLlmChatRequestへ変換し、usage、provider、実model、request hashを既存usage/auditへ記録する。DeepStillが送ったsystem messageをContextStill自身のs11tnext manifestとして偽装しない。
  • request body、入力token、出力token、timeoutに専用上限を設ける。tool callと任意URL fetchは受け付けない。
  • responseには通常のchoicesとusageに加え、X-ContextStill-Request-Idを返す。route/provider/実modelは同じrequest IDを持つ監査eventへ記録し、内部target情報をresponseへ露出しない。

親Queueが確保したprovider leaseをDeepStillへ持ち越してはならない。 委託前に親Queueのlockとleaseを解放する。LLM GatewayはdeepStillResearch route用に独立してprovider capacityを取得する。これにより、親jobがprovider枠を保持したままDeepStillが同じ枠を待つデッドロックを防ぐ。

現在のllm_provider_leasesはDistillationQueueNameとqueue rowを前提にclaimするため、そのままHTTP Gatewayへ流用できない。実装時は、同じactive target unique制約とpool上限を使う短時間のgeneric lease操作acquireProviderTarget(ownerKind, ownerId, route)を追加し、ownerKind=deepstill_gatewayとして確保する。外部LLM呼び出し中はheartbeatし、成功・失敗・client abortで必ずreleaseする。SQLiteではresident writer経由の短いtransactionだけでclaim/releaseし、LLM HTTP待ちの間にwriterを保持しない。PostgreSQLでも同じtarget排他を実装できるまでcapabilitiesでGatewayを利用不可と返す。

Gatewayの外向きHTTP endpointは既存Bun APIに置くが、Bun processからSQLiteを直接更新しない。Bun endpointは認証、schema検証、provider呼び出しだけを担当する薄いfacadeとする。leaseのacquire、heartbeat、releaseは、ContextStill residentが所有する既存loopback writer endpointへ型付きcommandとして送り、residentの短いwriter jobで実行する。任意SQLをBun側で組み立てて/writer/queryへ渡す設計にはしない。command routeはMCP toolとして公開せず、既存のsqlite-writer.tokenとowner-only run directoryを使って認証する。接続不能時にBunからDBへ直接書くfallbackは設けない。

  1. Bun facadeがDeepStill principal、request schema、logical model、予算上限を検証する。
  2. residentへacquire commandを送り、routeから選ばれたtargetId、poolId、lease ID、有効期限を受け取る。secretはcommand responseやDBへ含めない。
  3. Bunはsettings memoryから対象targetのcredentialを解決し、そのtargetだけに固定した既存provider adapterでLLMを呼ぶ。fallbackする場合も、residentで次targetを再acquireしてから切り替える。
  4. provider待ちの間はresidentへheartbeatする。成功、provider失敗、timeout、client abortのすべてでreleaseし、Bun crash時は既存のstale lease回収規則で回収する。

resident commandはtarget選択とlease状態だけを返し、credential、prompt、completion本文を受け取らない。これにより単一writer制約を守りながら、既存TypeScript provider群を再利用できる。既存writer endpointへの型付きroute追加、認証、target固定、stale回収までをGateway完成条件に含める。

DeepStillには汎用CompatibleLlmを直接流用するだけでなく、薄いContextStillLlm adapterを置く。jobごとに生成されるproviderへDeepStill job IDを渡し、各requestに一意なrequest ID、prompt kind、prompt manifest hashをextension metadataとして送る。ContextStillのusage logとDeepStillのoperation logをこのrequest IDで照合する。prompt本文やsecretをmetadataへ複製しない。

ContextStillの現行apiAuthenticationDispatcherはSecurity Intelligenceの2つの完全一致path以外をadmin authへ送る。DeepStill統合ではprefix単位の専用principalを追加し、admin session・admin API keyとは別のtokenをconstant-time比較する。capabilitiesを含めhealth以外は認証必須とし、token未設定時は503を返す。admin API自体がnetwork bindされていても、このprefixはloopback peerだけを許可し、Host/Originもlocal endpointと一致させる。 

{
  "model": "contextstill/deepstill-research",
  "messages": [{ "role": "system", "content": "..." }, { "role": "user", "content": "..." }],
  "max_tokens": 12000,
  "temperature": 0,
  "stream": false,

Gatewayは未知model、streaming、tool定義、metadata欠落を400で拒否する。provider枠が一時的に空かない場合はRetry-After付き503、quotaは429、認証失敗は401、timeoutは504とし、DeepStillが一時障害と恒久contract違反を区別できるようにする。

DeepStillの既存/api/jobsをhostへ直接公開せず、host-owned contractを実装する薄いadapterを追加する。以下のHTTP pathはtransport案を具体化するための例であり、ContextStill専用pathとして確定していない。HTTP、MCP、callback/pollingの選択はtransport非依存schemaの確定後に決める。

DeepStill側のHTTP transport例（未確定）
Endpoint 役割
GET /api/integrations/contextstill/v1/capabilities protocol version、engine version、利用可能なoutput、budget上限を返す。
POST /api/integrations/contextstill/v1/jobs idempotency key付きでResearch jobを作る。同じkeyと同じrequest hashなら同じjobを返す。
GET /api/integrations/contextstill/v1/jobs/:id queued/running/completed/partial/failed/cancelled、usage、終了理由を返す。

作成requestはtopicだけでなく、question、purpose、既知の主張、必要な独立根拠、禁止scope、repository identity、親Queue名/job ID、budget profile、期待outputを持つ。ContextStillの内部row全体やsecretは送らない。

budgetはDeepStillの方針に合わせ、targetBudgetを停止・再評価のsignal、hardSafetyCeilingを暴走防止の絶対上限として分ける。target超過だけでは即座に失敗させず、進行中の1 operationとfinalizationに必要な小幅超過を許す。ContextStill LLM Gatewayはhard ceilingを越える単一requestを拒否し、DeepStill resultにはtarget超過量とhard ceiling未到達を別々に記録する。

認証はloopback制限に加えて専用Bearer tokenを必須とする。ContextStillのadmin keyをDeepStillへ流用せず、integration専用secretを使用する。

DeepStillの既存APIは全/api/* requestを16 KiBへ制限している。V1 requestはこの上限内に収め、巨大なsource本文を送らずID、短い既知主張、gapだけを送る。上限を超える情報はContextStill側に保持し、必要な範囲を明示的に要約してから委託する。Integrationだけを理由に汎用APIのbody上限を広げない。

ContextStillから受け取ったprojectRef/repoKey/repoPathは、DeepStillが既存Knowledgeを読む際にも使う。現在のKnowledgeProvider.lookup(query, signal)をoptionalなscope context付きへ拡張し、search_knowledgeへrepository identityを渡す。repo scope jobでidentityを欠く場合は、global Knowledgeだけへ黙って広げずjob作成を拒否する。

ContextStill側のDeepStill endpoint設定はV1では127.0.0.1、localhost、::1だけを許可する。redirectでloopback外へ出ることを禁止し、認証header、prompt本文、result本文を通常logへ出さない。将来remote接続を認める場合はTLSと明示allowlistを別versionで設計する。

source rangeは任意URLを受け取らず、jobとevidence IDからDeepStill内部のsnapshotを解決する。canonical locatorはUTF-8 byte offsetとし、UTF-16 offsetは表示client向けのoptional値にする。range responseは64 KiBまで、redirectとnetwork fetchは禁止し、指定evidenceがそのjobのresultに属さない場合は404を返す。

6. Research Brokerと非同期再開

Queue processorからDeepStillを同期的に最後まで待たない。新しいresearch_delegationsに依頼を永続化し、親Queueをpaused、next_run_at=null、last_outcome_kind=waiting_deepstillへ移してlockとprovider leaseを解放する。既存claimはnext_run_atのないpaused jobを取得しないため、新しいQueue statusを全実装へ追加せず待機を表現できる。

Research Broker reconcilerがDeepStillへsubmit/pollし、terminal resultを取り込んだ後だけ親jobをpendingへ戻す。失敗時も同じ親Queueの通常attemptを無条件に消費せず、delegation側のretry policyで処理する。DeepStill停止時は親jobを待機のまま保ち、通常のLLM provider failureと混同しない。

delegation作成と親jobのpaused遷移は同じ短いDB transactionで行う。Result Ingressの確定と親jobのpending復帰も同じtransactionにする。submitやpollなどのHTTP待ちはtransactionとSQLite writerの外で行う。これにより、crash時に「委託記録なしで親だけ停止」「result未保存で親だけ再開」という中間状態を作らない。

managed SQLiteでは、この節で追加するdelegation、result、evidence、親Queue metadataのmutationもすべてresident writer commandとして実装する。Bun reconcilerはread-only queryと外部HTTPを担当し、取得した応答を検証してからresidentへ短いimport commandを送る。各commandは期待status、parent fence、request/result hashを条件にcompare-and-setし、再送を安全なno-opにする。residentが停止している場合は処理を進めず、Bunによる直接SQLite writeへfallbackしない。 

created -> submitted -> running -> result_received -> imported -> consumed
    └─────────────── unavailable / cancelled / invalid_result

V1はcallbackを使わず、指数backoff付きpollだけにする。親Queueをpendingへ戻せるのはimportedだけであり、result_receivedの段階では戻さない。completed/partial/failedのいずれでも検証可能なartifactがあればresultAvailable=trueとして取得できるが、schema、size、hash、repository identity検査に失敗した結果はinvalid_resultとし親処理へ渡さない。

DeepStillはcapabilitiesでresultRetentionMinSecondsを返し、その最小保持期間はContextStillの最大delegation deadlineと想定停止猶予の合計より長くする。ContextStillはresult importと親job再開をcommitした後にだけ、result hash付きACKを送る。ACKは削除許可であり即時削除命令ではない。DeepStillはACK後もadvertised grace periodを守り、ACKが届かなければ通常retentionまで保持する。ContextStill側のraw bundleと正規化evidenceは独立したretention policyで管理し、active Knowledge、Episode、未完了delegationから参照されるrecordをGCしない。

research_delegationsの主要項目
項目 意味
id / idempotency_key / request_hash 重複submitと再起動後の二重反映を防ぐ。
parent_queue_name / parent_job_id / parent_phase 結果の戻し先を固定する。
research_question / purpose / known_claims / required_evidence DeepStillへ渡す最小scope。
status / deepstill_job_id / attempt_count / next_poll_at submitとpollの状態。
result_hash / result_ref / terminal_reason / usage 結果の同一性と監査。
project_ref / repo_key / repo_path ContextStillのrepository isolationを維持する。

同じparent job + phase + normalized gap hashからの自動委託は1回までとする。partial resultを見て同じ問いを再委託するloopは禁止し、新しい未解決点または明示retryの場合だけ新revisionを作る。

親jobまたはQueue laneが利用者操作でpauseされた場合、自動reconcilerは親をpendingへ戻さない。実行中のDeepStill jobへcancelを要求し、取得済みpartial resultは監査用に保持するが自動反映しない。親jobがcompleted/skipped/failedになった後に遅れて届いたresultも保存だけ行い、再開させない。

現在の全Queue rowに共通revision列はないため、存在しないrevisionを前提にしない。delegation作成transactionでrandomなparent_fenceとdelegation_owned_pause=trueを親metadataへ書く。再開transactionは、paused状態、待機中delegation ID、parent fence、Queue laneがunpausedであることがすべて一致するときだけ成功させる。個別pause/retry APIはdelegation-owned flagを解除する。利用者操作や別workerの更新でfenceが変わった場合は、結果を保存しても親状態を上書きしない。

DeepStillが未起動、protocol不一致、またはdelegation deadline超過になった場合、親jobを無期限に待たせない。Covering canaryではdelegationをunavailableとして確定し、親jobを再開して既存のexternal evidence経路へfallbackする。DeepStillがpartial/failedのresultを返した場合は利用可能な検証済みevidenceだけを渡し、不足分を同じ問いで再委託せず既存経路またはinsufficientへ進める。

V1の上限はresult bundle 8 MiB、claims 200件、evidence package 200件、Knowledge候補10件、episode source 1件とする。各quoteは4,000文字、選択範囲のcontextは12,000文字までとする。DeepStillは上限内へ収めるため、優先度の低いitemを丸ごと省略し、truncated=true、省略件数、理由をbundleへ記録できる。quoteやcontextの文字列途中を切るとhash・locatorが壊れるため禁止する。有効なbundleを上限内で作れない場合、jobをresultAvailable=false、reason=output_limit_exceededでterminalにし、result endpointは409を返す。ContextStillは上限超過bundleをinvalid_resultとして反映しない。

DeepStillのKnowledgeをactive Knowledgeへ直接書かない。 Result Ingressがsource/evidenceを先に登録し、Knowledgeは既存のregister_candidates相当の入口からCovering、dedupe、Finalizeへ流す。DeepStill自身が作ったReportは根拠ではなく、claimと原source locatorを根拠とする。

imported sourceはDeepStillの全snapshot本文ではなく、採用候補が参照するevidence packageだけとする。ContextStillはpackage内のquote hash、offset、package hashを検証し、DeepStillが検証したsnapshot hashをprovenanceとして保持する。ContextStillが原snapshot全文を持たない場合に「原文全体のhashを独立検証済み」とは記録しない。必要ならDeepStillのsnapshot range endpointから該当範囲を再取得してquoteを照合する。

Knowledge候補はすべてを登録しない。ContextStillの用途に合う再利用可能なrule/procedureで、適用条件とverificationを持つものだけを内部のcandidate registration serviceへ渡す。一般的な製品説明や事実はReport/sourceとして保持し、無理にKnowledgeへ変換しない。MCPを自己呼び出しせず、既存normalizationを共有する専用producerdeepstill_result_ingressから候補pipelineへ投入する。

EpisodeをPOST /api/episodesで直接active登録しない。DeepStillのimmutableな実行eventとepisode候補をsource documentとして保存し、episode_distiller_queueへsourceKind=deepstill_researchで投入する。Episode Distillerが既存のvalue review、near-duplicate判定、score補正を通した場合だけEpisodeCardを作る。そのためQueue schema、TypeScript worker、Rust executor、source reader、EpisodeのsourceKind/refKindへこの値を追加し、sourceKey=deepstill job ID + result hashで重複を防ぐ。Episode Distiller自身がDeepStillへ再委託することはない。

9. 親Queueへの戻し方

result取り込み後、親job metadataへ巨大なbundleを埋め込まない。research_delegation_idとresult_refだけを保存し、processorが必要なclaim、evidence、limitationsをIngress repositoryから読む。

raw bundleはresearch_delegation_resultsへrequest/result hash付きのimmutable recordとして1件だけ保存し、利用可能なclaim・evidenceはresearch_evidence_packagesと親delegationへのlinkへ正規化する。親Queueが消費するのは正規化後の行だけで、raw JSONをそのままpromptやdomain resultへ流さない。再importは同じresult hashならno-op、異なるhashならprotocol違反として409相当の監査eventを残す。

  • Coveringは候補の各主張に対応する独立claim/evidenceを再評価し、knowledge_ready、insufficient、duplicate等を既存規則で決める。
  • DeepStillがcompletedでも、ContextStill側のcandidateを自動採用しない。
  • DeepStillがpartialでも、必要な主張を十分に覆っていれば親Queueは利用できる。terminal statusだけで採否を決めない。
  • evidence package、quote hash、locator検証が失敗したclaimは利用せず、result全体を成功扱いしない。
  • 親job、delegation、DeepStill job、生成Knowledge/Episode IDを双方向eventで辿れるようにする。

10. Contract管理

npm packageやgit submoduleを共有contractにしない。汎用ResearchEngine / SourceConnector protocolのownerはContextStillとする。ContextStillはhost-facing JSON Schema、version policy、canonical fixtureを管理する。DeepStillは対応version range、capabilities、内部jobとのmapping、adapter fixtureを所有する。双方のCIで同じ成功・失敗fixture corpusを検証するが、相手の内部型やDB schemaはimportしない。

  • major version不一致はsubmit前のcapabilitiesで停止する。
  • 未知fieldはminor versionでは処理判断に使わず、immutable raw bundleには保持する。必須field欠落は拒否する。
  • request/result hashはcanonical JSONから算出する。
  • ContextStill DB IDをDeepStillの内部主keyにしない。親参照はopaque stringとして保存する。
  • Result Ingressはtransactionalかつidempotentにし、途中でKnowledgeだけ二重登録されないようにする。
  • protocol fixtureにはcompleted、partial、failed、重複submit、stale locator、改ざんquote、未知minor field、major不一致を含める。
  • 各array件数、文字列長、bundle総bytesをschemaで制限する。汎用resourceはconnector kindとopaque resource IDで表現し、HTTP(S)制限はDeepStill V1のweb capabilityにだけ適用する。control文字、未宣言locator kind、重複ID、dangling claim/evidence refを拒否する。
  • Report、source本文、titleは外部由来の非信頼dataとして扱い、ContextStillのsystem instructionやQueue制御命令として解釈しない。Result Ingressはcode、command、URLを実行しない。

11. 実装順序

  1. ContextStill所有のcontractを確定する。 transport非依存のResearchEngine / SourceConnector schema、capabilities、version range、canonical hash、error taxonomy、上限、retention/ACK semanticsを決める。DeepStillの既存projectionとfixtureを入力資料にするが、その内部型を正本にしない。
  2. contract fixtureとcapability negotiationを先に通す。 completed、partial、failed、cancelled、同一key再送、hash conflict、unknown optional field、必須field欠落、stale locator、改変quote/event、repository scope fallbackを両repoのdeterministic testで検証する。まだQueueやprovider routingへ接続しない。
  3. Research Brokerを手動起動で導入する。 resident writer経由のdelegation state、DeepStill client、reconciler、raw result、cancel/restart/idempotency、ACKを実装する。外部HTTP待ちの間はDB writer transaction、Queue lock、provider leaseを保持しない。既存Queueの採否にはまだ影響させない。
  4. Evidence IngressとCovering canary。 claim/evidenceの検証・正規化と親Queueへの参照だけを追加する。明示flag付きのCovering jobだけ委託し、DeepStill結果あり/なしで同じcandidateを比較する。改善が確認できた条件だけauto policyへ昇格する。
  5. Ingressの反映先を拡張する。 canaryで検証済みのsource/evidence基盤からKnowledge候補、Episodeの順に追加する。Knowledgeは必ず既存pipelineへ流し、Episodeは新source/ref kindでEpisode Distillerへidempotentに投入する。Report参照は補助artifactのまま維持する。
  6. optional LLM Gatewayと外部SourceConnectorを個別評価する。 ResearchEngine lifecycleとResult Ingressが安定した後にだけ、ContextStillのdeepStillResearch routeをoptional capabilityとして追加する。provider lease、request correlation、abort、timeout、quota、usageを直接provider経路と比較する。外部SourceConnectorも別feature flag・別fixtureで段階導入する。
  7. 第2段階。 Coveringの実績を確認してからdeadZoneMergeReview、landscapeCurationへ個別に広げる。Finding、EpisodeDistiller、Finalize系からDeepStillへの再委託は無効を維持する。

13. 受け入れ条件

  • ContextStillなしでDeepStillのstandalone開発・verify・live実行が継続できる。
  • DeepStillなしでもContextStillの全既存Queueが従来どおり動作する。
  • 親QueueはDeepStill実行中にQueue lockまたはprovider leaseを保持しない。
  • ContextStill再起動、DeepStill再起動、poll重複でもDeepStill job、Knowledge候補、Episodeが二重作成されない。
  • LLM利用量がContextStillのprovider/model/routeとDeepStillのoperationの両方から追跡できる。
  • Reportの文章ではなく、検証済みevidence packageと原source locatorがKnowledgeのprovenanceになる。原snapshot全文を保持しない場合は独立full-hash検証済みと表示しない。
  • DeepStillの結果だけでactive Knowledgeへ昇格しない。
  • repository identityなしのrepo scope書き込みは拒否される。
  • 同一gapの自動再委託loop、親QueueとLLM Gateway間のprovider lease deadlockが試験で再現不能になる。
  • Queue lane pause、個別job pause、client abort、DeepStill timeoutの各場合に、親jobが勝手に再開せずprovider leaseが残留しない。
  • Covering canaryで、既存処理単独より最終Knowledgeの根拠範囲または正確性が改善し、費用・待ち時間が記録される。
  • dashboardまたはdoctorでdelegationのpending/running/terminal、DeepStill job ID、待ち時間、target/hard budget、fallback理由、生成candidate/Episode IDを確認できる。

13.1 Covering canaryの採用判定

同じfound candidate、同じ既存source、同じContextStill provider route、同じtarget/hard budgetで、既存external evidence経路とDeepStill委託経路を一件ずつ比較する。評価対象は中間Reportの見栄えではなく、最終的なcoverage status、独立source数、必要主張のcoverage、重複、Knowledge本文・適用条件・verification、Episodeの再利用価値、入力/出力token、要求数、待ち時間である。

DeepStill側の評価原則はdocs/handoffs/research-quality-reset/START-HERE.mdとそのtrial historyを正本とする。統合canaryでも次の観測値を失わず、Reportだけ、Knowledgeだけの局所的な改善で採用を決めない。

DeepStill経路が一部caseで改善しても、別の代表caseで最終Knowledge、provenance、重複、終了状態のいずれかを明確に悪化させた場合はauto delegationを採用しない。機械的なidempotencyや監査改善だけは独立して採用できるが、調査品質の改善とは数えない。不採用時もmanual delegationとresult artifactは残し、既存Covering経路をdefaultに戻せるfeature flagを維持する。

16. 最初の実装単位の結果

ContextStill所有のResearchEngine / SourceConnector port、capability・submit・status・result・resource locator schema、canonical JSON hash、deterministic fixtureを実装した。DB、migration、公開API、認証、Queue、LLM Gateway、Knowledge/Episode登録は変更していない。

各portのoperation methodはcapability宣言と対応するoptional methodとする。hostはcapabilityとmethodの両方を確認してから呼び出し、宣言だけ、またはmethodだけが存在するadapterをprotocol違反として扱う。

変更前baselineはTypeScript typecheck、Spec HTML check、unit test 2308件が成功した。追加したtargeted testは、key順に依存しないhash、NFC/finite number制約、capability/request/result hash、standalone JSON Schema、completed/partial/failed/cancelled、DeepStill commit c970f64170eeのcapability mapping、未知minor field、idempotency key再送、dangling reference、claim/evidenceの双方向整合、quote改変、非HTTP Web resource、target/hard budget、retention/ACK宣言、SourceConnectorのsearch/fetch応答とsnapshot hashを検証する。SourceConnector V1で宣言できるoperationは、request/response contractを確定したsearchとfetchだけとし、changesとauthorizeを先行宣言しない。

DeepStillの現行projectionは、Report・claim・evidenceをhost contractへ決定的にmappingできる。一方、現行knowledgeCandidatesとepisodeSourceはhost contractが要求する適用条件・verification・実行event表現を満たさないため、最初のcapability mappingではreport、claims、evidenceだけを宣言する。DeepStill側の追加変更はhost fixtureを渡した別依頼で行う。
