Decision全面撤去の作業手順書

作成日：2026-09-21。対象：ContextStill。状態：実装前。Terraが本書のカードを順番に実行できるよう、対象、変更内容、保持条件、検証、完了条件を固定する。今回の依頼は手順書の作成であり、この文書の追加時点では機能を削除していない。

1. 決定事項

ユーザーはDecisionの全面撤去を希望している。context_decisionとcontext_decision_feedbackの公開・実行・保存・表示・評価・固有学習・運用案内を削除する。非推奨のまま実行可能なAPIや、別名の判断サービスは残さない。最終的な実行判断はSAAA、Codex等の実行主体が担う。SAAAへのDecision移植は行わない。

context_compileは中核機能として維持する。 目的に応じた探索・選別・重複除去・圧縮・構成により、呼出し元へ必要以上のContextを渡さない価値を守る。単純なknowledge検索へ置換しない。LLM composer、根拠付き手順、token予算、反証、project scope、compile_eval、検索・採用履歴、KnowledgeとEpisodeの学習は維持する。

旧検討書はDecisionの責務とSAAA連携の検討を参照。本書が撤去方針の正本である。旧検討書の互換期間やDecision固有処理の再利用案より、本書の「機能を撤去し、compileを変更しない」を優先する。過去のcontext_compile結果や保存済み知識にある「Decision必須」「公開API・DBは変更対象外」は今回の指示に適用しない。

2. 全面撤去と過去データの境界

全面撤去とは稼働する機能の撤去を指す。既存DBの過去記録を消去する依頼とは分ける。既存Decisionテーブルは不活性な履歴として残し、新規SQLiteでは作成しない。旧テーブルの存在を必須にせず、起動・Overview・Doctor・compile・検索が動くことを保証する。既存DBへのDROP、履歴の一括削除、過去のknowledge scoreの巻き戻しは行わない。

削除と保持の固定方針
対象 方針
MCP / HTTP / UI / CLI Decisionを完全に除去。旧ツールを直接呼んでもunknown tool、旧APIは既存のAPI not-found契約、旧画面は既存の未定義route契約に従う。成功を偽装するstubを作らない。
Decision専用実装とプロンプト 削除する。固有ML、feedback effect作成、PR discard scanも対象。
現在のDB定義 専用ORM定義、専用定数、新規SQLiteの6テーブルとindexを除去。共有Episodeの旧source種別・旧counterは既存データを読めるよう必要最小限保持。
既存DB / migration履歴 既存6テーブルはそのまま保持し、アプリからの参照・書込をなくす。適用済みdrizzle SQL、snapshot、journalを書き換えない。PostgreSQLの履歴再生で旧テーブルが作られることは許容する。物理消去は本計画に含めない。
旧形式のimport/export 既存のknowledge portability形式を壊さない。既存Decision除外件数fieldは形式互換のため残してよいが、計数のために旧テーブルを読まない。詳細はD06。
一般的なdecision語 compile選別のagenticDecision、landscape判定、deadzone review、decision-default等の外部provider名、知識本文内の意思決定は対象外。文字列の一括削除は禁止。

既存Decisionの6テーブルはcontext_decision_runs、context_decision_evidence、context_decision_coverage_traces、context_decision_human_feedback、context_decision_feedback、context_decision_feedback_effects。共有knowledgeを削除した際の既存FK動作まで全面変更するものではない。退役テーブルを新しい履歴閲覧サービスとして公開し直さない。

3. 実行方法と作業記録

  1. AGENTS.mdを読み、この作業セッションで未実行ならinitial_instructionsを一度だけ実行する。context_compileで今回の目的を渡す。Decisionを撤去する作業の承認をDecision自身へ求めない。ユーザーの撤去指示を優先する。
  2. git status --shortとgit rev-parse HEADを記録する。既存の変更を戻さない。本書作成時にはqueue_lifecycleのRustファイル、スクリーンショット、複数の調査HTML、artifacts削除等が作業中だった。実行時に再確認する。
  3. カードはD00から順番に実行する。対象ファイルと参照元を読み、編集、指定検証、記録の順で進める。新たな対象が見つかればカードへ追記し、同じ責務の範囲で処理する。
  4. 各カードの結果をspec/docs/decision-removal-progress.htmlへ記録する。rootはarticle lang="ja"、h1は1つ。カードID、状態、変更ファイル、実行コマンド、exit code、既存失敗との差分、次のカードを残す。ログはassets/decision-removal/以下へ置き、相対リンクで参照する。認証情報や私的な知識本文はログへ出さない。
  5. チェックポイントの検証が通るまで次の段階へ進めない。途中で終了するときは「実装完了」とせず、最後に通ったチェックと残作業を記録する。別タスクへメッセージを送らない。

コード変更はこのリポジトリ内に限定する。SAAAやNightWorkers、利用者のグローバルAGENTS.mdを勝手に編集しない。外部利用者への通知は移行案内を用意するところまで。作業完了にdaemon再起動・本番反映は含めず、コードの検証完了と稼働環境への反映を区別する。

verifyはtypecheck、lint、format、Spec、unit test、web build等を内包する。既に成功した個別検査を理由なく繰り返す必要はない。Rust daemon検証は専用データディレクトリを使用する。実行前にscripts/verify-rust-daemon.mjsと各smoke scriptの環境指定を確認し、利用者の稼働DBを指す環境変数が継承されていないことを確認する。live ownership検査は本計画の必須条件にしない。

PostgreSQL用の専用test DBを用意した上でbun run test:integrationとbun run test:mcp:contractを実行する。CONTEXT_STILL_TEST_DATABASE_URLはtest専用DBを指定し、本番・利用者DBを使わない。環境がなく実行できなければ「未検証」を残し、全面検証完了とはしない。LLM credentialを必要とする実機の判断品質比較は不要で、provider fixtureによるcompile回帰検証を必須とする。
