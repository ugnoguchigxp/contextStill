設定の再整理：仕事の責務・実行先・Pool・LARM

後続のLARM統合指示により、共有connectionのcapacity・context window・admissionはLARM公開応答を正本とする。以下の3セッション案は固定値で実装しない。公開契約の不足と最新sourceとの差分はLARM共有connectionの契約調査を参照。agent sessionの終了と共有Chat Completions requestの完了は別の管理単位である。

2026年9月21日。現行作業ツリーの静的調査に基づく提案。先行するUI画像案はすべて不採用。本書は新たな画面デザインや実装承認を意味しない。製品コード、実環境の設定、接続情報は変更していない。

結論

設定の中心を「Providerを登録する」から「仕事ごとに使える実行先と待ち方を決める」へ移す。接続、実行先、Pool、仕事の割り当てを別の概念として扱う。LocalとAPIは対立する分類ではない。ローカル推論もHTTP APIを使い、LARMは推論モデルそのものではなく実行先を動的に確保する接続方式である。

現行Poolは、同じ仕事を処理できる候補の集合と同時実行制御を表す。各モデルへの異なる責務の割り振りはtaskRoutingで行う。「Aが生成しBが検証する」という段階分担をPool内の順序に持たせない。Pool指定ではメンバー全体が選択対象となるため、特定モデルを期待する仕事に異質なメンバーを混ぜない。

現行実装で確認した不整合

  1. Findingはsourceとvibe、CoveringはsourceSupport・externalEvidence・mcpEvidenceを型上は分離している。しかし設定画面は各グループを一括で上書きする。責務別に割り当てた設定を画面から維持できない。根拠：web/src/modules/admin/components/settings/task-routing-settings-panel.tsx:59、112。
  2. CompileのRouteEditorは静的Poolを選択肢に残すが、agenticCompileの型と更新処理にはproviderPoolIdがない。選択内容が保持されない経路がある。根拠：settings-controls.tsx:59、task-routing-settings-panel.tsx:184、src/modules/settings/settings.types.ts:276。保存・再読込までの再現試験は未実施。
  3. LARMメンバーはPoolの型に存在するが、通常のRust実行器はLARMを一つでも含むPoolを丸ごと除外する。動的実行計画は直接LARMを指定したrouteから作られ、Finding・Episode・Landscapeの計画を組み立てる。型に書けることを全タスクでの対応保証にしてはいけない。根拠：crates/context-stilld/src/domains/queue_lifecycle/executor.rs:1936、dynamic_provider.rs:400、834。全呼び出し経路の実環境検証は未実施。
  4. Pool編集UIはLocal LLMと固定のCodex Sparkを主に扱う一方、型はAzure・OpenAI・Bedrock・LARMも表現する。型、編集可能な項目、実行器の対応範囲が一致していない。根拠：web/src/modules/admin/components/settings/local-llm-pools.tsx、src/modules/settings/settings.types.ts。
  5. 実行先プレビューはproviderPoolIdの一致だけで保存済みeffectiveTargetsを再利用する。直接接続同士では双方undefinedとなり、編集中の実行先と古い表示が食い違い得る。根拠：settings-controls.tsx:79。設定候補と実際に選ばれた実行先も分けて表示する必要がある。

Poolの選択は、使用中・クールダウン中などの候補を除外した後のLRUとジョブの優先度・待機時間による。使用中target IDはPoolをまたいで除外する。設定の順番を役割や優先順位と解釈しない。根拠：provider_lease.rs:16、297、346、executor.rs:2183。

実行先には「実行場所（ローカル／外部／未確認）」「接続方式」「固定／動的」の独立した属性を持たせる案とする。provider名やURLだけからデータの外部送信可否を断定しない。検索APIとEmbeddingは推論LLMのPoolに入れず、別の機能として設定する。現行でもsearchとembeddingは独立した設定である。

実行制限はPoolから独立させる

ユーザー指定の運用要件として、OpenAI・Anthropic等のクラウドAPIは並列呼び出しを許容し、今回のLocal LLMはProviderごと最大3セッション、Azure OpenAIは同時リクエスト1とする。約10秒のインターバルはセッション上限とは別の制約として扱う。Azure全般の仕様とは扱わず、接続先ごとの運用制約として保存する。Anthropicはここでは将来の設定例であり、現行provider型への対応済みを意味しない。

接続・実行先・Pool・仕事への割り当てに加え、「実行制限」を独立した共有設定として設ける。同じGPU、サーバー、Azureの制限対象を共有する実行先は同じ制限グループを参照する。別Poolや直接指定、Compileから呼び出しても同じ上限を適用する。独立したローカル実行資源まで全体で直列化しない。

Azureの10秒の起点は未指定のため、「前のリクエスト終了から次の開始まで10秒」を提案上の仮定とする。開始時刻同士を10秒空ける方式とは区別する。例えば処理に20秒かかった場合、次は開始から30秒後以降となる。ストリーミングは終了まで実行中として数える。

制御単位は接続方式ごとに区別する。セッション型Local LLMではセッション枠、通常の推論APIではリクエスト枠を管理する。1ジョブ内の複数LLM呼び出し、再試行、fallbackにも適用する。Poolのジョブ同時実行上限は別に残すが、メンバー1つのクラウドPoolでも複数リクエストを扱えるよう、現行の「target使用中なら一律除外」「Pool容量はtarget数以下」という前提の変更が必要になる。

現行provider_lease.rsのcooling_provider_targetsはprovider_unavailable_retry後の障害待機であり、正常終了後に毎回10秒空ける制約とは異なる。Finding固有のminIntervalSecondsも全呼び出し経路の制限にはならない。共通のリクエスト送信境界で、共有スロットとnextEligibleAtを原子的に管理する案とする。複数workerでも同時取得させず、実行中か不明なtimeoutやlease失効を安易に空き扱いしない。

通常インターバルと障害時backoffは別設定とし、両方の条件を満たすまで送信しない。LARMと直接接続が同じ資源を使う場合、アプリ内だけの制限では外部サービスとの排他は保証できないため、LARMを共通の管理元にするか資源識別と排他を連携させる。

UIでは「Poolと同時実行」を「Pool・実行制限」へ改め、Poolの候補選択と共有制限を分けて編集する。実行先の詳細には「Provider A：セッション2/3、解放確認中1」のように実効制約と占有状態を表示する。解放確認中も上限に含める。Azureには「同時リクエスト1／終了後10秒」を表示する。待機理由も「実行枠待ち」「間隔待ち・残り秒数」「LARMの他サービス利用待ち」を区別する。

追加検証：別Pool・直接指定・CompileをまたぐProvider単位の最大3セッション、Azureの同時リクエスト1と正常終了後10秒の遵守、1ジョブ内の連続呼び出し、独立資源の並列実行、クラウド単一targetの複数同時実行、失敗・再起動時の制限維持。時間制約は制御可能な時計で検証する。

Local LLMのセッション終了を確認して枠を返す

ユーザー訂正により、Local LLMを一律に同時リクエスト1とした前案は撤回する。Providerごと最大3セッションを扱う。Providerはlocal-llmという種別全体ではなく、セッション枠を共有する実体を識別する。保持中のセッション数と、その内部で走る推論リクエスト数を同一視しない。

現行crates/context-stilld/src/shared/agent_session.rs:30では、session作成、turn送信、events受信、releaseの順に処理する。turn.completedで回答を確定し、releaseのHTTP成功を確認して呼び出しを成功にする。turn失敗時もreleaseを試みるが、turnとreleaseの両方が失敗した場合はturn側のエラーだけを返す。今回読んだ関数には、session IDを永続化して解放未確認を再照合する処理はない。サーバー側の最大3枠の実装や終了通知契約はこの調査では未確認。

turn.completedはターン完了であり、session終了の証明ではない。release応答が解放完了を保証するならその成功を使い、受付のみならセッション終了イベントまたは状態照会で確認する。実際に提供される契約を確認して選ぶ。LARMのagent-connection release、ジョブlease解放、session releaseはそれぞれ別の資源の終了であり、相互の代用にはしない。

提案する枠状態は「予約中→セッション利用中→解放確認中→解放済み」。session ID・Provider ID・担当ジョブ・最終確認時刻を記録し、解放済みになるまで枠を占有する。作成要求のtimeoutではサーバー上の作成有無が不明なので、同じ操作識別子を使った照合を前提とする。終了通知の重複で二重返却しない。通信断、プロセス再起動、release失敗では状態不明を空きにせず、サーバー側の状態を照合する。TTLもサーバーが終了を保証する契約がある場合だけ回収根拠にする。

3枠がすべて利用中なら4件目は待機し、1件の終了を確認した時点で1枠だけ返す。設定画面は上限と間隔を扱い、運用状態は利用中・解放確認中・空き枠を表示する。10秒はセッション開始間隔、解放後の枠再利用間隔、セッション内リクエスト間隔を分け、適用対象の確認まではLocal LLMを一律直列化する値を導入しない。

追加検証は、3件利用中の4件目待機、turn完了だけでは枠を返さないこと、release成功または終了確認後の1枠返却、release失敗、作成timeout、終了通知重複、再起動後の再照合とする。これらは提案であり実装済みとは扱わない。

設定は1画面・4区分から始める

新しい画面を増やす前に、設定内の区分を「仕事への割り当て」「実行先と接続」「Poolと同時実行」「検索・Embedding・詳細設定」の4つに整理する。通常は割り当てから入り、接続やPoolは詳細を開いて編集する。

割り当て一覧の1行はQueueではなく独立して指定できる責務とする。現行の11ルートとCompile補助の計12行が基準。Findingの2種、Coveringの3種はグループ表示しても個別値を保持する。一括適用は明示操作とし、対象と差分を見せる。各行には目的、実行先またはPool、候補メンバー、対応状況を表示し、使用不能な組合せは選択させない。

LARM詳細は固定エンドポイント入力欄の流用をやめ、制御接続・profile・audienceを設定する。状態は接続可否だけでなく「他サービス使用中で待機」「準備中」「利用可能」「更新中」「再試行待ち」を区別する。WaitingActivity等の内部状態は既存managerにあるが、UIへの提供方法は別途実装が必要。状態確認操作によって不用意に実行資源を確保しない。

Pool詳細では、メンバー一覧、上限、利用中、待機ジョブ、参照する仕事を優先する。lease回収やagingは詳細へ移す。staleLeaseSecondsはRust側で30〜120秒へ補正されるため、入力値と実効値の違いも解消対象とする。LARMのtoken TTL、リクエストtimeout、Pool leaseは別の期限として扱う。

責務分担の例

以下は初期設定を自動変更する案ではなく、評価後に選ぶ割り当て例である。ローカルなら低品質、外部APIなら高品質とは決めつけない。

  • 大量の定型抽出：必要な出力契約を満たすローカル実行先のPool。同一仕事を複数候補で分散する。
  • 空き時間に進める処理：対応済みの仕事からLARMを直接割り当て、他サービスが稼働中なら待機する。
  • 根拠の評価・最終化：対象責務だけ、品質評価で選んだモデルへ割り当てる。外部APIの利用は明示する。
  • 対話中のCompile補助：背景処理と異なる応答時間の要件を持つため独立指定を維持する。現行契約のままPoolやLARMを選択させない。

「待つ」「同じPoolの別候補を使う」「外部実行先へ切り替える」は別の操作方針である。特にLARMの使用中は故障ではない。将来の切替方針は、対象エラー・待機期限・外部送信可否を明示する契約として追加する。現行fallbackのprovider配列だけでこれらが保証されるとは扱わない。

実装する場合の順序と検証

  1. 最初に設定UIの整合性を修正する。責務別の値保持、Compileの非対応候補除外、LARMの対応範囲表示、無効Poolの扱い、編集中プレビューの更新を行う。既存設定を自動で別の実行先へ移さない。
  2. 既存schemaを維持して4区分へ整理する。接続・実行先の表示を分け、保存前に「どの仕事が、どの候補へ変わるか」の差分を示す。
  3. LARM混在Pool、実行先単位のfallback、物理資源ごとの同時実行制御は別の契約変更として検討する。UIだけで対応扱いにしない。未対応の保存済み設定は値を保持し、理由を示して修正できるようにする。

検証は、責務別設定の保存・再読込、Compileの選択肢とschema一致、直接接続変更時の候補表示更新、LARM稼働中の未claim待機、混在Poolの拒否または明確な非対応診断、同じtargetを参照する複数Poolの排他、Pool全員を候補とする選択を対象にする。将来の外部切替を実装する場合は、未許可時に送信されないことも検証する。

今回行ったのはソースと既存テスト定義の調査、およびSpec HTML検証。推論サービスへの呼び出しや実ジョブでの動作試験は行っていない。性能・品質・費用の最適値は未計測であり、モデル別の固定推奨値は提示しない。
