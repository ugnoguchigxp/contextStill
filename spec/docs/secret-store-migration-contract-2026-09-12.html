2. 保存形式と解決結果

新形式はvalueKind=secret_ref、isSecret=true、実値のないvalue、OSストア上の世代付き参照secretRefとする。参照の形式versionを持ち、未知versionをlegacy JSONと誤認しない。参照はprofileのidentity、namespace、key、ランダムな世代を区別する。別profileへのrestoreは一致を検証し、秘密を自動流用しない。

3. 更新・削除・故障の順序

  1. 保存前に全入力と対応adapterを検証する。OSストアへ新世代を保存し、読出しを検証する。この間にWriter transactionを保持しない。
  2. Writerで設定revisionと参照の比較・切替を確定する。並行更新には期待revisionを使い、後から到着した旧値で新参照を上書きしない。Postgresも同等のtransaction条件にする。
  3. 切替確定後にcacheを失効する。新規requestは新世代だけを使う。既に外部実行を始めたrequestは取得済み世代を使い切れるが、再試行で旧世代を再取得しない。
  4. Writer切替に失敗した新世代、切替後の旧世代を回収対象にする。参照されていないことを確認して削除する。削除失敗は再試行可能な状態として記録し、成功に見せない。
  5. clearはtombstone確定→cache失効→OSストア回収。OSストア削除が失敗してもruntimeが旧値を再使用しない。

起動時に秘密参照を解決できない場合、settings全体をdefaultCacheへ戻さない。秘密以外の有効な設定を保持し、利用不能のproviderのみ理由付きで拒否する。secret解決中のOS認証UI待ちを常駐requestへ無制限に持ち込まない。

4. 移行と復旧

旧row読出し→OSストア保存・検証→参照切替の各段に再開可能な境界を置く。最初は合成DBで障害注入を行い、live migrationは別工程として扱う。OSストアとDBを一つのtransactionとして扱わない。migrationログにはキー名・件数・状態だけを出す。

旧backup・WAL・freelist・OS snapshotには平文が残り得る。保守停止中のDB再生成等の手順、旧ファイルの保管期限、credential rotationを運用手順に記載する。利用者が複製したbackupやSSD上の完全消去を保証しない。新backupを別端末へ復元したら秘密の再入力を要求する。秘密参照を理解できない旧版へのdowngradeは禁止する。

5. A1を閉じるための残作業とA2の受入試験

A1の残作業は、macOSの常駐起動identityによるKeychain get/set/deleteの実機試験、locked/denied時の応答とtimeout、既存ローカルIPCの操作契約、参照identityのrestore時の扱いの確定。Linux/Windowsは実機証拠なしで対応済みとしない。今回、利用者のKeychainや既存秘密を読み出す操作は行っていない。

A2ではmock storeの中断・拒否試験、TS保存→Rust compile/queue利用、複数deployment/model、更新・clear・再起動、store参照欠落、同一/別profile restore、DBとbackupのみをコピーした読出し拒否を試験する。出力検査は構造と合成秘密のバイト検索を併用し、grepだけで暗号化済みとは判定しない。
